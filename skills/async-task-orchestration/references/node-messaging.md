# 节点侧能力边界

这份文档给执行节点看：它决定了节点能跟谁说话、停靠之后会发生什么。设计拓扑时"能不能"以这里为准，"怎么调"以该节点当跳的运行时契约为准。

## 可寻址范围

| 方向 | 是否可发 |
| --- | --- |
| 父节点 → 任意深度的执行后代 | 可发 |
| 子节点 → 父节点 | 可发，上行只有一层 |
| 同父兄弟之间 | 可发 |
| 表亲、祖父辈等跨子树节点 | 不可发 |
| 跨任务 | 不可发 |
| 自己的验收节点、父节点的验收节点 | 不可发，也不可操作 |
| 后代验收节点 | 可收，但投递不唤醒它 |

停靠声明的目标必须满足同一张表：声明一个发不了消息给你的节点，停靠会在提交时被拒。

## 停靠与唤醒

- 停靠的判据始终是"任意一条待注入消息"，不因为声明了等待对象而变窄。
- 声明等待对象只带来两件额外保证：互相等待会被识别成环并强制唤醒环里最浅的节点；被等的节点结束或被暂停时，等待方立刻收到一条带原因的定向消息，正文里回显当初填的停靠说明。
- 不声明就没有这两条，等待只能靠任务级失速告警兜底。
- 声明随下一次停靠覆写，停靠状态被消费时清掉，不会留下陈旧声明招来多余的唤醒。

## 暂停与终止

- 正在执行时收到的消息留在信箱，到下一个安全边界并入，不打断当前这次工具调用。
- 已暂停的节点收到机器发送方（父节点、前门）的消息会解除暂停并开新回合——这等同替操作员按了"恢复节点"。
- 已终态或已被终止的节点拒收，回执里给出原因。
- 等全部子节点结束用派生批次的回收语义；那批结果在整批终局后一起到达，不受"任意一条唤醒"影响。

## 验收与握手

- 验收节点的唯一激活源是绑定执行节点的待裁定提交；发往验收节点的消息只落箱，不唤醒。
- 被检验中的执行节点只放行裁定类消息；同级的普通消息以"目标正在验收"被拒收。

## 排查

- 停靠后一直没醒：先确认被等节点是否还活着，再看消息是不是因为发送方闸门只落箱未唤醒。
- 声明被拒：按回执原因处理——地址不在本任务、目标已终态、目标发不了消息给你，这三种都等不到，不要重试同一地址。
- 被叫醒但没看到预期内容：检查是不是任意一条无关消息触发了唤醒；停靠的语义不筛发送方。
