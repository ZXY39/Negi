# G3KU Web And Admin Architecture

This document describes how the web shell, admin APIs, and browser runtime fit together for day-to-day maintenance.

## Responsibilities And Boundaries

- `g3ku/shells/web.py` owns web runtime startup and binds the backend service into HTTP routes.
- `g3ku/web/frontend/*` owns browser-side rendering, interaction logic, and shell state presentation.
- `main/api/*` and `g3ku/runtime/api/*` own backend contracts consumed by the frontend.
- The browser shell should present backend state; authoritative project/runtime state remains backend-owned.

When debugging behavior, first identify which side owns the state transition:

- If the issue is display text, interaction wiring, or DOM updates, start in `g3ku/web/frontend/*`.
- If the issue is data shape, status lifecycle, or permissions, start in API/runtime services.

## External Agent API Assembly

The channel-agnostic headless surface for third-party bridges is mounted alongside the web/admin routers:

- `g3ku/web/main.py` mounts `g3ku/runtime/api/external_v1.py` at `/api/v1`; the global bootstrap-lock middleware (423) applies to it like every `/api/*` route. Bearer auth and bridge isolation are owned by `require_external_api` (`g3ku/runtime/api/external_auth.py`).
- Turn execution reuses `SessionRuntimeBridge` (same semantic base as `/ws/ceo`); per-session SSE streams come from `g3ku/runtime/external_events.py` hubs.
- The shared outbound drain started by `ensure_web_runtime_services` routes `channel == "ext"` messages to external session event hubs (heartbeat/cron/task-terminal proactive push), registering each one in the durable external outbox before the hub publish (startup replay re-injects unacked entries). Any other channel has no consumer and is skipped with a warning.
- The web CEO catalog groups `ext:` and legacy `china:` rows via `is_channel_session_key`, and the row shape keeps two separate axes: `is_readonly` (history cannot be truncated/forked/renamed, and REST answers `channel_session_readonly`) and `can_message` (the composer may submit into the session). A registered `ext:` row is `is_readonly=true` + `can_message=true`: the web lane hands the input to the external turn service, which is what lets the reply reach the channel — gate and turn contract are owned by `external-agent-api.md`「回合契约」. `china:*` archives and registry-less ext rows stay `can_message=false`; ext rows are registry-driven, so an external session appears in the catalog as soon as its bridge registers it, before any transcript file exists.
- The web UI「外部接入」page (nav `data-view="external"`, `g3ku/web/frontend/org_graph_external.js`) manages `externalApi.enabled` and bridge tokens through `admin_rest` `/api/external-api/*` endpoints; token plaintext is revealed exactly once at issue/regenerate time.

Full contract (endpoints, turn terminal invariant, event mapping, outbound routing): 详见 `external-agent-api.md`.

## Local Startup And Launcher Contract

- `g3ku.cmd` / `g3ku.ps1` / `g3ku.sh` are thin CLI passthrough wrappers around `g3ku_bootstrap.py`; with no arguments they default to `web`. `start-g3ku.*` remains the explicit double-click entry with its own managed-process handling.
- For the `web` command the bootstrap parent stays in the terminal as a readiness supervisor: it spawns the server child, polls `http://127.0.0.1:<port>/api/bootstrap/status` (a g3ku-specific endpoint so a foreign process squatting on the port cannot fake readiness), and prints a terminal banner: success with the clickable URL, or failure with the child exit code plus a pointer to `.g3ku/logs/console.log` (where the child's stdout/stderr are appended). A slow-start warning appears after the probe deadline instead of a false failure.
- `g3ku/web/launcher.py::prepare_web_server_start` self-heals before acquiring the single-instance lock: it terminates leftover web-server processes of this workspace (cmdline `-m g3ku web` or `-c "...run_web_server_entrypoint..."`, scoped by the workspace venv python path or the process working directory, excluding itself). Starting therefore replaces a stale/zombie server of the same workspace; two web servers for one workspace still cannot coexist.
- The single-instance guard is `.g3ku/start.lock` (byte-range lock; metadata pid/port are written right after locking, so a holder killed between lock and write leaves an empty file and error messages may show `pid=unknown` — fall back to `netstat` on the web port when identifying squatters).
- The web port for banners and probes is read from `.g3ku/config.json` (`web.port`, default 18790). Non-`web` commands keep the plain passthrough behavior, and direct `python -m g3ku` still prints CLI help.

## Memory Management Page And Admin Contract

The browser shell has a top-level `记忆管理` page. It is a read-only operator surface for the queued long-term memory runtime, plus mutation surfaces (failed-batch retry/discard, current-memory edit/delete, note edit) that are guarded by in-app confirmation dialogs and `memory/admin_audit.jsonl` audit records rather than an environment flag; only the legacy `POST /api/memory/admin/retry-head` keeps the `G3KU_ENABLE_MEMORY_ADMIN_MUTATIONS` gate.

### Frontend Responsibilities

- The left rail exposes `记忆管理` as its own top-level navigation item, not a nested subsection of model configuration.
- The page shows three panels: unprocessed queue items oldest-first in real queue order (left column top), parked failed batches (left column bottom, `失败记忆`), and terminal processed batches newest-first (right column), including applied, precheck-failed and operator-discarded outcomes. The `失败记忆` panel is hidden while no parked records exist, so the normal page is the queue/processed pair.
- Cards default to collapsed and stay compact; clicking a queue or processed card opens a frontend-owned read-only detail modal for the full payload, with long payloads kept inside scrollable text regions.
- A processed batch card's status slot renders one operation chip per distinct kind in that row's structured `changes`, in first-appearance order, each with its own icon and color (删除=red, 增加=green, 修改=amber, 更新 Note=violet). Only rows without parsable `changes` fall back to `op`/`source_op` and then `write_mode`, whose buckets merge deletes into rewrites and collapse several kinds into one value. A row with no effective change (`noop_reason`, `already_satisfied`, or discarded outcome) shows the single `无变更` status badge and renders that reason in the drawer's 无变更原因 slot; chips appear only where something was actually written.
- Failed cards render red with a failure-category chip (`provider 瞬时错误` / `协议违规`), the parked time, a right-side retry icon and a one-line error preview. Clicking a failed card opens the same detail drawer with grouped meta (类别/停车与重试计数/累计成本/重试策略) and the full `error_history` (failures and requeue events in order) above the original payloads; the drawer footer carries guarded 重试（重新入队尾） and 放弃 buttons, and 放弃 asks for a second in-app confirmation.
- In a processed batch detail modal, the eight meta fields (批次, 状态, 操作, 处理时间, 模型链, 请求数, 输入, 输出) render as one merged 基础信息 group, with 操作 listing the card's chip kinds joined in change order, and the 变更内容 section sits above the 原始请求内容 section. The 变更内容 section renders the structured `changes` payload as one block per affected memory entry, each with its full untruncated content; rewrite entries render the original text and the modified text in a side-by-side comparison, and delete entries render the removed body. Rows whose blocks carry `original_missing` render an explicit `历史批次未保留原文`-style placeholder, and a row flagged `changes_reconstructed` shows a hint that its blocks were rebuilt from the lossy legacy preview.
- The page header's 查看记忆 button opens the memory browser drawer listing the current SQLite memory rows (创建时间, 刷新值, 通过次数, 来源, ID, 记忆内容). The 记忆内容 column renders `ref:note_xxxx` / `见noteid:` references as clickable chips that open the note window, so note refs stay reachable from the table itself. Sort toggles for 创建时间/刷新值/通过次数 and keyword search run browser-side over the fetched snapshot. The drawer header carries an 编辑 toggle next to 关闭: edit mode adds a leading selection column and a trailing 操作 column (per-row 修改 / 删除) plus a bulk bar (全选 checkbox, selected count, 删除选中); 修改 opens an in-drawer dialog for 记忆内容 and minimal_memory whose save asks for a second in-app confirmation. Delete (single or bulk) opens a dedicated confirm dialog that lists the note refs referenced by the selected bodies: a master 同步删除关联笔记 switch with per-note checkboxes (notes still referenced by other, non-deleted memories are flagged 仍被其他记忆引用 and default unchecked), each note row expandable to its fetched body; checked refs are passed to the delete endpoint and their note files removed. Outside edit mode the drawer shows no mutation controls.
- The note window (opened from note chips anywhere) shows the note body and carries an 编辑 toggle: edit mode swaps the body for a textarea whose save asks for a second in-app confirmation and posts to the note update endpoint. Chips rendered from `ref:` and `见noteid:` spellings both open the window, including inside a processed batch's 变更内容; openings from a processed (historical) batch detail pass a read-only flag that hides the edit toggle, so history views never edit notes. The note window stacks above the browser drawer and detail drawers (z-index 105/110 vs 100/96) so it is never obscured by the surface it was opened from. Note files are removed only through the memory-delete confirm dialog above or by `reconcile-notes`.
- Detail drawers and list panels preserve their scroll positions across the 15s auto-refresh: re-renders skip identical content and restore scroll offsets instead of resetting them, and the detail shell only re-orders its sections when the ordering actually changes (unconditional re-parenting resets the 变更内容 scrollbar on every poll).
- `ref:note_xxxx` text is a preview trigger: clicking a note ref opens the note window, which fetches and displays the note body and offers the guarded edit surface described above.
- All mutation controls read their enabled state from the API (`mutations_enabled` on `/api/memory/failed` and `/api/memory/current`, always true for these surfaces); the frontend still renders disabled states defensively if a backend reports false.

### Backend Responsibilities

- `GET /api/memory/queue` and `GET /api/memory/processed` return queue-owned runtime state and terminal batch records (applied rows plus durable discarded rows), each with pagination metadata. Terminal processed rows carry a structured `changes` list — one entry per add/rewrite/delete/note_upsert with `memory_id`, full `content`, and for rewrite/delete also `original_content`. The original bodies are fetched from the SQLite store inside the commit path before the mutation applies, so each terminal row records the before/after state of every affected memory.
- Legacy processed rows that predate the structured `changes` payload are reconstructed at read time: the read path parses their flattened `change_preview` (`新增：/修改 ID：/删除 ID/更新 note ref:` segments) back into per-memory blocks and marks the row `changes_reconstructed`. Original bodies of legacy rewrites/deletes were never captured and are not reconstructible, so those entries carry `original_missing` and the frontend shows a placeholder instead of a before-text. This enrichment is display-only; the persisted `ops.jsonl` row is never rewritten.
- `GET /api/memory/failed` returns parked failed records newest-parked-first with pagination metadata and `mutations_enabled` (always true for this surface). `POST /api/memory/failed/{failed_id}/retry` requeues a parked record under its original `request_id`s at the queue tail; `POST /api/memory/failed/{failed_id}/discard` writes the `operator_discarded` terminal row into `ops.jsonl` and removes the parked record plus any stale queue rows. Missing records answer `404 memory_failed_not_found`, records not in `parked` state answer `409 memory_failed_not_parked`.
- `GET /api/memory/current` returns a snapshot of the current SQLite memory rows (memory id, body, source, refresh count, passed count, compression flag, timestamps) plus `mutations_enabled` (always true for this surface), and backs the memory browser drawer. `POST /api/memory/current/update` edits one row (body required non-empty; candidate document is validated against the memory document limits before the SQLite write; `MEMORY.md` is rebuilt afterwards); `POST /api/memory/current/delete` bulk-deletes rows by id, reports `deleted` vs `missing`, and rebuilds `MEMORY.md` once. The delete payload accepts `note_refs`: only the explicitly checked note files are removed, and the response reports `notes_deleted` / `notes_missing`. Both endpoints append audit records like the other mutation surfaces.
- `GET /api/memory/notes/{ref}` is the note preview contract, returning the note body for an existing `ref:note_xxxx` entry or a clear not-found error when the note file is missing. `POST /api/memory/notes/{ref}/update` writes a new body for an existing note (non-empty, ref format validated) and appends an audit record; there is no note delete endpoint.
- `memory/ops.jsonl` is a rolling processed-history surface rather than an append-forever archive; the backend prunes processed rows older than 7 days, so `/api/memory/processed` is the latest 7-day operator history window.
- Guarded operator mutations on the memory surfaces append an audit record to `memory/admin_audit.jsonl`; successful calls report `audit_logged`/`audit_error` in the response. The legacy `POST /api/memory/admin/retry-head` alone treats a failed audit write as a hard error (rolls back and answers `503 memory_admin_audit_failed`).

### Maintenance Boundary

- If the memory page looks wrong but the raw JSON from `/api/memory/queue`, `/api/memory/processed` or `/api/memory/failed` is correct, debug `g3ku/web/frontend/*`.
- If a `ref:note_xxxx` chip renders but the preview drawer cannot load, compare the frontend `ApiClient.getMemoryNote(...)` request with `GET /api/memory/notes/{ref}` before debugging the memory runtime itself.
- If the page is missing fields, ordering, discarded statuses, structured `changes`, `change_preview`, or request-artifact links already in the API response, debug the admin endpoints or `g3ku/agent/memory_agent_runtime.py`.
- If a rewrite comparison lacks the original text, first check whether the row is flagged `changes_reconstructed`: for legacy rows the placeholder is expected because their originals were never recorded. For a row committed with structured `changes`, inspect the original-body capture in the commit path of `g3ku/agent/memory_agent_runtime.py`; originals are read before the mutation applies and are not reconstructible after the commit.
- If the memory browser drawer fails to load, compare `ApiClient.getCurrentMemories()` with `GET /api/memory/current`. A `404` on that route means the running web process predates the endpoint and needs a restart; frontend files are served from disk with no-cache headers, so frontend-only edits need only a browser refresh.
- If the queue page is stuck on one `processing` batch, treat that as a backend/runtime issue first, not as a frontend pagination bug; processing failures park into `memory/failed.jsonl`, so an empty queue with entries in the failed panel is the provider-outage signature (parking and success-signal requeue semantics live in `runtime-overview.md`「队列状态机与失败停车语义」).
- Mutation controls on the memory surfaces are guarded by in-app confirmation dialogs and audit records, not by an environment flag; only the legacy retry-head endpoint answers `403 memory_admin_mutation_disabled` without `G3KU_ENABLE_MEMORY_ADMIN_MUTATIONS`. A disabled edit/retry affordance therefore points at `mutations_enabled` in the API response or the frontend defensive state, not at a missing env var.

## Log Audit Page And Event Contract

The left rail carries a `日志审计` page: a read-only, single-panel surface backed by a structured event sink — one untitled terminal-style stream of every raw event, newest first, paginated at 100 events per page. The page keeps no per-subsystem classification, no 24h rollup, and no error-only surface: every event, errors included, lands in the one stream, and each row's source tag is derived from its `subsystem` field as it is rendered. `level` stays an API-side filter rather than a page control.

### Frontend Responsibilities

- The `日志审计` nav item carries the first in-nav unread badge (`#audit-nav-badge`, class `.nav-badge`): a red pill capped at `99+`, hidden at zero. The badge is always-on, not view-gated: a 30s poll of `GET /api/audit/events?limit=1&since=<lastSeen>` renders `total` as the unread count, so the badge is visible from every view.
- The lastSeen marker lives in sessionStorage under `g3ku.audit.last-seen.v1` (tab-scoped, no flush on unload). First visit (no stored marker) anchors it to the newest existing event timestamp, so historical events never light the badge. Opening or in-view-refreshing the audit page marks everything read (marker = latest known event timestamp, badge cleared). `since` is a strict string-greater comparison on server-side ISO timestamps, so events stamped at the exact read moment are not double-counted.
- The stream panel renders every event newest-first as one terminal-style line (system-local time | level | source | summary, monospace), with JSON-detail expansion per line. Timestamps are rendered from the stored offset-aware ISO value through `Date` into the operator machine's system-local `YYYY-MM-DD HH:mm:ss`; the raw ISO string stays in state untouched because the badge's `since` comparison is a server-side string comparison.
- The stream itself is the view's scroll container (`.audit-event-list` with `overflow-y: auto`), while the pager footer stays pinned; the panel takes the remaining view height (`flex: 1 1 auto; min-height: 0`), so a 100-row page is reachable with the wheel instead of being clipped. Quiet 15s polls preserve the list scroll offset so reading older rows is not interrupted; paging and the explicit `刷新` reset the list to the top.
- The panel is paged, not load-more: `AUDIT_PAGE_SIZE` is 100, the footer shows `第 X/Y 页 · 显示 A-B / 共 N 条`, and `上一页`/`下一页` drive `offset = (page - 1) * 100` and disable at the first/last page. The view refreshes every 15s while active — quiet polls reload the current page so paging is not reset under the operator, while the explicit `刷新` button and the first entry into the view reset to page 1 (newest). Out-of-range pages clamp back to the last page, so a trimmed ledger never leaves a blank page. When a quiet poll lands on a page other than the first, the newest-event timestamp is fetched separately so the read marker still tracks the true head.
- Memory failures are read-only here: their events appear inside the stream, while retry/discard lives in 记忆管理.

### Backend Responsibilities

- The sink is `g3ku/audit_events.py` writing one JSON object per line to `<workspace>/.g3ku/audit.jsonl`. Record fields: `event_id`, `timestamp`, `subsystem`, `level` (`info`/`warning`/`error`), `event_type`, `summary` (≤240 chars), `detail`. Retention: a trim pass kicks in once the file exceeds ~2MB and keeps the newest 2000 events via pid-suffixed temp write + `os.replace`; reads cap at the newest 4000 events and skip malformed lines. Appends are small single-line writes shared by the web process and the managed worker, so cross-process semantics are best-effort (at worst a few events drop during a rare trim, never corruption).
- `emit_audit_event(subsystem, level, event_type, summary, *, detail=None)` is the one-call emitter recipe: fire-and-forget, never raises, returns False when unconfigured. The sink is configured once in `make_agent_loop` (`g3ku/runtime/bootstrap_factory.py`), which covers the web process, CLI and managed worker; an unconfigured sink writes nothing (no cwd fallback, so provider-factory unit tests never pollute a workspace).
- Signal sources: `provider_chain_exhausted` (model-chain exhaustion, emitted once inside the `exhausted_model_chain_error` factory in `g3ku/providers/fallback.py`, covering both chain loops in `fallback.py` and `main/runtime/chat_backend.py`); `task_node_error` (from `TaskLogService.append_task_error_log`, the single chokepoint for all five task-node error writers); `task_terminal_failed` (from the terminal publish path, only when the final status is `failed`; success terminals stay out of the audit feed); `web_api_5xx` (an HTTP middleware in `g3ku/web/main.py` that captures ≥500 responses plus unhandled exceptions on `/api/` paths, with a `/api/audit` skip prefix so audit-endpoint failures never feed back into the pool); `memory_batch_parked` (from `MemoryManager._park_failed_batch`, carrying the failed_id, category and last error text). Memory events are read-only here — retry/discard keeps living in the memory view's 失败记忆 panel. All emitters swallow their own exceptions; a broken sink never disturbs the host flow.
- `GET /api/audit/events` takes `limit` (1–200, default 50), `offset`, `level`, `subsystem`, `since` and returns `{ok, items, total, has_more}` newest-first; unknown filter values simply match nothing. Read failures answer `503` with `detail.code` `audit_events_read_failed` (Chinese message in `api_client.js`).

### Maintenance Boundary

- Badge stuck or zero while events exist: check the frontend path first — the sessionStorage marker under `g3ku.audit.last-seen.v1` and the 30s badge poll (`refreshAuditBadge`), not the sink.
- The stream is empty or stuck on a blank page: compare `GET /api/audit/events?offset=<n>&limit=100` against the rendered page. The frontend clamps an out-of-range page back to the last page, so an empty list means the endpoint answered `total: 0` or the ledger was never written.
- The log list cannot be scrolled by wheel while the panel still shows a clipped page: the scrolling owner is `.audit-event-list`, not the panel (`.resource-detail-panel` is `overflow: hidden`, so programmatic scrolling still works and hides the mistake) — check that the panel keeps `flex: 1 1 auto; min-height: 0` and the list keeps `overflow-y: auto`.
- Displayed times look shifted: the row renders system-local time derived from the stored offset-aware ISO timestamp; compare the raw `timestamp` values from `GET /api/audit/events` before suspecting the sink.
- No `audit.jsonl` at all: the process never went through `configure_audit_sink` (bootstrap wiring in `make_agent_loop`) or the workspace root differs; restart the web process and check `.g3ku/`.
- A failure class exists in the system but has no audit events: no emitter covers it yet — add one `emit_audit_event(...)` call at the failure's chokepoint (the recipe above); the source tag renders from the record's `subsystem` string with no fixed registry change needed unless it deserves a Chinese label (add it to `auditSubsystemLabel`).
- `/api/audit/*` returns 503: the sink read path cannot resolve a workspace root (`audit_sink_unconfigured`) or the file read failed.

## Model Config Page And Admin Contract

The top-level `模型配置` page manages `llm-config` provider records and model bindings. Config source-of-truth, binding resolution, and secret handling are owned by `config-and-models.md`「llm_config 子系统」; this section covers the admin surface and the add/edit model workflow.

### Model-Role Route Specificity

- The browser's session brain-chain reorder action and the model-configuration page both persist role chains through the role-specific endpoint `PUT /api/models/roles/{scope}` (for example, `scope=ceo`).
- In `main/api/admin_rest.py`, register that route before the generic `PUT /api/models/{model_key:path}` binding-update route. Starlette matches routes in declaration order; if the generic path comes first, `roles/ceo` is treated as a model key and the binding facade returns `Unknown model key: roles/ceo` instead of updating the CEO chain.
- When debugging a failed chain save, inspect the browser request URL first, then confirm the route declaration order before changing model-key validation or frontend drag payloads.
- **The model page is rendered and fed by `org_graph_llm.js`, not by `org_graph_app.js`.** That module overwrites the globals owning this page at load: `renderModelCatalog`, `renderModelRoleEditors`, `renderModelList`, `renderModelDetail`, `openModel`, `startCreateModel`, `loadModels` and `handleModelRoleEditorAction` (the 保存 button). Its data comes from `GET /api/llm/bindings` and `PUT /api/llm/routes`, not from `GET /api/models` / `PUT /api/models/roles/{scope}`. Two traps follow. An app-side renderer added for this page is never invoked — it must be called from llm's `renderAll`, and its payload must flow through llm's save, otherwise the UI renders nothing while every JS test still passes. And `routes` on that endpoint is the flattened candidate view, so chain order and group membership come only from `route_entries` + `load_balance_groups`: llm converts them once in `llmRouteChains`, keeps the group map in its own state, and `projectRoutes` projects both into `S.modelCatalog` (edit-session drafts survive a refresh). Reading a chain from `routes` would silently turn one group slot into its individual members and write that back on the next save.
- `GET /api/models` carries two views of each role chain: `roles` is the flattened candidate view (load-balance group members expanded), `route_entries` is the ordered fallback chain, and `load_balance_groups` holds the group definitions (`model_keys` plus `max_retry_rounds`). The model page is three columns: load-balance groups | model list | role chains. **The four role chains stay one row of four — never wrapped**, so the page opts out of the 1440px V2 content cap (`max-width: min(100%, 1760px)`) instead of letting the new column squeeze the chain cards. Groups are configured in that left column as first-class objects — 新建组 opens a dialog (组名, member checkboxes, free-entry 每成员重试次数 defaulting to the `1..3` cap) and a group row is dragged into a role chain the same way a model row is, which places one `group:<key>` slot in the chain. Both the column card and the chain card open that dialog when clicked anywhere on the card, so the group tile carries no drag handle: live model tiles have none either, and adding a 40px handle collapses the card's main area to zero width. A group is a single chain slot whose members are peers (the tile states that order inside a group carries no priority and that a node stays bound to one member for its lifetime), while a direct-only chain keeps the existing drag/remove UI unchanged. Member counts and per-member round budgets are deliberately not printed on either card.
- Group editing belongs to the same chain-edit session as the role chains: confirming the dialog enters that session, and one 保存 submits both. Renaming through the dialog rewrites the `group:<key>` tokens in every draft chain in the same pass, so a rename can never leave a chain pointing at a dead key; deleting a group removes its chain slots too. A dialog left unconfirmed touches nothing, and 取消丢弃 edits rolls the group drafts back with the chain drafts.
- A chain that contains a group is saved with `route_entries` plus the group definitions in the same request and never with `model_keys`: the backend treats the two as mutually exclusive (`route_entries wins`) and validates both together, so a group cannot be persisted while its referencing chain fails. The submit payload carries the **whole** group set (minus groups with no members, which the backend would reject and no chain can point at), not only the referenced ones — `models.loadBalanceGroups` is replaced per scope on save, so a subset payload would delete a group that was just created and not yet dragged into a chain, or one referenced only by a scope outside this request. When no chain uses a group at all, the set rides on the first group-capable scope (`execution`, else `inspection`).
- Group validation errors are surfaced verbatim: duplicate members inside a group, duplicate chain entries, `max_retry_rounds` outside `1..3`, a group key colliding with a binding key, and a chain referencing an unknown or disabled group all return a readable `400`. Deleting a binding that is the only member of a group is refused with the group and chains named, because silently emptying a group would remove load balancing from every chain that references it.
- `GET /api/models/load-balance/status` answers the worker's runtime view of the balancer (per-member running/waiting/reserved, rolling 60-second request count, decayed 429 penalty, score, node binding count, config revision). The only failure the balancer remembers across requests is upstream rate limiting: auth errors and disabled keys are reported nowhere here, because the model chain handles them in the request that hit them. It counts buckets, never bucket identity: endpoint/API-key material is only ever hashed inside the worker, and a non-zero `unresolved_bucket_count` means that process cannot resolve the key material at all, so the quota distribution is unknown rather than duplicate-free.
### Frontend Responsibilities

- The add/edit model modal keeps one provider-config JSON draft as its source of truth. Dedicated `请求地址` (`base_url`) and `Apikey` inputs stay two-way synced with that JSON draft. There is no manual binding-key (`模型ID`) field in create mode: the binding key is derived by the backend from the draft's `default_model`, so picking the model is what establishes its identity. Create mode opens with a required `配置名称` input (placeholder `请输入配置名称`) in place of the modal title; the name must not duplicate an existing config name (case-insensitive) and is saved into the binding's `name` field (see `config-and-models.md`「模型系统不是只靠 config.json」for the display-title priority).
- The protocol select is a header control in both create and detail modes and lists the provider templates, defaulting to `OpenAI Chat`. Its `协议` label is an invisible spacer, the same mechanism the `是否为图像多模态` field uses, so both boxes share one line and one control band without duplicated copy; the modal pins that band to the input height instead of the global select height. ### Backend Responsibilities

- `POST /api/llm/drafts/validate` and `POST /api/llm/drafts/probe` check an unsaved provider draft; `POST /api/llm/drafts/probe-max-concurrency` derives per-key concurrency limits; `POST /api/llm/drafts/models` fetches the provider model catalog (`GET {base_url}/models`) using the draft's credentials and rotates across multiple API keys on authentication failure.
- 测试连接 is not a reachability check: the draft probe reads the model catalog and then sends one inference request shaped like the live sender (streaming, protocol envelope fields, one placeholder function tool run through the same normalizer the provider uses). Catalog success alone does not pass, and a rejected envelope returns the upstream error text in the probe message, so a config whose protocol fields the provider refuses cannot be saved through the modal. Request-shape rules are owned by `config-and-models.md`「llm_config 子系统」.
- `POST /api/llm/bindings` creates a binding and derives a unique `key` from the record's `default_model`, appending a numeric suffix when a same-name model already exists, so different providers can share a model name. The binding payload accepts the display `name`; non-empty names are deduplicated case-insensitively across the catalog (excluding the binding being edited), and the created/updated item exposes `name` on both `/api/models` and `/api/llm/bindings`. `POST /api/llm/bindings/{model_key}/rename` remains a back-compat endpoint that renames a binding key, rewrites matching references in `models.roles.*` and `agents.multi_agent.orchestrator_model_key`, and rejects an empty or duplicate key.
- Display surfaces follow the binding `name`: the task `Token统计` window resolves every model identifier through the catalog to `name` (falling back to the identifier itself when the catalog has no match), and that resolution covers the per-config heading, the 模型 column of 模型调用明细, the breakdown's sort order, and the call-table search — one resolver (`taskModelDisplayName` → `ceoModelUsageHeadlineTitle`), never a per-surface rule. The ledger stores only the binding `key` (`ModelTokenUsageRecord.model_key`, written from `LLMModelAttempt.model_key`), so labels follow the current config name and a deleted config's history reverts to its key; the key stays reachable through the breakdown subtitle and the 模型 cell tooltip so a rename never costs the way back to the config. Opening the window re-requests the catalog when it is still empty, because a failed boot-time load would otherwise degrade the whole panel to raw keys.
- Draft endpoints validate the draft first and report field-level errors without issuing provider requests when validation fails. Draft validation normalizes endpoint-style `base_url` values (trailing `/chat/completions`, `/responses`, `/models`) to the provider API root instead of rejecting them.

### Maintenance Boundary

- If `获取模型列表` fails but `测试连接` succeeds, compare the draft `base_url`/`api_key` sync state in `g3ku/web/frontend/org_graph_llm.js` with `POST /api/llm/drafts/models` before debugging the provider.
- If catalog fetch returns a non-JSON or empty-catalog error, treat it as a provider endpoint-shape problem (same triage as a failed model-catalog connection probe), not as a frontend bug.

## Frontend Theme And Layout Contract

The browser shell renders one visual system per theme. Theme and layout are frontend-only concerns: they never change API, WebSocket, permission or state-machine contracts, and the backend stays the authority for session, task and runtime state.

### Layering And Rollback

- `g3ku/web/frontend/org_graph.css` keeps the legacy system; `g3ku/web/frontend/org_graph_redesign.css` is the active layer and loads after it in `org_graph.html`.
- Every rule in the active layer is rooted at `[data-ui-version="v2"]` on `<html>`, combined with `[data-theme="dark"]` / `[data-theme="light"]` for theme-scoped values. Dropping the `<link>` and the `data-ui-version` attribute returns the page to the legacy appearance.
- The active layer re-anchors the legacy custom properties (`--bg-app`, `--bg-panel`, `--text-primary`, `--brand-primary`, `--status-*`, `--radius-*`, `--shadow-*`, `--space-*`) onto its own `--ui-*` tokens, so retheming means editing `--ui-*` values rather than chasing component rules. Legacy rules that hardcode a color, radius or shadow instead of consuming those variables still need an active-layer rule of at least equal selector depth.
- Anchoring is the cheaper fix and is what the pre-layer screens use: the boot/unlock card, its banner, its legacy-data panel and preview, and `.interaction-flow` consume only `--bg-panel` / `--bg-surface-inner` / `--bg-app` / `--border-color` / `--shadow-*` / `--status-failed-*`, so one declaration serves both themes and no active-layer rule is needed. A legacy surface that hardcodes a dark background instead renders in light mode as a dark card floating on the light canvas carrying light-theme ink — unreadable text, and undetectable until someone opens that surface in the other theme, which is why every theme check covers the boot screen and not just the unlocked views.
- A tinted block that holds prose keeps `--text-primary` for its text and lets the accent border carry the meaning. The ~3:1 accent-on-own-tint floor sized for chips and status badges becomes unreadable under a full sentence of 16px body text.
- In the legacy file light is the `:root` default and dark is an override set, so both themes carry explicit token blocks. A change checked in one theme is incomplete until the other is checked.
- The light block changes surfaces (canvas / surface / elevated / input / subtle, borders, text tiers, shadows) **and the accent tiers**. Each accent carries its own light value, darkened on its own hue until it clears 4.5:1 as text on white: `--ui-brand #1e8478`, `--ui-success #288556`, `--ui-warning #9a6d17`, `--ui-danger #e91c1c`, `--ui-info #196ef7`, `--ui-inspecting #8058f8`. `--ui-on-brand` is white there because the brand fill is now dark enough to need it; dark keeps the bright accents and `--ui-on-brand #04211d`. An accent therefore does not read byte-identically across themes — light mode optimizes for legibility on white.
- Accent tints carry no alpha in either theme. The `--ui-*-soft` / `--ui-*-soft-strong` fills are opaque hex values, one pair per theme: dark uses the composite of the old translucent tint over `--ui-bg-surface` (so the dark theme looks unchanged), light uses 30% / 42% of its own darkened accent mixed with white — an alpha tint would composite against white and wash the chip out, which is what "light mode must not get lighter" forbids. Chip text on its own tint lands at about 3:1 and that is the deliberate floor: a tint is made of the text color, so 4.5:1 between the two is unreachable, and depth stops there instead of buying contrast by bleaching the fill back out. Accent borders on chips and switches are the plain accent (`border-color: var(--ui-brand)`, chip borders `currentColor`). The status stroke family is the exception: `.status-badge` borders and `.execution-tree-node` status borders are the same accent at 50% alpha (`color-mix(in srgb, … 50%, transparent)`), because 1px is the thinnest border this engine paints — `border-width: 0.5px` computes back to `1px` at DPR 1 — so a stroke that reads too heavy can only be lightened through opacity, not geometry. That 50% is that family's weight, not a global stroke default: a tinted box whose fill already states what it is takes a lighter edge, and the user bubble sits at 30% of `--ui-brand` because `--ui-brand-soft` alone says "mine" while a 50% ring makes the bubble the loudest object in a feed whose model text carries no frame at all. Neutral overlays keep their alpha in dark (`--ui-neutral-soft`, scrollbar thumb, focus rings, shadows) because they must composite over varying backgrounds and carry no hue; light's `--ui-neutral-soft` is the solid `#e6e6e6`, because `rgba(188,188,188,.12)` over white computes to `#f7f7f7` — an invisible status badge and a no-op hover. `--ui-scrim` stays alpha in both themes: it is a floating overlay and has to show what is underneath.
- Surface tokens are achromatic in both themes: every background tier, border, `--ui-neutral-soft` and `--ui-scrim` has equal R/G/B channels (dark `#121212 / #191919 / #212121 / #272727 / #151515`, light `#f6f6f6 / #ffffff / #ececec / #e6e6e6`, borders `#d3d3d3 / #b6b6b6`). Hue belongs to the accent tiers only, so a new surface token must not carry a green or blue cast.

### Theme Persistence

- Default theme is dark; a first visit without a stored preference renders dark.
- `#theme-toggle` flips `data-theme` on `<html>`, stores the choice under `g3ku.ui.theme.v1`, and updates the sun/moon icon plus the button `aria-label` / `title` so they name the theme the next click produces. Only `dark` and `light` are valid; any other stored value falls back to dark.
- Switching theme does not reload the page, request data, or rebuild the current view.
- Every `localStorage` read/write is guarded: blocked or unavailable storage degrades to dark theme plus the default navigation state instead of breaking startup.

Its contract points:

- The two risk paragraphs must be readable end to end without scrolling. ### CEO Reading Column

- `.ceo-shell` is a two-column grid whose first column is `var(--ui-ceo-session-width)`: 92px collapsed, 288px expanded. A hardcoded `288px` column or `auto` both break the session-panel toggle and are not valid.

The composer is the exception on both counts: `.chat-input-area` is `width: min(50vw, 100%)` and centers by `margin-inline: auto`, and it floats over the feed instead of reserving a row of it. The width is anchored to the viewport, not to the chat column, because the column itself narrows when the session panel expands — a percentage-of-column composer visibly shrinks every time the operator opens the session list. Inline padding is zero so the box reads as exactly that width.
- The floating toolbar paints nothing behind itself: `.chat-input-area` is transparent, with no band and no top divider, so the transcript keeps running underneath. Its controls are one size (40px tall, `--ui-radius-control`) but no longer sit beside the textarea: the context-usage brain and attach buttons overlay the textarea's bottom-left corner and send/pause overlays its bottom-right, so `.chat-input-area` is a single-column grid and `.ceo-input-row` is the controls' positioning context. Their insets are 28px inline (8px gutter plus half a 40px control — both sides carry the same value or the band reads as skewed) and 8px from the bottom. The textarea's bottom padding (52px = 40px control + 8px inset + 4px gap) is what keeps typed text out from under them, and its `min-height` (120px) is the resting height the drag floor reuses. `#ceo-send-btn` therefore lives inside `.ceo-input-row` in the DOM, not as a second toolbar column; the legacy layer keeps it as a third grid column of the same row so dropping the active layer still renders the old side-by-side toolbar. A new composer control joins at 40px inside that bottom band rather than introducing another radius. Below 768px the toolbar returns to full width with the page's inline gutter.
- Because the toolbar is one column, the textarea's center line, the top resize band and the 回到最新 button (absolutely positioned over the toolbar) are the same axis; anything that reintroduces a second toolbar column puts those three back out of alignment.
- Out-of-flow means the feed's bottom clearance is not automatic: `watchCeoComposerInset` measures `.chat-input-area` and writes `--ceo-composer-inset` onto `.chat-wrapper`, and `.chat-feed` spends it as bottom padding (the CSS fallback 96px only covers the resting toolbar). A constant there is the bug shape to avoid — the toolbar grows with typing, with a drag, and with the queue / upload / edit lanes stacked above it, and each of those would otherwise park the newest message permanently under the floating box.
- The textarea's top edge doubles as its resize grip: `#ceo-input-resize-handle` is an 8px band whose `#39c5bb` pill sits centered on it. The band is grid-placed into the textarea's own cell, which makes that cell its containing block, so the grab area matches the textarea exactly at every width instead of relying on a hand-computed inset. Move and release are listened for on `window`, not on the band: an 8px target loses the pointer as soon as the drag starts. A drag writes an explicit height that outranks content autosizing (`syncCeoInputHeight` returns early once one exists, longer text then scrolls inside the box), lifted `max-height` included, and the drag range is bounded by the textarea's CSS `min-height` (its 120px resting height) at the bottom and 60% of `.chat-wrapper` at the top so the feed can never be squeezed out.

Giving the container its own fill and border draws a second, squarer box behind the chip's rounded corners.
- The expanded session-panel header keeps one center line: `.ceo-session-tabs` is 40px like the 多选 button beside it, but the tabs inside must not carry their own height. The capsule's 1px border plus 4px padding leaves a 30px content box, and the legacy 36px tab starts at that box's top edge and spills 6px below it, which drops 本地/渠道 3px under 多选 and off the center of the `::before` highlight pill. `height: auto` lets the grid row stretch, so the tab box and the highlight pill are always the same box.

Finalizing a turn clears `assistant-text-loading` and its `role="status"` label for the same reason.

The exemption is a more-specific selector with `!important` inside a reduced-motion block, and the keyframe runs 0→360deg `linear infinite`, so the wrap is seamless. The lucide `loader-circle` glyph is a gapped arc, not a closed ring, so it visibly rotates — unlike a truly symmetric circle.
- No status glyph wears a ring. `.interaction-step-icon` — shared by the stage-trace tool steps and the in-bubble loading placeholder — is a bare 26×26 box with no `background`, `border` or `radius`; state rides on `color` plus the always-present title text. The 26×26 box stays so the icon column's baseline does not move. The placeholder's arc is 16px against the track's 14px, and that override must repeat `interaction-step-icon` in its selector to beat the same-specificity `.interaction-step-icon svg` rule. The compression divider's `::before` paints only `border-top-color` and leaves the other three sides transparent, so it is one rotating arc rather than a ring on a track: the paused state drops the pseudo-element entirely (`.is-bars-only` → `content: none`), which makes that arc the only visual difference between 压缩中 and 已暂停, and a static full-circle track would erase it.
- Below 768px an expanded session panel leaves the grid flow: `.ceo-shell` drops to a single column so the chat keeps the full width, and the panel overlays it at `min(288px, calc(100vw - 24px))`. Keeping two columns there lets grid auto-placement drop the chat wrapper into the 92px track.

### Status Color Semantics

`data-status` keeps one meaning across every page, and the label text is always present so color is never the only signal:

- `running` / `in_progress` → `--ui-info` blue; `inspecting` → `--ui-inspecting` purple. Execution and acceptance are both "in progress" but read as two lifecycle tiers, so a running node, its task-detail pill and its task-hall card carry the same blue, while an acceptance node stays distinguishable at a glance. Brand teal is not a lifecycle color at any tier — it stays reserved for selection and primary actions.
- `completed` / `passed` / `success` → success green; `failed` → danger red; `unpassed` → warning amber.
- `paused` / `queued` / `pending` / `waiting` / `blocked` / `unknown`, plus read-only and disabled → neutral gray.
- An unmapped `data-status` renders neutral gray with its original text; it never inherits brand or danger styling and never renders unstyled.
- Every `.status-badge` box uses `--ui-radius-control`, the same radius as buttons, so a badge sitting in a button row reads as one family; the badge's own height comes from the surface it is on (24px tags in tree nodes, cards and drawers; the task-detail pill lifts to the 40px header control tier). Lifecycle color rules own `background` / `color` only; the base badge box owns the border (`1px` of 50% `currentColor`, i.e. 50% of that rule's own text color), so a surface rule may resize a badge without repainting it and a new lifecycle tier contributes a fill plus a text color and nothing else. The neutral tier is the one exception: it re-asserts the hueless `--ui-border`, because 50% of its gray text ink would paint a heavier ring than the badge needs.
- Node cards take the solid tint tier — `--ui-*-soft` fill with a 50%-alpha `--ui-*` border and the normal text color — instead of the legacy `color-mix(soft 24%, panel)`, which diluted the tier a second time and read as no fill at all on a white page. Running and inspecting share the brand teal container (teal is the "in progress" surface) while their badges split blue and purple; the running card's breathing `::after` ring stays at the legacy 88% because it is the in-flight attention cue, not a container edge. Two traps: `.execution-tree-item` is the `<li>` wrapping a whole subtree and only carries the connector color, so painting it turns a branch into one large block and destroys the card edges; and the badge inside a card keeps a surface fill, because card and badge would otherwise share one token and only the border would separate them. `.selected` re-asserts the brand border after the status rules, otherwise selecting a colored card leaves only the shadow as the cue. The user turn bubble is a member of the same tier (`--ui-brand-soft` fill, 50%-alpha brand border): the chat column and the execution tree are read side by side, and a full-opacity brand border on the bubble paints it a tier brighter than the running nodes it sits next to.

Task hall status badges are labeled in Chinese from `taskStatusLabel` (`运行 / 成功 / 失败 / 暂停 / 未通过 / 未知`); the task detail pill uses its own Chinese mapping. Both must stay Chinese so the two surfaces agree.

### Page Surfaces Are Flat

Admin pages draw one level of boxes only. The page-level containers (`.resource-list-panel`, `.resource-detail-panel`, `.memory-column`, `.audit-feed-panel`) are transparent and borderless, so repeated content — task cards, Skill/Tool cards, model rows, memory records, token rows — is the only framed layer. Drawers and dialogs keep surface fill, border and `--ui-shadow-dialog` because they float above the page rather than nesting inside it. A new admin surface must not wrap content in a second bordered panel.

Each view's own `<h1>` page title is visually hidden (clipped to 1px, kept in the accessibility tree) because the top bar already marks the current section; the header row keeps only its toolbar and status content. Do not delete the `<h1>` — it is the page's accessible name. Hiding the text is not sufficient: the wrapper that held it (`.task-header-main`, the model page's `.resource-header-title`) also leaves the flex flow, otherwise it still contributes width and the first header control starts one gap to the right of the page padding.

Header controls share one left edge at the page padding, and one 12px gap between siblings. A header whose only left-edge item is 刷新 pins that button there absolutely; a header whose left button belongs to a group instead keeps the button in flow and left-aligns the whole group — the model page reads 刷新 → 添加配置 → 编辑模型链 as one left-aligned row. New header controls join the group that matches their page and never re-introduce a per-page offset.

No header button is filled. `.toolbar-btn.success` — 编辑模型链, 保存并连接, 签发桥接 token, and the dialog primaries 确定 / 保存 / 确认修改 / 添加 / 启用模型 — renders exactly like a plain toolbar button (surface fill, `--ui-border`, `--ui-text`, hover `--ui-neutral-soft`); the legacy class painted it with a `--ui-brand` fill, a `color-mix(..., transparent)` border and a same-color glow, which after the light-theme accents were darkened read as a blue-green block. `#model-roles-save-btn` carries its own legacy id rule with the same colors, so both selectors need the reset. The only filled chip left in the chrome is the active navigation item.

The 任务排序 / 全局任务树深度 buttons label their name in `--ui-text`, the same ink as the 多选 button beside them — a gray label next to a black one reads as a disabled control even though both are clickable.

There are two control tiers and no third: **large** = 40px tall, **small** = 32px (`toolbar-btn small`, e.g.「回到最新树」and the 外部 page actions). Both carry `--ui-radius-control` (currently 16px), 13px text, `--ui-bg-surface` fill, 1px `--ui-border`, no shadow. Because the tier radius is 16px, anything 32px tall or shorter in the same family renders as a pill — the 24px `.status-badge` and `.memory-op-chip` boxes are pills by design at this radius, not a regression to "fix". The large tier covers page-header controls (`.toolbar-btn`, `.resource-search`, `.resource-select-trigger`, 排序/树深度 main button), the CEO composer row, the session panel's first row, and the task-detail row — 返回 icon button, 状态 pill, 初始提示词, 活跃节点, 错误日志, Token统计 — where the icon-only button is a 40px square so it never reads as a smaller control than its labelled neighbours. A new control joins one of these two tiers rather than introducing a third height, a legacy radius, or a larger font. Radius tiers are `--ui-radius-control` 16px / `--ui-radius-card` 12px / `--ui-radius-panel` 14px, so controls are currently the roundest family in the UI; raising the control tier further, or wanting cards to read as calmer than buttons, means editing those three values in one place rather than component rules. Chat bubbles (`.message .msg-content`) sit at `--ui-radius-control` as well, with all four corners equal and no tail corner, so a bubble and the composer controls stacked in the same column read as one family; the card radius stays the card family's value and is not a bubble fallback.

Three families deliberately stay outside the tier, so a sweep for "all controls at 40/16/13" must stop at them: **card-shaped controls** (`.resource-list-item`, `.execution-tree-node`, `.memory-card`) keep `--ui-radius-card` / the node's own 18px corners and size to content; **toggle switches** (`.tool-governance-switch`) keep a 999px track because the radius is the switch's shape, not its box; **content disclosure rows** (`.task-trace-summary`, the node drawer's 完整上下文) are headings that open, and their type scale belongs to the transcript, not to the toolbar. Legacy `org_graph.css` still hardcodes 42px/14px on `.compact-resource-header-actions` children and 46px/16px on `.resource-select-trigger`; those are dead values under the active layer — the tests that assert them guard the legacy file, not the rendered page, so measure in the browser before "fixing" them.

The task hall header is one row: 多选 → 任务排序 → 全局任务树深度 hug the left edge, and the status capsules after them are pushed to the right edge at every width. The pressure state and the CPU/memory/disk reading share one capsule, and each of the three resource numbers colors itself by its own occupancy tier (≥75% warning, ≥90% danger) so the reading is not pinned to one color.「任务排序」and「全局任务树深度」are single borderless buttons carrying only their name and a chevron — the chosen option is not echoed on the button — and their dropdown appears below the button on click. At ≥1200px the three buttons and the capsules share one row; below that the capsules take a full-width row of their own and stay flush right.

A dropdown that opens inside a clipped or scrolling surface is lifted out of it: a `resource-select` carrying `data-resource-select-portal="true"` moves its option panel to `document.body` while open, positions it `fixed` against the trigger's viewport rect (flipping above when the space below is shorter than the panel), and returns it to its shell on close — 模型配置 弹窗的 深度思考 下拉就是这么一个控件。Keeping the panel inside the shell instead adds to the scroll container's overflow and makes the browser scroll the focused option into view, so opening it shifts the whole form. The same escape-by-reparenting shape owns the `配置说明` popover. `enhanceResourceSelects()` drops any portaled panel whose owner shell is gone, which is what a modal rebuild leaves behind.

### Responsive Bands

The task hall grid is content-sized — `repeat(auto-fill, minmax(300px, 1fr))` — so its column count follows the available width, and a long token count wraps inside a fixed-size card rather than the card shrinking to fit one line. ## CEO Composer Runtime

The Leader/CEO composer has two distinct runtime behaviors that maintainers need to keep straight.

### 1. Active-Turn Button Semantics

- If the current session is idle and the composer is empty, the primary button stays in a disabled `send` state.
- If a user-visible turn is currently running and the composer is empty, the primary button switches to `pause`.
- If the composer contains text or attachments, the primary button switches back to `send` even when a user turn or heartbeat turn is still running.
- Channel sessions split on `can_message`, not on the read-only flag: a registered `ext:` session behaves like a local one (composer, attach and send all live, and a running turn still offers `pause`), while `china:*` archives and registry-less ext rows keep the button disabled with the read-only label. Even there, a running turn must switch the button to `pause`: the writability constraint is what blocks sending (`client.user_message` → `channel_session_readonly`) and it must never block pausing. The pause request is the same `client.pause_turn` lane as local sessions, and `client.resume_interrupt` (工具审批续跑) is likewise open on channel sessions.
- History actions never follow `can_message`: 编辑重发 / Fork stay hidden on every channel session (the snapshot gate returns no flags for channel keys and the REST endpoints re-validate).

This is intentional. The composer button means "pause only when the user has not prepared a follow-up payload", not "pause whenever a turn is active".

### 2. Queued Follow-Ups

- The composer-side queue lane above the input box is two lists merged on render: the runtime's accepted queue (read from `ceo.state.queued_follow_up_messages`, which carries `content` / `attachments` / `metadata._transcript_turn_id`) painted first, then the browser's not-yet-sent drafts. A chip has three states, and only the third one owns affordances: a server-queued item shows 已受理 plus 撤回重新编辑; an item already forwarded but not yet reflected by a state frame shows 已受理 alone (the runtime holds it — there is nothing to re-arm and nothing to withdraw, and it leaves the lane when `consumeRepresentedRuntimeSentCeoFollowUps` sees it represented by a turn); a local draft shows 立即发送 (only while a turn is running), 撤回 and 丢弃. 撤回 (corner-down-left arrow) drops the item from the lane and hands its text and attachments back to the composer through the draft lane, never auto-sending. For a server-queued chip that affordance calls `POST /api/ceo/sessions/{id}/queued-follow-ups/withdraw` `{turn_id}` first — the browser's own copy is not the truth there — and only refills on success; a 丢弃 (x) affordance exists solely for items the runtime has never seen. The endpoint answers `409 follow_up_not_queued` for a turn the runtime already consumed, because deleting that row would erase an answered user message, and it emits a `state_snapshot` afterwards so other tabs painting the same session converge.
- Browser storage (`sessionStorage`) is only ever the authority for drafts that have not been handed to the runtime. The runtime-held half must survive a refresh, a different tab, and a process restart, so a re-opened session shows it from the state snapshot rather than losing it with the local cache. The bound this sets: an item still held by the browser is lost if that tab closes before the running turn ends.
- Sending while a turn is active does not interrupt the current turn and no longer reaches the backend at all: the item stays in the browser lane and starts its own fresh user turn, in arrival order, once the running turn closes (`maybeDispatchQueuedCeoFollowUps` on the final frame and on any state frame that finds the session idle). A chip therefore shows 立即发送 only while a turn is running; that affordance forwards just that one item on the ordinary `client.user_message` lane, which is what merges it into the running turn's next safe boundary. A message arriving while a manual context compression is in flight takes the same merge path (inbound-hold and dispatch contract: `runtime-overview.md`「压缩窗口：入站闸门与基线写入仲裁」).
- The backend-owned follow-up queue is authoritative once that send succeeds, and chips already handed off to the runtime must never be re-sent when the turn later closes — the browser's own idle dispatcher only forwards items with no `runtime_sent_at` marker, which is what keeps the server-side dispatcher and the client-side one from duplicating a message.
- CEO/frontdoor consumes queued follow-ups at the safe boundary right before the next `call_model` send of the same visible turn. The runtime appends them as independent `user` messages to the current request body instead of concatenating them into one synthetic supplement string.
- If the current visible turn finishes before another `call_model` round happens, the backend immediately starts the next fresh user turn from the queued follow-ups after the current turn closes.
- Each queued item still remains its own user message in transcript persistence; batching only changes which next LLM request sees that group first.
- A single visible turn can hold multiple distinct user messages once follow-ups are consumed. The browser treats two user messages as equivalent only when their turn id (when present on both), content, and attachments all match; matching on turn id alone drops a distinct follow-up and leaves the user's supplement invisible.
- Once a queued follow-up has been handed off to the backend, it should still remain in the composer-side queue lane until runtime snapshot/final-reply data can prove that the follow-up has been consumed into a visible turn.
- Browser rendering must not create a provisional transcript bubble merely because a follow-up was accepted by the backend queue. Queue acceptance and visible conversation placement are intentionally different stages.
- `ceo.reply.final` may include `user_messages` for the just-finished visible turn. This is the authoritative current-turn user batch and exists specifically so the frontend can decide whether runtime-sent follow-ups belonged to that same reply or to a later chained turn.
- If `ceo.reply.final.user_messages` includes a runtime-sent follow-up, the browser must rebuild the final visible order as `current turn user batch -> final assistant reply` and clear the matched queue entry.
- If a runtime-sent follow-up does not appear in the just-finished turn's `user_messages`, the browser should keep it in the queue lane until a later fresh user turn or transcript snapshot represents it authoritatively.
- `snapshot.ceo.messages` must also avoid replaying running-turn `pending` user transcript rows as ordinary history bubbles. During a live running turn, authoritative current-turn user placement comes from `inflight_turn.user_messages`, not from flat transcript replay.
- When a running follow-up is actually consumed into the next model send of the same visible conversation lane, the runtime also archives the pre-follow-up assistant execution bubble into visible UI history before the consumed user bubble is restored. That archive is UI-visible but prompt-hidden, so refresh/reconnect can preserve the same visual ordering without polluting later prompt history.
- The archive turn id carries a `:followup:` segment. When the browser renders an archived turn with that segment, it marks the last stage in that archive as the interrupted stage (interruption marker in the stage title), because a follow-up consumed mid-flight splits that stage between the archive (rounds already done) and the continuation turn (remaining rounds).
- A consumed follow-up's user bubble is inserted immediately before the current live turn element, not appended to the end of the feed, so it reads in chronological order between the archive and the continuation.
- The same ordering rule governs the snapshot restore lane: `inflight_turn` / `preserved_turn` carry the *current batch*, which is not the same thing as "just sent". `restoreCeoInflightTurn` therefore lands each user bubble at its own `timestamp` — rendered bubbles expose it as `dataset.ceoTimestamp`, written by `addMsg` — and appends only when no parseable timestamp exists (the live typing path). Batching a stale message into the current turn would otherwise surface it below the newest reply and read as the user re-asking an old question; the authoritative queue-side fix is `runtime-overview.md`「压缩窗口：入站闸门与基线写入仲裁」, this is the display-layer bound.

### Model Retry Visibility UI Contract

- `ConfigChatBackend` publishes live-only `model_retry_status` before each real retry (per-model backoff round or same-model key-switch resend) and clears the field when retrying exits. A cross-model fallback is normal chain operation: it is counted but emits no status. The status carries `state=retrying`, `retry_count` equal to provider requests actually sent so far (hence the ordinal of the retry about to happen), the model retry round, the model refs, an `error_message` capped at 4096 chars to keep websocket payloads bounded, the backoff delay (0 for key-switch emissions), and local-offset `last_retry_at` / `next_retry_at` timestamps. The task-node frame sanitizer (`_sanitize_model_retry_status`) is a field whitelist — the timestamps must be listed there or they are stripped — and its error-text bound equals the emit-side limit because the browser expands the toast to the full received text. The CEO snapshot deep-copies the whole status and needs no whitelist entry.
- For CEO sessions, running `inflight_turn.model_retry_status` reaches the browser through the `snapshot.ceo` / `ceo.turn.patch` lanes. The browser shows a warning toast above the conversation feed while `state=retrying`, shaped `模型自动重试中 · 第 N 次重试 · 最新 HH:MM:SS · 下次 HH:MM:SS · <error>` (clocks render only when present); the toast disappears when a snapshot clears the field or the session leaves the running state. Long error text is visually clamped to two lines with an expand affordance (click or Enter/Space toggles the full text).
- For task nodes, the runtime frame exposes the same field through `task.live.patch`. Node detail reads the selected frame and shows the same toast below its header. Live patches update the toast while the detail drawer is open, and opening the drawer during a retry restores it from the current frame.
- The status is transient observability state, not transcript history. It is not appended to persisted CEO messages, does not backfill historical node output, and is cleared on success, terminal failure, pause, discard, or config-refresh-based turn rebuild. A failed websocket delivery is covered by the next low-frequency snapshot/patch or by reopening the session/node while the runtime is still retrying.
- If the chat is stuck but no retry toast appears, check that the actual failing boundary is the retryable `ConfigChatBackend` path rather than an outer idle/preflight/tool wait, then inspect the `on_model_retry_status` callback, `inflight_turn.model_retry_status`, and the node runtime frame field in that order.

### 2.2. Regulatory Approval Flow

- Web CEO has a second blocking composer lane besides ordinary running turns: a pending `frontdoor_tool_approval_batch`.
- The websocket/runtime path emits that batch through `ceo.turn.interrupt`, and reconnect/session-restore should also be able to rebuild it from `GET /api/ceo/sessions/{session_id}/pending-interrupts` or the paused snapshot lane.
- The frontend review UX is intentionally split:
  - the operator reviews one risky tool call at a time in a toast-like approval card,
  - but the browser must not resume the agent per item.
- The authoritative resume payload is one batch submission:
  - `client.resume_interrupt`
  - `resume.type="submit_batch_review"`
  - `resume.batch_id`
  - `resume.decisions=[{tool_call_id, decision, note?}, ...]`
- The browser may let the operator move backward, change earlier choices, and keep a session-local draft, but it must submit a complete decision for every `review_item` in the batch before the backend resumes.
- Rejection notes are optional operator text, but they only belong to rejected items. The frontend should not send a `note` field for approved items.
- Clicking the parameter preview opens a separate full-args modal. Long argument bodies must stay scrollable, and clicking outside that modal should close it.
- While a regulatory approval batch is pending, the composer should behave as blocked-active state rather than as ordinary paused state:
  - no new user message send,
  - no queued follow-up dispatch,
- session/page switching is allowed while the batch is pending, but the pending review must remain session-local draft state and reappear when the operator returns to that CEO session.
- Frontend pause rendering must not rely only on `source="approval"`. Approval pauses may arrive with ordinary `source="user"` plus approval interrupts in the inflight/paused snapshot lane; in that case the browser should keep the current visible turn in the approval-waiting state instead of finalizing a new `已暂停` history bubble.
- Once the operator submits the batch, the browser should clear the local draft for that batch and wait for the normal runtime events (`ceo.state`, `ceo.reply.final`, etc.) to continue the conversation.

### 2.3. Streamed Reply Delta Contract

- `/ws/ceo` remains the single duplex transport for Web CEO. Browser sends, pause/resume control, tool events, and assistant reply delivery still share the same websocket connection; streamed assistant text is not a separate SSE channel.
- User-visible assistant text may arrive on a dedicated live-only event `ceo.reply.delta`.
- The payload is intentionally small:
  - `turn_id`
  - `source`
  - `text`
  - `seq`
- `text` is the authoritative assistant text of the stream's latest thinking segment: the previous segment stays visible until the next model-call boundary resets it, so the live block shows only the latest segment rather than a whole-turn accumulation; it is neither a raw provider token nor a stage-trace snapshot.
- The browser should treat `ceo.reply.delta` as a cheap text-only lane:
  - render the latest-segment text as a transient live block inside the turn's stage rail (`.task-trace-live-text`), not into the final assistant bubble; the bubble only receives the authoritative final text at `ceo.reply.final`
  - update cached `inflight_turn.assistant_text` for reconnect/session restore
  - never treat the delta as durable transcript history and never rerender the stage trace from it
- Streamed text renders through a plain-text path while the turn runs; `ceo.reply.final` remains the authoritative closeout, where full markdown render, transcript finalization, canonical-context finalization, and visible-turn completion happen.
- The CEO turn body renders as the turn's stage timeline, not as a single overwritten bubble; see "CEO Turn Timeline Rendering Contract" for the layout and field rules.
- The projected `canonical_context` on assistant transcript entries carries the retained raw stage window and per-round narration across reloads; older completed stages remain compact summaries.
- `ceo.turn.patch` is not the high-frequency assistant-text streaming lane; it is the lower-frequency lane for inflight/preserved snapshot refreshes, state transitions, reconnect bootstrap, tool/interrupt-related snapshot changes, and stage-state progression: the frontdoor graph emits `frontdoor_stage_synced` after each graph-node boundary sync of the session-stage/canonical state, and the websocket relay answers with a live turn patch, so a newly submitted stage and its first tool rounds reach the browser without waiting for the next tool event.
- That lane is rate-limited per connection by `_CEO_TURN_PATCH_MIN_INTERVAL_S`: building one patch walks the session's whole accumulated stage workset (measured 100-270 ms of event-loop CPU on a long channel session), so a tool-event burst would otherwise spend the turn rebuilding frames and the feed would only catch up at the end. Inside the window at most one trailing patch is scheduled, and it is rebuilt from **current** runtime state at flush time rather than from the triggering event, so a dropped intermediate frame loses nothing (its delta is always relative to the last persisted assistant row) and a turn that already ended flushes as cleared state. Turn-terminating frames (`ceo.reply.final`, `ceo.internal.ack`, `ceo.error`) force the pending patch out first, which keeps patch-before-final ordering for fast turns instead of losing their rail, and keeps a stale `running`/`paused` patch from landing after the closeout and being re-opened as a ghost turn row.

### 2.4. Runtime Error Contract

- `/ws/ceo` may also emit `ceo.error` when a visible turn fails before `ceo.reply.final`.
- The frontend should treat `ceo.error.data.message` as the authoritative operator-facing text for that failure boundary, not as optional debug metadata.
- Backend error delivery has an explicit empty-message fallback. If the raw exception string is empty (for example a bare `MemoryError`), websocket delivery must reuse the session snapshot `last_error.message` when available, and otherwise emit a non-empty fallback message instead of leaving the browser to show `unknown error`.
- This matters especially for memory-pressure failures during request-artifact persistence: the operator-visible contract is “a readable runtime failure message plus a terminal error state”, not “blank message that the browser turns into `unknown error`”.

### 2.5. Image Upload Gating

- Whether uploads become provider-visible image content is gated per turn by the selected model binding's `image_multimodal_enabled` flag: off keeps uploads on the text downgrade path; on lets only the current visible turn's live request carry provider-visible image input, while durable transcript/baseline lanes strip the image blocks back out.
- A stable reopen lane, `attachment_reopen_targets`, rebuilt from current-turn uploads and earlier transcript metadata, lets uploaded files/images be reopened after the user text is rewritten into a direct-visual note. Detached task creation does not auto-fill from this lane; `create_async_task.file_targets.path` must already be the exact absolute path of an existing file.
- Upload protection is two-layered: `/api/ceo/uploads` rejects a single image larger than `5 MiB`, and the runtime rechecks size before expanding an upload into a provider request, so bypassing the endpoint does not bypass the limit.
- Historical reopen via `content_open` is a separate lane that injects a single-send runtime overlay plus the provider-visible image block; the overlay does not survive a later overflow, compression, or error, and a non-multimodal binding fails rather than degrading to a text preview.

### 2.6. Attachment Bubble Rendering Contract

- Browser-side CEO message rendering must treat uploaded attachments as structured UI, not as plain transcript text.
- When a user message contains both text and attachments, the frontend should render:
  - the user text as the normal user text bubble
  - the attachments as separate attachment bubbles stacked directly below that text bubble in the same message lane
- When a user message contains attachments but no user-visible text, the frontend must render only the attachment bubbles. It must not synthesize a summary bubble such as `已附加附件`, and it must not surface the backend/internal `Uploaded attachments: ... local path ...` note as chat content after refresh or reconnect.
- The backend snapshot contract behind that rule is:
  - transcript/runtime messages may still carry the internal upload note in `content` for model/debugging purposes
  - `snapshot.ceo.messages[].content` must prefer `metadata.web_ceo_raw_text` whenever `metadata.web_ceo_uploads` is present, even when that raw text is the empty string
  - the authoritative user-facing attachment lane comes from `attachments`, not from reparsing the internal note text
  - that same persisted metadata lane is the source of truth for rebuilding `attachment_reopen_targets` in later frontdoor turns; if reopen paths break while attachment bubbles still restore, debug transcript metadata preservation first
- Non-image attachments should render as clickable file bubbles rather than inline text. Clicking them should open a new browser tab against the backend-owned read-only file route `GET /api/ceo/uploads/file`, not against a raw local filesystem path.
- Image attachments should render as thumbnail bubbles, not as ordinary file pills. The same thumbnail should also be the click target that opens the underlying file in a new tab.
- `kind == 'audio'` is a third shape and never a pill: the user message itself becomes a voice bar (play/pause control, duration, and a `T` button at the right end whose `aria-label` is 转文字). Duration comes from the browser's `loadedmetadata`; `T` reveals the marker-stripped transcript **below the bar**, never inside it, and the `用户语音，机器识别结果：` line is stripped from the visible text on every user row — the marker exists for the model, and a bubble that prints it reads as the machine talking. The disclosure is wired through `.message-stack` because the button lives in the bar and the panel lives under it. The clip's own storage/visibility contract (decoded WAV on the wire, compressed to MP3 at the store seam with a WAV fallback, excluded from every model-visible surface, removed together with the session) is owned by `speech-to-text.md`「语音气泡与音频字段的存放」.
- Channel-session clips reach the same renderer through `metadata.external_attachments` (the bridge posts them over `/api/v1`); `_normalize_snapshot_attachments` lifts audio entries only — lifting every channel file would silently reshape how existing channel sessions display — and points them at `GET /api/ceo/external-upload-file?session_id=&path=`, a read route whose containment is that session's own `.g3ku/external-uploads/<slug>` directory (400 outside it, 400 on an empty `session_id`, 404 when the file is gone). It exists because `uploads/file` is rooted at the web upload directory and cannot serve a channel path.
- If refresh/reconnect shows the internal upload note instead of attachment bubbles, debug the snapshot builder in `g3ku/runtime/api/websocket_ceo.py` before debugging CSS or DOM layout.

### 2.7. Inline Markdown Image Rendering And Media Middle Layer

- The chat markdown renderer (`renderInlineMarkdown` in `g3ku/web/frontend/org_graph_app.js`) renders `![desc](src)` as an inline image for both persisted history and live turns: `https`/`http` URLs render directly, local filesystem paths resolve to the read-only route `GET /api/ceo/uploads/file`, and `data:` URIs or unknown schemes render nothing. This inline path complements, rather than replaces, the structured attachment bubbles in section 2.6.
- That file route serves from two allowed roots only — the per-session upload directory and `workspace_path()/output` — returning `400 upload_path_outside_session_dir` for paths outside either root and `404` for missing files.
- Most assistant local references are rewritten at the snapshot egress by the media middle layer (`g3ku/runtime/api/ceo_media.py`) so they become servable without touching the on-disk transcript: raster images become staged thumbnails inside an already-allowed root, other local files become signed viewer URLs, and URLs, already-servable references, and failed rewrites pass through unchanged.
- Originals are reachable only through the signed viewer route `GET /api/ceo/media/original?token=...`, which takes an unguessable signed token rather than a caller-chosen path. Because only raster image bytes are ever staged into a serving root, the endpoint cannot become an arbitrary file oracle.

### 2.8. Message Edit-Resend And Session Fork Contract

User message bubbles carry a hover action row (`编辑` / `Fork`, `.msg-actions` inside `.message-stack`) backed by two backend contracts. Server-side core lives in `g3ku/runtime/web_ceo_history_edit.py`; endpoints hang off the existing `ceo_sessions` router.

- **Eligibility flags are server-owned, and the two actions have different axes.** `snapshot.ceo.messages[]` (user items) carries `can_fork` and, on top of it, `can_edit_fork`; assistant items may carry `task_dispatched`. Both share the content gate; only edit adds a runtime gate, because edit rewrites the source transcript while fork is a read-only prefix copy:
  - content gate (both flags): the session is a local `web:` session (channel sessions never get flags); strict async-task gate — no verified `create_async_task` dispatch (`metadata.task_ids` on assistant transcript rows is authoritative) at or before the message, and a task created in the clicked message's own reply turn also closes the gate (gates walk the raw transcript, internal rows included; an assistant row with task ids retroactively closes every still-open user row of its group; legacy transcripts without any `task_ids` field fall back to comparing `list_tasks_for_session` `created_at` against the run's first assistant reply timestamp); the message is the first of its user-run (a maximal consecutive run of visible user messages — prompt-batch siblings and mid-turn consumed follow-ups share one execution turn and have no clean boundary, so only the run head is actionable; truncating the run head removes the whole run); a per-turn boundary snapshot exists for the previous transcript message's turn (`.g3ku/web-ceo-turn-boundaries/<session>/<turn_id>.json.gz`, gzip, most recent 3 turns kept), or the boundary is the session start. There is no heuristic rebuild: messages older than the retained window are permanently ineligible.
  - runtime gate (edit only): the session is fully stable — no inflight/preserved turn (including heartbeat/cron internal turns), no queued follow-ups, no pending approval interrupts, no blocking tool execution, not paused, not running.
  - The frontend mirrors each axis on its own side: the feed-level `.ceo-turn-active` class hides the edit button only (the row keeps `Fork`), edit clicks carry a toast guard, and fork clicks are guarded only by the upload/pause/catalog busy flags.
- **Flag delivery has two frames, both from the same gate call.** `snapshot.ceo` carries per-row flags at connect; `ceo.edit_fork.gates {turn_ids, fork_turn_ids}` re-delivers both gate sets on every CEO websocket `state_snapshot`, including the ones reporting `paused` — a blocked session has no usable composer, so the action row is the only exit left. The second frame exists because the just-sent message only becomes eligible at finalize: the strict task gate needs this run's assistant row in the transcript, and the edit gate needs the inflight sidecar gone — `_emit_state_snapshot` re-syncs that sidecar right before emitting, which is why the frame hangs off `state_snapshot` and not `message_end` (at `message_end` the sidecar still carries the running turn). Each list holds the run-head keys of its own gated rows, so the browser flags the first cached user row per turn id (prompt-batch siblings share one id), revokes every other row, then re-renders through `renderCeoSnapshot`; the render signature covers both flags, so an unchanged set costs no rebuild. Gated transcript rows without a turn id are skipped — the turn id is the button key. Channel sessions never receive the frame.
- **A gates frame can only flag a row the browser already has in its cached transcript.** Rows a turn leaves behind normally arrive inside `ceo.reply.final` (`finalizeCeoTurn` writes them into the snapshot cache). A manual pause ends without a final frame — the server archives the run into the transcript and clears the inflight sidecar, while the browser only marks its live turn element `paused` — so `finalizePausedCeoTurn` lands that run's user row (turn id taken from the lane; `normalizeCeoSnapshotInflight` keeps content/timestamp only) plus its `已暂停` assistant row through the same `buildFinalizedCeoTurnPayload` the final path uses. A pause caused by a pending approval interrupt is not a finished turn and must not write transcript rows: the lane stays alive and resumes into the same turn.
- **Edit-resend** = `POST /api/ceo/sessions/{id}/truncate` `{turn_id}` then the ordinary WS send. The endpoint truncates transcript from the run head (atomic JSONL rewrite, `last_user_turn_at`/`commit_turn_counter`/preview recomputed), replaces the continuity sidecar with the prev-turn boundary snapshot (`continuity_source=turn_boundary`) or an empty baseline at session start (`fresh_path`), clears inflight/paused sidecars, deletes removed turns' actual-request artifacts (mandatory for `fresh_path`: an empty-baseline sidecar cannot stop the restart artifact fallback from resurrecting deleted turns), and mutates the live `RuntimeAgentSession` in place (`apply_history_truncation_state`) so stale WS closures cannot reuse the old baseline. The frontend then closes the WS, clears local follow-up chips and the session snapshot cache, reconnects, waits for open (`whenCeoWsOpen`), and sends the edited text/uploads through the existing `client.user_message` lane — the single send pipeline owns streaming/finalize. The composer shows a warning banner while in edit mode (`S.ceoEditResend`); cancel restores the previous draft. Truncation is irreversible by design: there is no backup or undo.
- **Fork** = `POST /api/ceo/sessions/{id}/fork` `{turn_id, title?}`. Read-only on the source session (safe while a source turn runs; the boundary snapshot is read into memory before copying). The new session gets: the transcript prefix (deep-copied rows), attachment files copied into the new session's upload dir with descriptor/`attachments`/content-note and baseline path rewrites (shared paths would fail the per-session `uploads/file` root check), the truncated continuity sidecar, and a copy of the prev-turn boundary snapshot (so the fork's tail stays editable). Task records never migrate. The response is create-shaped catalog payload plus `fork.composer {text, uploads}`; the frontend activates the new session and prefills the composer through the draft lane without auto-sending.
- **Validation and concurrency**: both endpoints re-run the content gate server-side (`turn_not_found` 404; `turn_not_run_first` / `boundary_unavailable` / `edit_fork_blocked_by_async_task` / `channel_session_readonly` 409; `no_model_configured` 503). The runtime check is edit-only: truncate calls `_assert_edit_fork_runtime_idle` (`ceo_turn_in_progress` 409) before and inside the session `_turn_lock` (5s acquire timeout, closing the heartbeat race), while `fork_ceo_session` never inspects runtime state and takes no lock — that asymmetry is the contract, not a missed check.
- **Known edges**: bubbles appended by the live send path carry no flag of their own — the action row arrives with the gates frame, and that frame reaches only rows already in the cached transcript, so a still-running turn's own user message (lane-only until finalize) shows buttons at finalize; a turn dispatched after the boundary is outside the gate by spec — truncation removes its transcript row while the task keeps running and its terminal callback still targets the session (banner text warns); the first post-edit request pays a one-time prompt-cache miss; the memory review window (`memory/review_state.json`) has no per-turn pruning, so buffered review records of removed turns may still flush to the advisory memory lane later (conversation context is unaffected); `user_edit_truncation` is a whitelisted continuity shrink/source reason (forensics in `context-and-cache-troubleshooting.md`).

### 2.9. CEO Websocket Lane Failure Contract

`/ws/ceo` 的失败面只有一个方向会致命：车道静默而 socket 还开着。此时浏览器既收不到后续帧，也不会触发 `onclose` 的 1 秒自动重连，界面就永久停在半截回合（转圈、没有最终文案），只有手动刷新才同步——转录里通常早已落好完整 assistant 行，所以这属展示层车道故障，不是数据缺失。

- 三条 `sender()` 队列与连接期内联发送共用一条 socket，因此**任意时刻只允许一个写者**：所有出口写都走 `_safe_send`，它在连接期一把 `asyncio.Lock` 下串行。`websockets` legacy 协议明确不支持并发 `send()`——并发会在那条链路上抛 `AssertionError`（`_drain_helper`），帧被吞掉而 socket 仍开着，正是下面描述的静默形状（`console.log` 里按 `CEO websocket failed to send frame` 逐帧计数可证）。新增第二条写路径必须复用同一把锁。
- 单帧写失败（载荷不可序列化、半开连接）只丢那一帧并记 `logger.exception`；连续 `_SENDER_CONSECUTIVE_FAILURE_LIMIT`（3）帧都失败才判定链路已废：置 `closed`、以 code 1011 主动关掉 socket，让前端走 `onclose` 重连重取快照。sender 静默退出等于把一次可恢复故障变成永久静默。
- 转发层 `relay_session_event` 是 `_relay_session_event` 的守卫包装：`RuntimeAgentSession._emit` 逐个 `await` 订阅者且不做捕获，转发层抛出异常会打断正在收尾的回合（`message_end` 之后还有 `state_snapshot`/`turn_end`），前端因此连权威收尾帧都等不到。守卫只记日志不上抛，`CancelledError` 继续传播。
- 浏览器只接受 JSON 帧：`onmessage` 的 `JSON.parse` 必须带 try/catch。裸解析下，一帧解析失败会让该 socket 之后每帧都被同一个异常吞掉。失败即 `closeCeoWs()` + `initCeoWs()` 重连重取快照，并按 `CEO_WS_PARSE_RESYNC_LIMIT` 限量（收到 `snapshot.ceo` 即恢复预算），避免解析不了时打成重连风暴。

### 3. Context Loader Notices

- Successful CEO/frontdoor `load_tool_context` and `load_skill_context` calls do not render as ordinary `Interaction Flow` steps under the assistant bubble.
- Frontend loader-notice detection must treat both legacy and v2 loader names as the same UI family:
  - `load_tool_context` / `load_tool_context_v2` => tool notice
  - `load_skill_context` / `load_skill_context_v2` => skill notice
- Instead, the browser shows a short-lived composer notice above the input row, using the loaded `tool_id` or `skill_id` when the runtime payload exposes it.
- These notices are intentionally stackable rather than single-slot: multiple successful loader calls may coexist in one right-aligned floating column that lines up with the send-button edge.
- The type-specific styling comes from a leading icon rather than a leading green dot:
  - tool notices use the same `wrench` icon family as the sidebar Tool page
  - skill notices use the same `sparkles` icon family as the sidebar Skill page
- The risk-colored dot remains present on the trailing edge so operators can still distinguish low / medium / high loader risk at a glance.
- Risk color comes from the resource catalog in browser state (`S.skills` / `S.tools`), not from the tool result. Catalog population is on demand: the node detail path awaits `ensureContextRiskCatalog()` (which fills both lists from `/api/resources/skills` + `/api/resources/tools` and de-duplicates concurrent calls) only when the rendered trace actually contains context-load steps. An empty catalog degrades every risk color to the medium fallback rather than failing the render.
- Tool risk lookup resolves the concrete executor against the owning surfaced family: `actions[].executor_names` decides the level for ids like `filesystem_write`, while a family-level load (`load_tool_context("filesystem")`) takes the highest action level in that family. `tool_id` equality alone never matches, because the catalog is family-keyed.
- The task node detail page renders the same loader family as round chips rather than hiding it: the chip title is `加载 skill` / `加载 tool` with a leading risk-colored kind icon (`sparkles` / `wrench`, same palette as the notice dot), and the loaded resource id is exposed only as the chip tooltip. Expanding a loader chip shows a single `内容` field holding the loaded body (`content` from the loader result payload), with no arguments field and no tool name.
- Loader steps that did not succeed keep the ordinary tool-step rendering (name, arguments, raw output), so gate errors and failed loads stay diagnosable instead of collapsing into an empty `内容`.
- The intended motion contract is still "launch from the composer, settle into the notice stack, then fade out"; the full lifecycle is currently about 5 seconds per notice.
- That notice is intentionally live-only UI state. It should fade away after a short timeout and must not be appended into the persisted CEO session `messages` list.

### Manual Pause Resume Rule

- Manual pause means “freeze the current round as previous-round context,” the operator-visible “pause” button is a terminal stop for the current visible turn, the runtime state ends as `completed` tagged `stop_reason=user_pause`, and ordinary user sessions are never left in a long-lived resumable `paused` state. The next outbound user message after pause must start a new round.
- The paused round's user message, execution trace, stage state, tool calls, and compression state are preserved in transcript and snapshot context so the next round can inherit them without rewriting the original user text.
- Manual pause writes the completed-session continuity sidecar immediately, clears that session's ordinary paused/inflight restorable snapshots, and archives the paused assistant bubble into a persisted message with `status=paused` during the stop flow itself, not only when the next user turn is about to dispatch.
- That archived paused assistant is durable UI history for `snapshot.ceo` restore/reconnect, but it remains hidden from prompt-history assembly and session-summary counts via `history_visible=false`.
- Browser-side restore should therefore render that persisted paused assistant as a paused bubble rather than a completed reply. The next ordinary user turn inherits context from visible history plus completed continuity state, not from resuming the old paused turn.

### CEO Stage Trace Round Rendering Contract

- The browser CEO stage view should treat `canonical_context.stages[].rounds[].tools` as the authoritative round-level tool list.
- A `ceo.agent.tool` frame for `submit_next_stage` carries the new stage's full header in its result text. The frontend parses it and upserts that stage into the live rail immediately (`extractCeoSubmittedStageContext` → `mergeCeoLiveTraceContext` → `renderCeoStageTraceIntoTurn`), so the turn leaves tool-card form at the moment the stage is committed instead of waiting for the next `canonical_context` delta. The tool card is not rendered for that frame. When the authoritative delta later arrives, the same stage id is replaced in place, so the provisional header never duplicates.
- The early switch is best-effort: a non-`submit_next_stage` tool, a truncated (non-parseable) payload, or a header without a stage goal all fall back to the normal tool card.
- Refreshing the page or reopening a completed session should reproduce the same round grouping that live inflight snapshots used; the frontend should not try to regroup same-name tools on its own.
- `tool_names` and `tool_call_ids` may still be present for compatibility, but they are summary metadata rather than a second grouping algorithm.
- The stage progress badge in both the CEO session view and the shared task-trace components must reflect budget-counted rounds rather than raw round history length.
- The shared stage body renderer (CEO turn timeline and task node detail flow alike) displays, inside each expanded stage in order: the stage preamble (CEO stages), each round's `rounds[].text` (the model's mid-round narration) above that round's tool chips, and the stage's `completed_stage_summary` as a trailing 阶段总结 block; a round without text renders tool chips only. The task node detail payload carries these fields at both detail levels: `execution_trace` (full) and `execution_trace_summary` (summary) both keep `stages[].completed_stage_summary` and `stages[].rounds[].text`.
- Frontend progress rendering should use `tool_rounds_used` as the primary source, and only infer a fallback count from `rounds[].budget_counted=true` when an older payload lacks an explicit count.
- Do not derive displayed progress from plain `rounds.length`: successful `load_tool_context` / `load_skill_context` rounds may remain in history for auditability while being hidden from visible execution chips, and treating raw round count as budget usage will overstate progress.

### CEO Turn Timeline Rendering Contract

- The CEO session view renders each visible turn as a timeline: the user message right-aligned, then the turn's own stage rail (stage titles collapsed by default with budget/progress meta, expandable to rounds; a round with no mid-turn text renders tool cards only), then the final assistant output; the legacy wrapper element remains only as the rail container.
- A stage that spans turns is therefore painted once per turn that referenced it, and transcript rows are append-only: a row keeps the status it was written with, so a stage that later finished would otherwise stay 进行中 in every earlier row. `reconcileCeoFeedStageStatuses()` closes that gap in the DOM only — it walks the feed, takes each stage's newest copy, and raises the earlier non-terminal copies to that terminal status (class token plus label text). It never walks a settled copy backwards, so an earlier `error` is not flattened by a later `success`, and it never touches card order, rounds, expansion state or output hydration. Identity comes from the `data-stage-id` attribute the rail renderer emits, never from `data-trace-key`, whose value legitimately degrades to `stage_index` or ordinal position and collides across turns. It runs at the end of `renderCeoSnapshot`, after `patchCeoInflightTurn`, and after `discardPendingCeoTurns` on both finalize branches — before those two it would rewrite the `.running` marker that `hasRunningCeoToolStep` reads to decide whether a turn may be discarded.
- Live inflight turns resolve stage data from the per-turn `canonical_context_delta` first, then the turn's own rendered trace summary, and never from the session-cumulative `canonical_context`: `_frontdoor_stage_state` accumulates across turns, so a full-context fallback leaks the previous turn's stages into a new live turn. A patch whose `turn_id` differs from the reused turn clears that turn's rendered trace summary and live stream text before resolving context.
- Each live patch merges its delta into the turn's already-rendered trace summary (stages and rounds merge by identity, stage headers take the delta) instead of replacing the timeline, so completed stages stay visible while later phases render. A patch carrying no delta is a no-op for the trace: the browser keeps rendered stages and live tool steps instead of resetting to the "waiting" placeholder, preserving mid-turn stage submissions between graph-node stage refreshes.
- Deltas are produced server-side by `ui_canonical_context_delta(...)` through the canonical projection contract owned by `runtime-overview.md` "CEO Frontdoor Canonical Context Contract": projection keeps historical stages stable, so a new turn does not re-expand compact stages into the newest bubble.
- Persisted assistant transcript rows store their rail in one of two durable forms — a full checkpoint row (`canonical_context_projection: stage_window`) or a `cc_upsert` delta row (per `runtime-overview.md` "CEO Frontdoor Canonical Context Contract") — but `snapshot.ceo.messages[]` carries only the message-local `canonical_context_delta` — never a cumulative `canonical_context`. The delta key is always present on rail rows, and `{}` is the explicit "this turn added no rail" signal: the browser renders a plain text bubble and must not resurrect older stages. A per-row cumulative context inflates the first frame quadratically — on tens-of-MB channel transcripts most payload bytes reach the client only to be discarded. Inflight/preserved turn payloads carry the same message-local `canonical_context_delta` and never the cumulative `canonical_context` either: the UI projection (`project_canonical_context_for_ui_payload(...)`, raw-window round bodies reattached from the live snapshot) belongs to `ceo.reply.final`, the one frame whose rail is written into durable history. Attaching it to live frames costs a full projection per event and ships a workset the browser's live lane discards (measured 462 KB per frame against a 3.4 KB delta on a long channel session).
- Snapshot assembly replays transcript rows in order and rolls the delta baseline forward instead of re-projecting every row: `stage_window` rows pass through as their own view, `cc_upsert` rows advance a dedicated storage cursor (hidden runtime rows included, since upserts are encoded against the previous physical rail row), legacy rows are projected once, and `ui_canonical_context_delta_from_views(...)` consumes the views (byte-identical to the raw-input path). Re-projecting the whole transcript per row is a quadratic-build regression.
- The browser's snapshot-cache normalization must preserve `{}`-delta key presence (not just truthy deltas): a cached row that loses the delta key falls back to any cumulative `canonical_context` at re-render and resurrects older rails, diverging from the authoritative WS first render.
- First-screen rendering is windowed: `renderCeoSnapshot` builds only the last 80 messages; older pages render from the in-memory snapshot array (`S.ceoFeedWindowSource`) when the operator scrolls near the top (scroll-height compensation keeps the reading position) or when a view-state anchor sits outside the window (bounded expansion). The WS frame itself is still delivered in full — JSON parse of a few MB is cheap, DOM construction is not. Message `data-ceo-key` occurrence counters are computed globally (`buildCeoMessageKeyList`), so windowed/paginated rows carry exactly the keys a full render would; incremental-finalize and anchor restore depend on that. Pinned by `tests/resources/org_graph_app.ceo_feed_window.test.js`.
- `rounds[].text` carries the model's mid-turn narration for that tool round; a stage's `preamble_text` carries the narration from the response that created the stage (rendered above the stage title). Both are display-only fields of the stage state; prompt assembly, transcript durability, and archive semantics do not depend on them. Round narration is bare rail text — no border, fill or own padding (`.task-trace-round-text`), so it lines up with the round's timestamp and the stage card stays the only box on screen. Giving it a bubble re-nests a container inside the stage card and puts a second frame around text the rail already owns.
- `ceo.reply.final` remains the authoritative closeout (final markdown plus final delta/trace when present); the payload shape is defined by the backend contract below.
- The frontend must not reconstruct CEO stage flow from flat `tool_events`; `canonical_context_delta` is computed server-side from message order, so refresh/reconnect rebuild the same per-bubble trace slices without a browser-local cursor.
- Tool output rendering follows canonical payload fields: inline `output_text` renders directly; an externalized or transcript-capped body renders preview and the artifact-open path. The frontend must not invent extra truncation or backfill old tool-event text.

The backend contract behind that UI behavior is:

- CEO/frontdoor runtime writes precise round tool entries into `frontdoor_stage_state.stages[].rounds[].tools` when a tool cycle finishes.
- Session snapshot assembly trusts stored `round.tools` first and only backfills legacy rounds by exact `tool_call_id`.
- A `tool_name`-only fallback is considered a regression because it can make a later same-name tool appear inside an earlier stage round after refresh or transcript reload.
- The browser still treats `round.tools` as authoritative input, but it filters successful `load_tool_context` / `load_skill_context` entries out of the visible stage-trace tool chips because those calls represent context acquisition rather than user-facing execution work.
- `ceo.reply.final` canonical-context shape: the shared assembler `final_reply_canonical_merge` (`g3ku/runtime/web_ceo_sessions.py`), used by the userspace relay and the heartbeat publisher alike, includes the UI-projected `canonical_context` only when the completed turn added stage progress over the previous assistant message, omitting both `canonical_context` and `canonical_context_delta` otherwise (the delta uses the same `ui_canonical_context_delta(...)` view, so a closeout never re-emits historical stages). Browsers prefer that payload over any older inflight or persisted trace; a message whose delta renders empty stages shows a plain text bubble with no stage rail, and neither `finalizeCeoTurn` nor `renderPersistedCeoAssistantTurn` may fall back to `turn.lastExecutionTraceSummary` or the session-cumulative `canonical_context` — backfilling an older trace under a new direct-reply bubble is a contract bug.

### CEO Feed View State And Scroll Preservation Contract

- `renderCeoSnapshot` is a full feed rebuild (message replay plus inflight/preserved turn restore) used for session loads, session switches, and as the authoritative fallback whenever the rendered DOM can no longer be trusted. Rebuilds are avoided when unnecessary: an incoming `snapshot.ceo` whose render signature (full messages projection plus live turn key fields) equals the current render is skipped outright, so reconnect re-pushes do not churn the feed; and `ceo.reply.final` closeouts carrying `user_messages` update incrementally — missing user bubbles are appended before the running turn and the turn finalizes in place — whenever the rendered DOM exactly matches the recorded message-key model (each child carries its `data-ceo-key` in order, the final child is the active turn). Any mismatch (promoted follow-ups, hand-sent bubbles, preserved-turn coexistence) falls back to the full rebuild, which stays the authoritative self-healing path.
- The live/preserved turn part of the signature covers the turn's stage-track skeleton, not only `source`/`turn_id`/`status`/`assistant_text`/`usage`: stage identity, stage status, and each round tool's name/status/output length. A live turn grows its rail through `canonical_context_delta` while `assistant_text` and `usage` stand still (the model is executing tools between provider calls), so a skeleton-less signature lets a session switch-back's cache-first render occupy the signature and silently skip the authoritative snapshot that carries the stages and tool rounds created while the operator was away — the fix looks like "refresh the page and they appear". Signature additions stay pixel-relevant and bounded: never put tool output bodies or time-ticking values in it. Pinned by `tests/resources/org_graph_app.ceo_message_actions.test.js`.
- Both full feed rebuilds and live turn re-renders must preserve the operator's reading position and expansion choices. Live updates (`ceo.turn.patch`, `ceo.reply.final`) re-render the turn's whole stage track through a wipe-and-rebuild (`renderCeoStageTraceIntoTurn`), so a turn-scoped capture/restore contract applies to every such re-render, not only to snapshot rebuilds.
- Feed follow behaviour is one intent bit (`S.ceoFeedFollowLatest`), never instantaneous geometry. Live mutations pin to bottom only while follow is on; a user gesture (wheel/pointer/key/touch followed by a scroll) that leaves the bottom disengages follow permanently — while disengaged no mutation, compression divider, or image-load re-pin may move the feed scrollbar, and `#ceo-scroll-to-latest-btn` stays visible until the operator returns to the bottom or clicks it. Sending a message or opening/switching a session re-arms follow. Geometry-only checks re-armed follow mid-drag (64px threshold re-triggers on every mutation), which read as "scrolling up gets yanked back repeatedly". Pinned by `tests/resources/org_graph_app.ceo_live_view_state.test.js`.
- The button's breathing is a second signal with a second gate, so visibility and pulsing never share one condition. Breathing answers "the runtime is still producing output you are not looking at", which requires follow to be disengaged **and** a turn to be running: the same `S.ceoTurnActive` bit behind `.ceo-turn-active` on the feed, covering heartbeat/cron internal rounds as well as user rounds. `updateCeoScrollToLatestButton()` (visibility writes) and `syncCeoFeedTurnActiveClass()` (turn-state writes) are the only two writers and both re-derive `.is-breathing` from that bit, so a turn closing while the operator reads history stops the pulse on the spot and leaves the button up; scrolling back to the bottom clears both at once. The glow itself is a `::after` halo that is out of flow and whose only animated property is `opacity` — the halo's reach, the button's own shadow, and its 42px box stay constant across the cycle. Interpolating `box-shadow` spread on the button (or leaving `backdrop-filter` on it) makes the painted outline swell and collapse every 1.8s, and the peak reaches past the small clearance above the composer onto neighbouring message text, which reads as the effect "filling up the surroundings" rather than breathing. `prefers-reduced-motion` removes the pulse and keeps the resting glow.
- Tool-output boxes are scroll containers of their own (`.interaction-step-detail` and the stage rail's `.task-trace-code`, both capped with `overflow: auto`), so the reading position lives one level below the feed's own `scrollTop` and needs its own preservation. In-place output sync (`setCeoToolStepOutput` and the lazy output hydration) writes text only when it differs and re-applies the previous `scrollTop` when it does, because replacing a scroll container's children collapses its content height and zeroes the offset — otherwise every tool event and every one-second duration tick throws away the position an operator is reading from. `hidden` writes are skipped when the state already matches for the same reason. Turn-scoped capture/restore additionally carries each nested box's `scrollTop` keyed by owning-stage trace key plus its class discriminator and in-step order. Pinned by `tests/resources/org_graph_app.ceo_tool_output_scroll.test.js`.
- Before a live stage-track re-render wipes the turn DOM, the browser captures turn-scoped state: Interaction Flow open/closed, per-stage `<details>` open keyed by `data-trace-key`, and the round tool strip selection keyed by owning-stage trace key + `data-round-key` (in-turn host-order fallback when the round key is empty, stage-scoped because `round_index` repeats across stages). Restore runs right after the rebuild and before the `[open]` step hydration pass, so re-opened stages re-fetch output blocks and a restored tool selection re-activates its panel through `setTraceRoundActiveTool`. Capture is gated on `turn.lastExecutionTraceSummary`: a turn-id change clears that field, so a new turn never inherits the previous turn's expansion state (stage ids repeat across turns). A turn's first track render uses the defaults — flow open, stages collapsed.
- Turn closeout respects the operator's Flow container choice when a stage track exists — `finalizeCeoTurn` does not force the container open; a track-less tool-event turn keeps its default-open closeout. Pause/approval holds still force the container open so a pending approval stays visible.
- Before a full rebuild, the browser captures a transient per-session view state from the live DOM: the anchor element (`data-ceo-key`, with a bottom-relative positional fallback) plus its in-element scroll offset; per-turn Interaction Flow open state and `展开全部` history expansion; per-stage `<details>` open state (scoped per turn because `stage_index` fallback trace keys collide across turns); and the active round tool chip (scoped by per-turn DOM order because an empty round key would collide across rounds).
- After the rebuild, the browser restores that state onto the new DOM and re-syncs the scroll position to the anchor element's new geometry (element-anchored, not pixel-preserving), re-pinning once more after a double rAF so late media/lazy output blocks settle; restored-open steps re-run output hydration because assigning `open` directly skips the toggle listener, and restored round tool selection re-activates its panel through `setTraceRoundActiveTool`. Operators following the bottom keep bottom-follow behavior; a missing anchor falls back to pixel clamp.
- Every feed mutation runs under a preserve-mode scroll snapshot (`captureCeoFeedScrollSnapshot` / `restoreCeoFeedScrollSnapshot` in `mutateCeoFeed` / `withCeoFeedBatch`): an at-bottom operator (`ceoFeedNearBottom`) follows new content to the bottom (stick-to-bottom), and a scrolled-up operator gets the position restored against the anchor element's post-mutation geometry, falling back to pixel clamp when the anchor is missing. The live follow pins synchronously without the async re-pin of `scrollCeoFeedToBottom`, so a pending frame cannot yank the operator back after they scroll up mid-stream.
- Stable identity is mandatory for rebuilt feed nodes: messages get `data-ceo-key="m:{turn_id}:{role}:{occurrence}"`, turns get `data-ceo-key="turn:{turn_id}"`, and the recorded message-key model (`S.ceoFeedRenderedMessageKeys`) plus the render signature are updated by every render path (full rebuild, incremental finalize, and the skipped-snapshot fast path alike). New render paths that add feed nodes without these keys, change stage `traceKey` composition, or fail to maintain the recorded model silently weaken scroll anchoring, rebuild-stable expand state, and the incremental-finalize gate.
- Capture is per-session and is skipped whenever the feed still shows a different session than the render target (`S.ceoFeedRenderSessionId`), so session switches and new-session loads never clone the previous session's view state.

### Per-Turn Token Usage Contract

- Each assistant turn renders a small per-response token line under the final bubble (`输入/缓存命中/输出 · 完成于 HH:MM:SS`), built from a normalized usage object `{input_tokens, output_tokens, cache_hit_tokens, call_count}` that maps directly onto normalized provider usage (`g3ku/providers/base.py`): `input_tokens` is the uncached lane, `cache_hit_tokens` the cache-read lane, `output_tokens` the generated output; normalized provider usage additionally carries an optional `thinking_tokens` key, written only when the provider reports `reasoning_tokens`, so a missing key means "not reported" rather than zero; no cost or cross-lane arithmetic is done in the browser. The completion time is the assistant transcript message's `timestamp` for history and the browser clock at closeout for a live turn.
- Visibility is state-dependent: while a turn runs the token line is always visible and updates live; once the turn settles (finalized, paused, or loaded from history) it collapses and reveals instantly on hover or keyboard focus of the bubble. A settled turn with a known completion time shows at least the time segment, so hover always reveals metadata; only a turn with neither usage nor timestamp keeps the line hidden.
- The same hover row carries the bubble's copy affordance, and the row is the only place it appears: a bare `copy` lucide glyph at the same size and color as the metadata text, hidden with the row (`opacity: 0` + `pointer-events: none`) rather than removed, so nothing is permanently visible on a bubble. `.message:hover` / `:focus-within` is the sole reveal gate for both families. On an assistant turn the row is `.ceo-turn-meta`, which wraps `.ceo-turn-usage` and pins the glyph to the bubble's right edge; `setCeoTurnUsage` keeps writing `textContent` of the usage node, so the glyph is a sibling and never a child it would wipe. On user and track-less assistant bubbles the row is `.msg-meta`: `发送于` time for user messages, `完成于` time plus token usage for assistant fallbacks, with the glyph at the user bubble's left corner and the assistant fallback's right corner. `message-stack` is width-hugged (`fit-content`, capped at the bubble's own 760px band) precisely so that row spans the bubble and the glyph lands on a corner instead of the column edge. A bubble with attachments but no text gets no glyph.
- Copy reads the rendered visible text of that one bubble — `.assistant-text` for a track turn (so the stage rail is excluded) and `.msg-content` otherwise — not the markdown source and not a server round-trip, and it reaches the clipboard through the shared `copyTextToClipboard` + `flashTraceCopyButton` lane used by tool-output copy. Clicks bind through one feed-level delegation on `[data-ceo-copy]`; per-bubble listeners would not survive feed rebuilds. Pinned by `tests/resources/org_graph_app.ceo_message_meta.test.js`.
- The live send path stamps the browser clock onto the bubble and into the cached inflight `user_message.timestamp`; server snapshots supply the authoritative transcript `timestamp` on both roles.
- The usage object reaches the browser through the same CEO websocket lanes as the turn it describes: `snapshot.ceo.messages[].usage` for persisted history, `inflight_turn.usage` / `preserved_turn.usage` for live turn patches, and `ceo.reply.final.usage` for the authoritative closeout.
- Live-turn value comes from the session's in-memory per-turn accumulator (`RuntimeAgentSession._frontdoor_turn_usage`, keyed by `turn_id` and incremented once per visible frontdoor `call_model`), exposed through `_build_execution_context_snapshot`. At closeout `_persist_turn_transcript` persists that per-turn aggregate onto the assistant transcript message (`usage` field), so history usage survives independently of artifact retention. Reopening a completed session prefers the transcript-level `usage` in `_build_ceo_snapshot` and falls back to aggregating persisted actual-request artifacts by `turn_id` (`read_session_turn_token_usage`) only for legacy transcripts without the field; all sources produce the same shape, and the aggregation participates in nothing else — baseline/handoff and cache-family decisions never read it.
- Browser-side stability invariants: the turn object keeps sticky usage/completedAt across finalize calls (`setCeoTurnUsage` never clears metadata it already holds, so the history re-finalize path cannot wipe the line); the feed render signature covers per-message `usage`/`timestamp`, so a cached render missing metadata is rebuilt when the authoritative snapshot arrives; and the finalized snapshot-cache write always carries the assistant message's `usage` and `timestamp`.
- The token line is display-only telemetry. It is not prompt-assembly input, not a shrink reason, and must not be used to gate rendering, queueing, or approval behavior.

### Heartbeat Compatibility

- Heartbeat turns count as active session work for the composer button and queueing logic.
- Queued follow-ups should not interrupt heartbeat execution.
- Active-turn follow-ups stay in the browser lane during heartbeat execution too, and become the next fresh user batch once heartbeat finishes; only a per-chip 立即发送 lets the backend see them earlier, where they may merge into the next safe `call_model` boundary of that same running turn.
- Terminal-event delivery is idempotent per session: a re-delivered `task_terminal` whose `dedupe_key` already produced a visible reply is acknowledged silently without running the agent or emitting a second `ceo.reply.final`, so the user sees that reply from the transcript snapshot instead of a live push, and the transcript stays authoritative. Key derivation, the durable callback/outbox boundaries, and the persisted `handled_terminal_dedupe_keys` list belong to `heartbeat-system.md`「Task Terminal Repair Contract」.

### Task Hall Action Contract

- The browser task hall exposes only `pause`, `resume`, and `delete` task actions; `retry`, `continue-evaluate`, and `open continuation` are absent from the UI and REST surface.
- Status pills derive from the current task `status` plus final-acceptance state, but the task's `is_paused` flag is checked **first**: a task in task-level pause renders as `已暂停` even while its `status` is still `in_progress`, and a task that reached `success`/`failed` never renders as `已暂停` because its pause flag is cleared on the terminal transition. What sets and clears that flag — it tracks the task root node's pause state — is owned by `runtime-overview.md`「Node-Level Pause and Recovery」. The multi-select menu uses the backend buckets `已暂停` / `完成` / `未读` / `失败` / `未通过` / `进行中`; `完成` maps strictly to `success`, and `未通过` maps strictly to `unpassed`.
- Batch delete sends one `POST /api/tasks/bulk-delete` request with `task_ids`. The per-task response is authoritative: inspect each `items[]` result (`deleted`, `not_found`, `failed`) before choosing toast behavior.
- The task detail tree exposes node pause/resume controls; pause is local by default, and cascading asks about all descendants including inspection nodes. The backend stores `pause_requested`, `is_paused`, `pause_reason`, and an optional remark; a non-cascaded child continues until its parent reaches a safe boundary.
- Every node pause goes through the shared centered confirmation modal (never a native dialog, never a direct request), because pausing any node interrupts executing work: no node-pause request is sent before the user confirms, and cancelling sends nothing. When the node has an active or waiting child the modal explains that pausing the parent does not stop children and exposes an unchecked `同时暂停所有子节点（包括检验节点）` option, with confirmed `cascade` equal to that checkbox; a node without active children gets the same confirmation without the checkbox, and its request carries `cascade=false`. Only `resume` stays single-click.
- During task-level pause, the tree displays every non-terminal node as `任务暂停` via frontend projection; node pause fields remain unchanged, and recovery reveals any pre-existing node pause.
- The `错误日志` drawer reads `GET /api/tasks/{task_id}/error-log`, shows time, node, and error text, and treats the node id as a navigation target. Clicking it runs the shared tree-node locate pipeline (`locateTaskNode`): each ancestor's round selection switches to the round that contains the next hop, the ancestor's subtree is refetched with that round id (`GET /api/tasks/{task_id}/nodes/{node_id}/tree-subtree?round_id=...` — fetching the default round instead would delete old-round children from the frontend snapshot), then the node is centered and highlighted once; a node that cannot be displayed in any tree resolves to centering its nearest visible ancestor instead of failing silently. Pause/resume changes arrive through the task-node patch/snapshot path, not by reconstructing state from raw storage tables.
- 任务树左上角悬浮节点搜索框：输入节点 ID 或 goal 关键词后，在前端快照（`nodes_by_id`）中按“精确 > 前缀 > 包含”（ID 与 goal 同分优先 ID）排序展示候选，每条显示 goal、节点 ID 与状态。点击候选走同一定位管线并把缩放固定到 `TREE_FOCUS_SCALE`（1.2）以便看清节点；定位不清空搜索框内容与结果列表，方便在候选中连续跳转。定位命中的节点播放一次性放大脉冲动画（`.task-tree-node-locate`：放大到 1.18 倍并保持，配 #39c5bb 光圈后回落，约 1.2s）；动画窗口期记录在 `S.treeLocateHighlight`，整树重渲染后以负 `animation-delay` 补挂并从当前相位续播，保证运行中任务的高频重渲染不会吞掉高亮。因跳转到旧轮次而产生的手工轮次选择会让「回到最新树」按钮出现，点击它恢复所有节点的最新树视图。清空选择本身不够：切轮次走的是「先删旧子树再整体重建」的合并，被切过的那个节点在默认轮次下的孩子已经不在前端快照里，所以「回到最新」在确实存在手工选择时补一次整树快照，否则该节点会渲染成空子树，整棵树看起来像没加载出来。
- Task pause is a synchronous experience with an in-card hint: after a single-card or batch `pause` request succeeds, that task's card renders a small hint box (not a page-top toast) showing `暂停中 (stopped/total)` with a spinning icon and a `恢复运行` button while the backend reports draining, and switches to `暂停成功` (auto-hidden after ~2.5s) once draining ends; the page-top success toast is suppressed because the hint owns that feedback. Truth comes from `GET /api/tasks/{task_id}/pause-state` (`internal_total` / `internal_stopped` / `draining`), polled every 400ms with a ~30s cap: `draining` is true only while that task's `pause_task` command is still unfinished and a live worker exists, so `暂停成功` means the worker actors truly stopped rather than only the durable flags being set. The `恢复运行` button runs the ordinary resume path — worker command FIFO guarantees the resume lands after any still-pending pause command.
- 任务磁盘治理 UI（契约本体见 `runtime-overview.md`「磁盘写保护与治理」）：任务大厅性能条的磁盘数据与剩余空间合并显示在「CPU/内存/磁盘」一项的磁盘段（`0%(剩余10.1G)`，紧急=critical 着色落在该项上；数据来自 `GET /api/tasks/worker-status` 的 `machine_pressure_disk_busy_percent / machine_disk_free_bytes / disk_emergency_active`，1s 轮询；该接口只给最新快照，历史区间的读法与模型侧入口见 `runtime-overview.md`「Worker Performance History」和 `tool-and-skill-system.md` 的 `perf_inspect` 行），不单列「磁盘剩余」项，紧急态在任务网格顶部渲染红色横幅。任务卡片动作只有 `暂停/恢复/清除临时文件/删除`（kebab 菜单，`taskCardActions`），删除确认文案明示「报告类产出自动导出到 deliverables 目录保留」；「清除临时文件」同样走确认框（warn 档），成功后按 `freed_bytes` 报释放量、`failed_dirs` 非空时降级成「部分临时目录未删除」警示，两者都只重载列表让占用数字刷新、不移除卡片。两个动作的可见性判据不同且必须与后端逐字一致：`canDelete` 含暂停态，`canClearTemp` 只认 `success`/`failed`（清除契约见 `runtime-overview.md`「手动清除任务临时文件」）。任务数据没有归档/压缩/固定状态，也没有任何自动删除——任务只随用户手动删除（或模型删除工具）彻底清除，任务卡片经 WS `task.deleted` 推送从列表消失，无墓碑徽章；`.pc-corner-badge`、「已清理」chip、pin/compress/decompress 端点与按钮均不存在。
- 任务大厅大小与排序：任务总占用 `disk_usage_bytes` 随 `GET /api/tasks` 与 WS `task.summary.patch` 下发（口径 = files/artifacts/event-history/temp 目录实测 + 五张大行表 payload 字节；小时对账 + 终态对账，展示延迟 ≤1h；patch 缺失该字段时前端合并保留旧值）。每张任务卡片渲染「占用大小」一行（`org_graph_tasks.js` `formatTaskBytes`），卡片增量补丁（`patchTaskCardElement`）同步刷新该值；任务由 `in_progress` 转终态时前端延迟一次全量 `loadTasks`，拿终态清理与对账后的最终值。大厅工具栏提供排序开关（`#task-sort-select`）：按时间（默认，创建时间倒序）或按大小（占用字节倒序，同为 0 时回落时间序）；排序是纯前端客户端行为（列表全量下发，比较器 `compareTaskListOrder` 与增量插入共用，切换经 `resortTaskOrderedIds` 重排并重置渲染签名；`diskUsage`/`sortMode` 进渲染签名）。排序状态不持久化，刷新回默认时间序。清除临时文件与终态清理都会在动作结束时同步重算一次对账，所以这两个动作后的占用大小是即时值，不等小时级 loop。模型侧对应能力：`task_stats` 工具 `mode=list` 支持 `sort=size`，大小读自 `task_disk_usage` 记账表（无记账的新任务兜底一次目录实测）。
- 任务卡片时间行与总耗时：卡片时间字段取自 `TaskListItem` 的 `created_at` / `finished_at`（`finished_at` 只在 `success`/`failed` 终态写入，窄读 `json_extract` 与整包回退两条路径都要产出，见上文列表读契约）。首行标签「开始」（`created_at`），任务进入终态时同行追加「结束」+ `finished_at`（`taskIsTerminal` 覆盖 `success`/`failed`/`unpassed`）。「占用大小」行右侧只显示分钟精度的耗时数字（`taskElapsedText`，如 `15h30m`，不足一小时降为 `30m`），无标签。耗时参考时刻的取法决定其是否增长：终态定格在 `finished_at`、暂停（`taskStatusKey=blocked`）定格在 `updated_at`（暂停后 actor 停止、无节点活动刷新该字段，故暂停期间数字不涨），运行中用 `Date.now()`。耗时只随渲染签名重建刷新——运行中卡片因 token/输出变化频繁重建而逐分钟推进，暂停或终态卡片不因心跳/读取动作刷新而保持稳定；不把 `now` 放进签名，以守住大厅滚动防抖。

### Web Event Loop Contract

- The web server runs one uvicorn event loop shared by every `/api/*` route and websocket. All `/api/tasks/*` read handlers (`main/api/rest.py`) are async and run their synchronous query work (SQLite reads, pydantic parsing, snapshot building) via `asyncio.to_thread`, keeping the event loop itself free while heavy tree-snapshot or task-detail builds run. Control-plane handlers (pause/resume/cancel/delete/notice/bulk-delete) stay on the event loop.
- `GET /api/tasks/{task_id}` runs its `mark_read` step on the event loop before offloading the snapshot build: `mark_task_read` publishes `task.summary.patch` through the registry, whose subscriber queues are `asyncio.Queue`s that only the loop thread may touch. Any new query path that publishes to the registry must not move into `asyncio.to_thread`.
- Offloading to threads does not by itself unblock light reads, because `SQLiteTaskStore` funnels every read through one read connection guarded by `_read_lock`; a heavy read (multi-MB `task_node_details`/`nodes` payloads) would serialize the light reads behind it. The store therefore keeps a second `_light_read_conn` (own `_light_read_lock`) for the high-frequency small reads the task hall polls — `list_worker_status`, `list_task_summaries`, `get_task_disk_usages` — so they run concurrently with heavy reads under WAL instead of queueing. `_fetchall_light`/`_fetchone_light` route to it; `refresh_read_snapshot` and `close` service both connections. New high-frequency light reads should use the light fetch helpers; a reader must never mix the two connections in one transaction.
- `GET /api/tasks` reads through the narrow path: `SQLiteTaskStore.list_task_summaries` extracts the list fields from `tasks.payload_json` with `json_extract` instead of parsing the full `TaskRecord` blob per task (`user_request`/`final_output` reach megabytes on report tasks). `TaskQueryService.get_tasks` falls back to the full parse when the narrow read is unavailable, and both paths produce identical `TaskListItem` rows (equivalence pinned by `tests/resources/test_task_list_narrow_read.py`). New task-list fields need both the `json_extract` expression and the fallback builder.
- The CEO surface obeys the same protection. A `/ws/ceo` connect and `GET /api/ceo/sessions` build the session catalog across every CEO/channel transcript (a cold cache parses tens of MB of JSONL), load the requested session transcript, and project the transcript snapshot; all of it runs through `g3ku/runtime/ceo_catalog_offload.py` on one dedicated single-thread executor (`run_off_event_loop`), so a CEO WS reconnect — browser tabs wake from sleep and reconnect in bursts — never stalls task-hall endpoints. A short-TTL catalog cache collapses the repeated builds inside one connect/publish burst; write-side handlers (create/rename/delete) store their fresh catalog through `store_ceo_catalog_cache`, whose generation bump discards any stale in-flight async build result, and `POST /ceo/sessions/{id}/activate` builds through `build_ceo_session_catalog_async` for the same reason — a synchronous catalog build there pins the event loop for the whole session-switch click. The executor thread reads the same `SessionManager` as the loop, so `SessionManager.get_or_create` guards its load path to keep a session from ever loading into two forked objects. New CEO read paths that walk transcripts must go through the same executor instead of the event loop.
- The turn-event side of the CEO surface is protected the same way: every frame a tool event produces is built on the loop, so per-event work has a hard budget. Session catalog/patch rows for `ext:` channels resolve their bridge label through `g3ku.config.live_runtime.get_runtime_config()` (mtime-keyed cache) rather than `load_config()`, because that builder runs once per `state_snapshot` — i.e. per tool call — and `load_config()` re-runs the whole config migration and validation pipeline (~50 ms) each time. New per-event display helpers take the cached accessor; `SessionManager.get_or_create` on a warm cache and transcript row walks are the other two allowed costs there. What remains after those are the patch build itself, bounded by the per-connection coalescing window described in「Streamed Reply Delta Contract」and by the delta-only live frame rule in「CEO Turn Timeline Rendering Contract」.
- Web cron readiness never spawns subprocesses on the event loop. `ensure_web_runtime_services` sits on every internal task-event callback, and its readiness gate (`_cron_runtime_ready`) checks the cron service status first: an enabled cron is ready without any port-ownership probe. The probe itself (`_process_owns_listen_port`, netstat/ss) exists only to decide whether this process should start web cron; its result is cached per (port, pid) — a confirmed ownership lives for the process lifetime, a negative or failed probe is retried after a short TTL. Synchronous child-process spawning on the loop froze the whole server for a second or more per worker event callback on connection-heavy machines (all task-hall requests stalled at once). New readiness checks must stay allocation-free on the loop or go through the offload executor.
- Task-hall grid rebuilds are signature-gated and scroll-preserving (`org_graph_tasks.js`). The render signature (`taskGridRenderSignature`) may only contain values that change rendered pixels: `workerLastSeenAt` was removed after it turned every worker heartbeat into a full grid rebuild — the grid element is its own scroll container, and the rebuild's `innerHTML=""` reset `scrollTop` to zero, so hall scrolling looked frozen while the performance bar kept updating. `renderTasks` captures `scrollTop` before a same-page rebuild and restores it afterwards; a page-number change intentionally starts at the top. In-place token updates go through `patchTaskCardElement` and re-stamp the signature without rebuilding. The three token metrics carry one growth cue: `.pc-metric-value.is-increasing` plays the one-shot `pc-token-breathe` color swell, and `patchTaskCardElement` removes that class, forces one reflow per card, then re-adds it — a counter that rises on every patch would otherwise keep the class applied, and a CSS animation restarts only when the class is genuinely re-applied. The animation is the deliberate exception to the global `prefers-reduced-motion` silencing (the glow drops, the fade stays), so "tokens grow with no feedback" points at the class churn rather than at the media query; the `.pc-metric` box itself carries no highlight style. New fields belong in the signature only if they change visible output; anything ticking with time (heartbeats, clocks) stays out. Pinned by `tests/resources/org_graph_tasks.hall_scroll_survival.test.js`.

### Task Tree Live Sync And Self-Healing Contract

- The task-detail websocket (`/api/ws/tasks/{task_id}`) reconnects automatically at 1s intervals after an unexpected disconnect while its task detail view is still open and `S.currentTaskId` still names that task. Intentional closes (switching views, opening another task) detach the close handler before closing and never schedule a reconnect; the task-list WS follows the same reconnect policy.
- Live events missed during a disconnect window are not replayed. After a reconnect the browser therefore refetches the task detail and the full tree snapshot with `preserveView + reopenSocket:false` to re-align state; manual round selections survive that reconcile.
- The tree snapshot cache defends itself against corrupting incremental merges:
  - `applyTaskTreeSubtreePayload` rejects any subtree response that does not contain its own `root_node_id` and falls back to a full `tree-snapshot` reload. Its merge is a destructive wipe-of-old-subtree-then-rebuild, and a response missing its root would cut that root out of the cache; when the subtree root is the tree root, the whole tree disappears while node search still matches the stale cached entries.
  - When `renderTree` finds `S.treeRootNodeId` missing from the cache, it renders the empty state and schedules a debounced full-snapshot reload, capped at two attempts; a successful full-snapshot apply resets that budget.
- `renderTree` replaces the whole `U.tree` DOM, so anything carrying user interaction state must be re-findable afterwards by a stable identity rather than surviving the rebuild:
  - Which round a node shows is `S.treeSelectedRoundByNodeId` (pruned only when that round really disappears from the node, and cleared by a full snapshot reload), so every rebuild re-renders the same selection.
  - The round dropdown's expanded state is restored, not preserved: `treeRoundSelectId(nodeId)` gives the `<select>` an id that does not change between rebuilds, `buildResourceSelect` copies it onto the shell as `data-select-id`, and `renderTree` finishes by calling `restoreOpenResourceSelect(U.tree)`, which reopens the shell named by `S.openResourceSelectId` and returns focus to the selected option. `S.openResourceSelectId` is cleared on close (option picked, Escape, click away), so a rebuild that follows a selection does not pop the menu open again. A node whose dropdown is gone from the new tree is skipped silently. Any future in-tree popup control needs the same stable id, because `buildResourceSelect` falls back to a random `selectId` when `select.id` is empty and a random id cannot be recognized after a rebuild.
- Node badges state what the node is doing, never its raw status token: a non-terminal node renders 运行中 / 请求中 / 检验中 / 等待中 and never `IN_PROGRESS`. The judgement lives in `resolveTreeNodeStatusLabel` and reads three live inputs — the node's own runtime frame (phase, `stale`, `await_marker`) and its acceptance children's statuses:
  - `运行中` / `检验中` require the node to be inside its own turn: `isLiveTurnFrame` accepts the `before_model` / `after_model` / `message_distribution` phases or a still-in-flight tool call, and rejects a frame that is waiting on children. A frame normally exists only while that node's turn is in flight (`remove_frame` clears it when the turn returns a terminal result, and the task's terminal path clears the whole set), so "has a frame in a turn phase" is the browser's evidence of real execution. An acceptance node in that state reads 检验中, an execution node 运行中. The phase set mirrors the `runnable` derivation in `main/monitoring/log_service.py::_frame_index_payload`; changing one means changing the other.
  - `等待中` covers every other non-terminal node: a parent whose spawn round has not returned, an acceptance node that has never been dispatched, and an acceptance node idle because its verdict sent its execution node back for a retry. 检验中 therefore never stands for "an acceptance node exists".
  - `请求中` is the in-flight sub-state of 运行中: the node's own fresh frame carries `await_marker` = `model.chat.dispatch` or `model.chat.await_response`, i.e. the provider call has been sent and its stream has not come back. It writes `visualState: "running"`, so the badge keeps the execution blue and the card treatment is unchanged — the label only names which part of the turn is holding. `model.chat.response_postprocess` is deliberately excluded: by then the stream has ended. A stale frame never reaches this branch (`stale` is checked first), so a node that stopped producing frames at 15:00 reads 等待中 rather than a permanent 请求中.
  - A submitted execution node (`success`) whose acceptance child has not reached a terminal status is still `等待中`, not a completion label: the delivery has not been accepted yet.
  - Pause outranks all of this: a task-level pause renders every non-terminal node as 任务暂停, a node-level pause as 已暂停（reason）, per `runtime-overview.md`「Node-Level Pause and Recovery」. That doc also owns the tool-side reading contract (`task_progress`, which additionally demotes stale frames to 疑似中断).
- Because those inputs arrive on `task.live.patch` and `task.node.patch`, badges move with the runtime: `refreshRenderedTreeNodeStatuses` re-derives the whole tree model and patches each rendered node's badge, card color and connector color in place on the next animation frame, without refetching the snapshot. The same pass refreshes the open node drawer's status line (`syncSelectedTaskNodeDetailStatus`), so a selected node's label tracks its activity without reopening the drawer. Display state must therefore not be computed from snapshot-only fields: `task.node.patch` carries node-record fields, and `children_fingerprint` changes only when the child set changes, so a label derived from handshake or other snapshot projection fields stays frozen until a branch sync or a reopen.
- A frame the backend marks `stale` never reads as in-turn. Every runtime frame reaching the browser carries `stale` and `await_marker` — `TaskLiveFrame` on the task snapshot, the `runtime_summary.frames` entries on `task.live.patch` — derived from the frame row's own `updated_at` against `main/monitoring/frame_liveness.py::STALE_FRAME_MINUTES`, the same threshold `task_progress` uses for its 疑似中断 demotion (`runtime-overview.md`「Node-Level Pause and Recovery」). The patch channel spreads the raw frame payload so it carries every field, while the snapshot channel serializes a model: a badge predicate that reads a frame field needs that field on `TaskLiveFrame` too, otherwise the label only appears after the first patch and the two transports disagree on the same node. The tree demotes such a node to 等待中 and does not borrow the tool's 疑似中断 wording: a stale frame proves nobody rewrote it, not that the node stopped existing, and the browser has no frame age to quote. The flag is computed as the payload is built, so it ages out on the next patch or reload rather than on a browser-side clock.
- 活跃节点 (`syncTaskTreeHeaderState`, which also writes `S.taskSummary.active_node_count`) counts nodes in their own turn plus paused non-terminal nodes. It uses the same in-turn predicate as the badges so that undispatched acceptance nodes, which are always rendered, do not inflate it.
- If an operator reports "the task tree is frozen although the task is running", check the tab's task-detail websocket first: a tree stuck on a stale snapshot means the detail WS dropped without a working reconnect. Confirm the reconnect loop in the browser console before debugging the runtime side.

### Task Tree Chunked Load Contract

- `GET /api/tasks/{task_id}/tree-snapshot` serves one bounded chunk per request when `max_nodes` is set: nodes are sliced in a stable order (`sort_key, node_id`), so consecutive chunks never overlap, and the response carries `truncated`, `total_node_count`, and `next_after_node_id`. The browser continues with `after_node_id=next_after_node_id` until `truncated=false`. Without pagination params the endpoint keeps the historical whole-snapshot payload; the per-node subtree endpoint is unchanged.
- `_build_tree_snapshot` materializes only the current chunk's nodes and reads per-node state through the light projection rows (pause/handshake/pending-notice fields are written there at sync time); the runtime `nodes` blobs are fetched only for legacy projection rows that predate those fields — a per-node `get_node` when the row carries no handshake state, plus one batched read per build for rows lacking the pending-notice count. Per-node full-payload `get_node` reads are what made whole-tree builds exceed the browser's 10s default timeout on large trees, which is why display state is derived in the browser instead of from an extra per-node read here. Token aggregation likewise reads `payload_json` via `json_extract` instead of parsing whole detail payloads.
- The browser treats the chunk pipeline as the task-open bootstrap: `loadTaskTreeSnapshot` resets the tree cache on the first chunk, merges later chunks by node id, and gates `renderTree` via `S.treeBulkLoadingTaskId` so no partial tree renders mid-load. While loading it shows a one-line progress notice `正在打开任务：加载中 (loaded/total)` in its own element (`U.taskLoadNotice` / `#task-load-notice`, a pill inside the toast viewport): no title row, no close button, `pointer-events: none`, and it stacks above a toast rather than overlapping it. Its vertical offset is measured at each show against the tree's top-left search box (`.task-tree-search`), so the line lands on the search box's height — the details header wraps at narrower window widths, which moves that box by ~80px, so the offset is not a constant; when the anchor is missing the CSS default applies. The notice belongs to the task-open path only — `loadTaskTreeSnapshot` arms/updates/finishes it solely under `announceLoad`, which `loadTaskDetail` sets when `preserveView` is false. In-place reloads never raise it: node pause/resume, append-notice, snapshot self-heal and subtree fallback call `loadTaskTreeSnapshot` without `announceLoad`, and the `loadTaskDetail({preserveView: true})` refreshes (pausing/resuming the currently open task, batch actions, the post-reconnect reconcile) fall under the same rule; reporting 正在打开任务 there reads as if the task had been reopened. An in-place reload that supersedes an in-flight open flow cancels the open flow's stale notice instead of adopting it. The notice first appears after a ~400ms delay (while the task-detail request is still in flight it reads `0/…`), so small-tree opens do not flash it; once visible, every chunk updates the numbers — the chunk-count anti-flicker gate only decides whether to *start* showing, never whether to update. When the last chunk lands, the final numbers stay visible for ~800ms before the notice hides (show then immediately hide would leave no painted frame), and the loader renders the tree once, keeping the existing fit-to-view behavior. A mid-load failure shows the inline tree error plus an error toast.
- A per-load token (`S.treeBulkLoadToken`) invalidates an older chunk loop when a reconnect or reopen starts a newer load for the same task; chunk merges are idempotent by node id. A vanished cursor node restarts the slice from the head — the id-based merge skips nothing.
- Leaving the task-detail view cancels the tree-load pipeline instead of letting it finish in the background (`cancelTaskTreeLoading`, called from `switchView`): the per-load token is bumped so an in-flight chunk loop stops at its next request boundary, the load notice and snapshot self-heal timer are cleared, pending branch-sync timers and dirty flags are dropped, and a view generation (`treeDetailGeneration`) is bumped so an in-flight `tree-subtree` response is discarded before its merge. `loadTaskTreeSnapshot`, `renderTree`, and branch-sync scheduling additionally early-return while the detail view is hidden, so operation callbacks (node pause/resume, append-notice) cannot relaunch the chunk stream or a full tree rebuild from the task hall, and a `loadTaskDetail` that resolves after the user has left applies nothing and does not reopen the task-detail WS. Re-entering a task always runs a full reset-and-reload, so the cancellation discards no visible state; it exists to keep the task hall responsive instead of burning chunk requests and whole-tree DOM rebuilds in the background.
- The same exit path releases the retained detail state and its rendered DOM (`releaseTaskDetailRetainedState`): the whole-tree snapshot, per-node full details, context caches, and the trace/message containers are dropped so the hidden view does not keep megabytes of heap and thousands of DOM nodes resident. On memory-overcommitted machines a large resident tab gets trimmed and paged out by the OS, and the next interaction freezes for seconds while it faults back in (queued wheel input replays all at once). Reopening a task refetches everything, so the release costs no visible state. When leaving the detail view, the release and its companions (view-state capture, token-stats drawer close, persist scheduling) do not run in the click frame: `switchView` synchronously cuts the live WS and cancels the tree load, then defers the heavy steps to the next macrotask, so the click frame only flips views and fires the hall requests — the same requests the sidebar nav fires (`GET /api/tasks`, `/api/ws/tasks`, worker-status). This aligns the back-arrow timing with the two-hop sidebar detour path (which users observed as smooth) instead of stacking the detail teardown's concentrated cold-memory touches with the hall re-render in one frame; if the user re-enters the detail view within the same tick the deferred teardown is voided wholesale. Pinned by `tests/resources/org_graph_app.task_detail_exit_defer.test.js`. (History: a temporary two-hop detour shim — back-arrow via the conversation-list view — was trialed to spread the exit work across frames and reverted unchanged once instrumentation showed the perceived freezes came from heartbeat-driven whole-grid rebuilds (`taskGridRenderSignature`) and machine-level memory storms, not from the back path's click-frame timing.)
- `ApiClient.getTask` uses a 120s client timeout instead of the 10s default: the payload scales with task size and the 10s bound surfaced as `Failed to open task: Request timeout` on large trees.

### Node Detail Error History

- The node detail drawer embeds a `历史错误记录` section between `验收` and `日志`. It reads `GET /api/tasks/{task_id}/nodes/{node_id}/error-log` and lists that node's raw records (time, node title, full error text) newest-sequence first; an empty node shows `暂无历史错误`, and a header `刷新` button refetches.
- History rows are the same `task_error_logs` records as the task-level `错误日志` drawer, filtered by node. They are durable history, not live-only state: they persist while the task exists and are deleted with the task.
- The runtime appends a record for every invalid final-result submission while the node is still running (not only when the node dies): the entry carries submission count, `response_tool_call_count`, tool names, `output_tokens`, `finish_reason`, provider model and `sent_max_tokens`, plus a `疑似触及输出token上限被截断` marker when `output_tokens` reached the sent cap — enough for operators to confirm truncation or no-tool-call failures without reopening request artifacts.

### Node Output Content Read Contract

- `GET /api/content/{describe,search,open,read}` plus the excerpt/`full` lane of `GET /api/tasks/{task_id}/artifacts/{artifact_id}` are the HTTP face of `ContentNavigationService` (`g3ku/content/navigation.py`). The node detail drawer and the CEO feed hydrate a stored tool-output ref into full text through `read`.
- A ref whose bytes are gone is an expected state rather than a server fault: disk governance prunes a task's `temp/tasks/` outputs and its artifact rows while node trace rows keep quoting those refs. `_resolve` reports it as `FileNotFoundError`, and `main/api/rest.py::_content_action` answers `404` with `detail.code` `content_not_found`; a ref that resolves to something other than a file answers `400` with `content_ref_invalid`. Both sit under the `≥500` audit threshold, so a cleaned output never enters the log audit stream. Pinned by `tests/test_web_content_ref_error_mapping.py`.
- Hydration de-duplicates by ref, not by DOM node, because every panel render recreates the code block: `getTraceOutputContentByRef` stores a `404` as a terminal cache marker, and the block renders `完整输出已被清理，仅保留预览片段` under the retained preview while the copy lane keeps returning the preview text alone. Any other failure (503, timeout, transport) stays retryable. Pinned by `tests/resources/org_graph_app.trace_output_cleaned.test.js`.

### Task Token Stats Window Contract

- The task-detail `Token统计` modal (`ensureTaskTokenUi` / `renderTaskTokenStats` in `g3ku/web/frontend/org_graph_tasks.js`) renders a task-level topline, the per-model breakdown, and the 模型调用明细 table. The table's data is `recent_model_calls` of the task snapshot (`main/monitoring/query_service.py::_recent_model_calls`, unbounded) merged with live `task.model.call` websocket events; each row is a `TaskModelCallRecord` (`main/monitoring/models.py`), which carries `call_index`, `node_id`, `created_at`, prepared-request counts, the per-call usage delta, and the per-call gauges `duration_ms` / `first_token_ms` / `thinking_tokens` — the same record family also feeds the `task_progress` tool's `model_calls` field, so node-level attribution stays consistent between the web window and tool output.
- The topline and the per-model breakdown have separate sources: the topline reads the task record's own `token_usage`, while the breakdown is the snapshot's `summary.token_usage_by_model`, aggregated by `main/monitoring/query_service.py::_projection_token_usage_by_model` from every node-detail projection row. That aggregation never loads the multi-MB detail columns: it narrow-reads each row with `json_extract(payload_json, '$.payload.token_usage_by_model')`, because a node's per-model list lives inside the detail record's own `payload` object (`main/monitoring/models.py::TaskProjectionNodeDetailRecord.payload`), not at the row's top level. A window that shows real task-level numbers while reporting 尚无按模型明细 therefore points at that read path or the JSON path it queries, not at the token-recording writer.
- 模型调用明细 puts 序号（the call sequence number）first and defaults to 时间（`created_at`）descending with `call_index` descending as the same-instant tiebreak; records without a timestamp sink last. The table additionally shows 节点ID so per-node token attribution can be confirmed without leaving the window, and the three gauges 总耗时 / 首 Token 耗时 / 思考 Token so a slow call can be told apart from a call that merely sent a large context.
- The gauges are per call, not per node: the 咽喉点 (`main/runtime/chat_backend.py`) times each provider request and fills `LLMModelAttempt.duration_ms`; the streaming providers fill `LLMResponse.first_token_ms` from their stream diagnostics (first received chunk, falling back to the first text delta); thinking tokens come from the provider's own `reasoning_tokens` usage field, extracted by `normalize_usage_payload`. `TaskLogService._model_call_attempt_metrics` then folds one call's attempts into the row: durations and thinking tokens sum across retries, while first-token latency takes the **last** request that reported it — a fast failed retry must not become the row's value. A gauge no provider reported stays `null` and renders `--`; it must never be coerced to `0`, which would assert the model did not think. Non-streaming requests have no chunks to measure, so their 首 Token 耗时 is `--`.
- The window is frozen while open: live events keep updating `S.recentModelCalls` in the background but do not rebuild the open window, so scroll position, the current filter and the search box content survive real-time patches. The 刷新 button beside the search box is the only manual refresh entry (`renderTaskTokenStats({force})`); reopening the window always renders from the latest in-memory state while preserving the search query and page.
- The search input to the right of the 模型调用明细 title filters by 序号 (call sequence number, substring match), node id, or the model cell's searchable text — the resolved config name plus the raw ledger identifiers (`model_key` / `provider_model` / `provider_id`), per「Backend Responsibilities」; the filter runs over **all** records before pagination (searching never limits itself to the visible page), then pagination paginates the filtered set. Search and pagination rebuild only the table region (`refreshTaskTokenCallTable`), leaving the search input element, its focus and its value intact.
- The modal is `min(1200px, 100vw - 32px)` wide and the twelve-column table is compacted to fit it (0.78rem cells, 6px/7px padding) rather than being allowed to overflow: 节点ID and 模型 cells ellipsize in-cell, so the right-most columns are not pushed out of view. `.task-token-call-table-wrap` keeps horizontal scrolling as the narrow-viewport fallback.

### Task Message Distribution UI Contract

- Task-tree distribution UI is scope-driven: the frontend treats `runtime_summary.distribution.mode == "subtree_barrier"`（兼容旧持久化 meta 的 `task_wide_barrier` 名称）as the authoritative banner source instead of inferring state from the root node's pending-notice count alone. `target_node_ids` names the frozen subtree roots and `blocked_node_ids` carries exactly the frozen subtree union — the tree view banners and highlights only the frozen subtree: nodes listed there render `barrier_blocked`, and connector lines turn the amber distribution color only between affected nodes; nodes outside the subtree keep their ordinary status rendering and keep executing.
- While the epoch is in `barrier_requested`, `barrier_draining`, or `distributing`, the task-tree view shows a task-local sticky notice (text 「新消息分发中」, not a global shell toast) and marks affected connectors: `distributionAffectedNodeIds` expands `blocked_node_ids` ∪ `target_node_ids` into full snapshot subtrees; a rendered item receives `execution-tree-item--distribution-affected` when its node is affected, and its child list receives `execution-tree-list--distribution-affected` when the parent node is affected. CSS colors a connector only when both endpoints are affected (list + item carry the classes), so the boundary edge between a frozen subtree root and its unaffected parent keeps its status color. When the epoch completes (target notices consumed/processed) the distribution state clears, the classes disappear on the next render, and connectors restore their status colors.
- A distribution `state == "failed"` renders the same sticky notice in a red failed variant (`task-tree-distribution-bubble--failed`) whose text carries `distribution.error_text` plus the intervention hint (re-append the notice to retry, or resume the task), and keeps the affected-subtree connector marking because the subtree stays frozen as the failure lever; an explicit resume downgrades the banner to the ordinary pending-notice state (`resume_ready`) and clears `blocked_node_ids`/`target_node_ids`. Failure semantics are owned by `runtime-overview.md`「frontdoor 与任务运行时的关系」.
- Node detail receives a backend-owned message list (its own section before `派生记录`) rather than a pseudo execution stage, and the frontend must not reconstruct entries from raw mailbox tables or prompt tail blocks. The message list shows real message content only: system-generated「定向通知转述族」(【任务收到用户定向通知】/【后代节点收到用户定向通知】/【被检验节点收到用户定向通知】/【正在检验的节点接收了用户通知】, marked `payload.origin=system_relay` on ledger rows, or matched by message prefix for legacy rows) is filtered out of the display list and the tree pending-notice count, while the ledger rows themselves and the node context merge path stay untouched — these relays still reach the model's acceptance/ancestor notice windows. Distribution results are backend-owned and show delivered targets and skipped targets (with the recorded reason) as node + distribution-state rows only: 每条投递行渲染语义标签 + 图标芯片 via `messageDeliveryStatusDescriptor`/`renderMessageDeliveriesField` — 已分发·待处理 (`delivered`) / 已消费 (`consumed` without `merged_at`) / 已并入上下文 (`consumed` with `merged_at`) / 未下发 (`skipped`) — and must never surface raw ledger status tokens (`[delivered]`/`[consumed]`); the backend supplies `consumed_at`/`merged_at` on each distributed delivery for that derivation. The delivered row does not repeat the message body (it is already shown in the entry's 消息内容 field); the skipped row keeps its reason.
- **消息三态**：message-list entries render `status` as 待处理 (`pending`：已投递、任何回合尚未处理) / 已消费 (`consumed`：控制或决策回合已处理，内容等待恢复路径并入或不再并入) / 已并入上下文 (`merged`：内容已真正注入模型上下文)。`messageListStatusDescriptor` 是三态标签的唯一映射；`consumed` 与 `merged` 的判定源是后端账本（`merged_at` 字段与归档记录），前端不做推断。条目内的「分发情况」沿用同一套三态语义（见上一条），显示的是各接收节点侧的状态，而不是发送侧动作。
- **定向通知输入框**：节点详情「消息列表」标题右侧（`.agent-detail-section-header` 内与 h4 平级，h4 内容会被 `renderMessageHeading` 整体重写）常驻一个输入框+发送按钮（`syncNoticeComposerState` 控制可用性：验收节点/终态节点/已结束任务禁用并给出原因 placeholder）。提交走 `POST /api/tasks/{task_id}/nodes/{node_id}/notice`（body `{message}`，网页端不做会话归属校验，其余校验与工具一致：终态目标 400 `append_notice_target_terminal`、验收/不可见目标 400 `append_notice_invalid_node_target`），成功后刷新整树快照并强制刷新当前节点详情。分发是异步链路（epoch 排队→分发节点决策回合→投递记账），提交返回时新消息通常尚未落表：前端随后启动局部 settle 轮询（`settleTaskNoticeAfterSend`/`runTaskNoticeSettleTick`，间隔 2.5s、单条消息 90s 超时），轮询只重拉目标节点的 full 详情并局部重渲染消息列表，消息一经记账即自动出现；超时静默退出，由 WS `task.node.patch` 与手动刷新兜底。`resetTaskView` 清空轮询状态。
- Tree snapshots expose two visibility contracts that must not be collapsed: `parent_visible` / handshake fields are the distribution-oriented recipient projection, while browser rendering shows every node the snapshot carries. Execution nodes stay visible in every status, and an acceptance node stays in the tree for as long as its execution node has one — dispatched or not, terminal or not. Force-showing all nodes while distribution is active is not proof that they were all valid recipients.

### Task Recovery Notice UI Contract

- 「本任务遇到异常停止，已回退到稳定步骤继续。」（`task.metadata.recovery_notice`）以全局 toast 呈现：打开对应任务或该任务数据刷新时弹出一次，`kind=warn`、persistent（不自动消失），标题「任务自动恢复」。
- 全站只有一个 `#app-toast` 元素，所有提示（含任务恢复提示）共用它，因此外观合同只有一处：**上下定档、左右跟文案**。标题与正文排同一行（13px / 行高 1.5），卡片高度只由这一行里的 32px 关闭键加 4px 上下内缩决定（1280×690 实测 42px），`width: fit-content` 让横向等于文案实测宽（短提示 137–189px），`min(420px, 100vw - 48px)` 只是长文案的折行上限而不是固定宽（30 字左右的恢复提示因此折成 3 行、68.5px）。圆角固定 16px（与 `--ui-radius-control` 同档），不随盒子变小收档。关闭键收档写在 V2 层：`.icon-btn` 全局是 36px 见方，比这行文字高，会把卡片顶回一行装不下的尺寸。文案下方没有进度条（persistent 与非 persistent 一视同仁），垂直位置顶部 20px + safe-area。视口的居中基准归「Navigation Bar And Compact Mode」的 fixed 层规则。同一视口里的「正在打开任务」进度条不是可关闭面，按自身宽度渲染，不跟这条合同走。
- 用户可以点击关闭：点击 toast 任意位置（含右上角关闭按钮）即关闭，并把该任务的关闭记录写入浏览器 `localStorage`（键 `g3ku.taskRecoveryNotice.dismissed.v1`，内容为 任务 id → 提示文本），前端在首次评估提示时一次性读入 `S.taskRecoveryNoticeDismissals` 后按内存值判重——整树每次渲染都会重新评估该提示，只靠内存集合会在刷新页面或重启 Web 后把已关闭的提示再弹一次。同一任务不再重复弹出；切换到其他带提示的任务仍会弹出自己的提示；提示文本变化（含后端换文案）使记录失配，该任务会再提示一次。
- 该记录只存在于浏览器侧，不是后端状态：任务元数据里的 `recovery_notice` 不会因关闭而被清除，换浏览器或换设备会重新提示一次，也不需要任何服务端清理入口。
- 若 toast 在用户关闭前被其他提示覆盖，下一次任务树渲染会重新弹出该提示（显示状态按“当前显示的提示文本”去重，而不是按“曾经显示过”）。
- 提示是否出现由后端元数据决定：只有非优雅中断后的恢复清洗写 `recovery_notice`；优雅暂停 + 自动恢复不产生该提示。生命周期语义见 `runtime-overview.md`「Graceful Shutdown Pause and Startup Auto-Resume」。

### Task Depth Default Contract

- The task-hall "global task tree depth" control is a global main-runtime default, backed by `PUT /api/main-runtime/settings`.
- New CEO/web sessions inherit that global default lazily. The runtime must not freeze the current global depth into ordinary session metadata just because a session was created, listed, or reopened.
- A CEO session only overrides the global task depth when the session has an explicit session-scoped override saved through `PATCH /api/ceo/sessions/{session_id}/task-defaults`.
- That explicit override is persisted as session-owned metadata and remains authoritative for later `create_async_task` calls from that session until changed again.
- Legacy session records that contain `task_defaults` without an explicit session-override marker must be treated as inherited/global, not as an override. Maintainers debugging "I changed global depth but new tasks still use an old value" should check for this distinction first.
- The practical rule is:
  - global task-hall updates should affect later new tasks immediately;
  - explicit session overrides may intentionally diverge from the global default;
  - unscoped legacy `task_defaults` must not pin later task creation to stale values.

### Heartbeat Visible-Turn Contract

- Browser-side CEO websocket payloads may carry both `inflight_turn` and `preserved_turn`.
- `inflight_turn` is the current real running turn. For heartbeat this means the heartbeat turn itself, not the earlier user bubble that is being kept on screen temporarily.
- `preserved_turn` is a live-only carryover bubble that should remain visible until a later `ceo.turn.discard` closes it.
- `preserved_turn` only exists for an older bubble that has not yet been superseded by a persisted assistant transcript entry with the same `turn_id`. Once that assistant turn is durable history, the backend/frontend should stop surfacing the preserved copy.
- Frontend rendering should treat these as two separate bubbles. It must not reuse `preserved_turn.canonical_context` as the `Interaction Flow` for the current heartbeat bubble.
- Frontend trace fallback is only safe within the same rendered turn identity. Reusing the previous bubble's trace across `turn_id` or across `source=user -> heartbeat` is a contract bug.

### CEO Session List Interaction Contract

- The session list distinguishes "session switch is still settling" (`ceoSessionBusy`, a session-view readiness flag, not a general catalog lock) from "session catalog is being mutated" (`ceoSessionCatalogBusy`, covering create / rename / delete / bulk-delete checks).
- Catalog items always carry the shape of their own session family: `china:*` / `ext:*` keys are built by the channel-shaped builder (`session_family=channel`, `channel_id`, readonly/`can_message` flags) in both the REST catalog and global `ceo.sessions.snapshot` / `ceo.sessions.patch` pushes; only `web:*` keys go through the local-shaped builder with the generic summary fallback. Emitting a local-shaped item for a channel key makes the browser insert that channel session into the local web-session list momentarily.
- The persisted active session id survives page refresh whenever it names any valid session: a `web:` key with a transcript/artifact, a parseable `china:` key with a transcript, or an `ext:` key that has a registry entry or a transcript. Only unknown ids fall back to the most recent local session (and write that fallback back to the state store), so resolving an active `ext:` channel session as "invalid" is a contract bug.
- The browser fetches the REST session list only on page load; live catalog updates arrive as global `ceo.sessions.snapshot` websocket pushes. The `/ws/ceo` open sequence therefore sends `hello`, the session catalog, and `ceo.state` BEFORE `snapshot.ceo`: the transcript snapshot can be tens of megabytes on long channel sessions (canonical-context payloads), and the sidebar must never be queued behind it. Frontend envelope handling is order-independent, and any reconnect re-delivers the current catalog first.
- Bulk session delete-check and delete execution are backend-owned batch contracts (`POST /api/ceo/sessions/delete-check` and `POST /api/ceo/sessions/bulk-delete`, both with `session_ids` plus one shared `delete_task_records` flag). Each returns the per-session `results[]` and the refreshed session catalog (`items`, `channel_groups`, `active_session_id`) in one payload. The frontend does not loop per-session calls for a bulk action.
- During `ceoSessionBusy` alone, the left rail still allows `new session` and bulk-selection entry so operators are not trapped in a fully disabled sidebar, though composer send/pause may stay blocked; destructive or catalog-writing actions key off the stricter mutation-safe state.
- An expanded session card carries the title and the preview only. Session id and creation time are not card fields: they render as two read-only rows at the top of the `⋯` menu, before 命名 and 删除 (`.ceo-session-menu-info`), because they cost two lines of vertical space and one line of preview width each. The panel keeps its horizontal budget for text instead of chrome — 10px panel padding, 6px list right gutter, 12px card padding, and only the title row reserves 32px for the absolutely positioned `⋯` — so the preview line is as wide as the card while the menu button never overlaps text.
- Bulk selection exists only in the expanded panel: collapsing the rail clears `ceoBulkMode` plus the selection and re-renders the list, so no `.ceo-session-checkbox` node survives on the collapsed rail where cards render as glyph-only tiles. In bulk mode the checkbox owns the card's top-left corner and the unread badge relocates to the card's top-right corner (the per-card actions menu is hidden there). Any rule that hides expanded-only chrome while collapsed must cover the checkbox as well as `.ceo-session-actions`.
- Local session cards are drag-reorderable in both panel states, on the model-chain lane: `dragstart` / `dragover` / `drop` / `dragend` are delegated on `#ceo-session-list`, cards carry `draggable` plus `data-ceo-session-index`, and the insertion point is the vertical midpoint of the card under the pointer. A drop writes the whole visible id sequence to `S.ceoSessionOrder` and `g3ku.ui.ceo.session-order.v1`; `sortCeoSessionsByTime` ranks manual position first and only then `created_at` desc, so an unranked session (created after the last drag) surfaces above the pinned block. Because the array is otherwise sorted only on ingest, a drop re-sorts `S.ceoLocalSessions` itself before re-rendering. There is no server-side order field: the REST catalog still arrives in server order and only this browser remembers the manual sequence. Drag is disabled on the channel tab (items are grouped by channel type and have no flat index) and in bulk-select mode, where the card is a checkbox target.

If an operator reports "switching sessions makes the whole Leader sidebar unusable", inspect these frontend flags separately before changing button rules:

1. `ceoSessionBusy`
2. `ceoSessionCatalogBusy`
3. `ceoPauseBusy`
4. `ceoUploadBusy`

Do not treat `ceoSessionBusy` as equivalent to "all session-list mutations must be locked". That coupling is a UX regression for the Leader session rail.

### Channel Session Clear Contract

- In the CEO session UI, deleting a local session removes the session record itself; deleting a channel session is a clear operation — the channel/account entry remains available, but the next reopened conversation starts from empty session context.
- Batch-delete allows mixed local and channel selections in one request; result rows distinguish `deleted=true` local removals from `cleared=true` channel clears even though the refreshed catalog arrives as one post-mutation snapshot.
- Backend clear handling for channel sessions must remove the persisted `SessionManager` transcript for that channel session key (`ext:*`, or a legacy `china:*` archive), invalidate any in-memory cached session object, and clear the same side artifacts that local-session deletion clears: inflight snapshots, paused execution context, completed continuity sidecars, uploads, and frontdoor stage-archive artifacts.
- The registry entry for an external session survives clear (get-or-create stays idempotent); only the conversation context is wiped.

If an operator reports “the channel conversation was deleted but old context came back,” inspect these layers in order:

1. `DELETE /api/ceo/sessions/{session_id}` response payload for `cleared=true`
2. persisted channel transcript files (`sessions/ext_*.jsonl`, legacy `sessions/china_*.jsonl`) and in-memory `SessionManager` cache
3. inflight / paused CEO session artifacts
4. frontend snapshot cache only after the backend-owned state is confirmed cleared

### Heartbeat/Cron Visibility Versus Prompt Inheritance

- Browser-side CEO timeline rendering and inflight bubbles are allowed to show heartbeat / cron work as ordinary active turns.
- The same heartbeat / cron round is also durable prompt history, but visibility is split in two: prompt inheritance uses `prompt_visible`, while browser transcript/snapshot rendering uses `ui_visible`.
- Maintainers should not assume "frontend cannot see the hidden rule/event bundle" means "the model cannot see it later". The hidden rule/event messages are intentionally persisted for later prompt reuse while remaining absent from UI transcript surfaces.

The current rule is:

- UI may show heartbeat / cron stage openings, tool calls, execution trace, compression state, and visible assistant replies directly.
- The hidden heartbeat / cron rule and event-bundle messages must stay out of transcript lists, session preview text, session message counts, and `snapshot.ceo.messages` by way of `ui_visible=false`.
- Later turns inherit heartbeat / cron work from the authoritative continuity baseline plus prompt-visible history, not from a separate semantic-summary-only recovery lane.

## CEO Compression UI Contract

Context compression has one operator-facing surface: a rule inside the CEO feed that separates folded history from everything after it. It covers both the automatic send-time compression and the operator-triggered manual compression. See `runtime-overview.md`「Frontdoor Context Compression (Current Contract)」 for the runtime behavior; this section covers only what the operator sees and clicks.

- `compression_state` only means inline frontdoor `token_compression` progress. The frontend treats `status === "running"` as "context is being compressed right now" and infers no durable semantic-summary state from it.
- A running compression renders `上下文压缩中`, a finished one `会话已压缩`, an interrupted one `压缩已暂停`. All three are the same `.ceo-compression-divider` row and use the `#39c5bb` accent (`--ceo-context-compress-color`). The row is a text label between two thick hairlines that stop short of the feed edges; both sides take the same flex weight so the label is centered no matter how wide the feed or the session panel is. The running and paused states draw their own icon (a rotating ring with two vertical bars in the middle, sized in `em` off the label's font size) instead of a lucide glyph — a rotationally symmetric circle would spin invisibly. That ring is deliberately exempt from the stylesheet's global `prefers-reduced-motion` animation freeze: here the motion is the only "compression is still alive" signal, and operators on machines with animations switched off read a frozen ring as a stalled compression. The icon takes layout width, so the left hairline carries an equal transparent gap to keep the label itself on the center line. There is no separate composer toast — the feed rule replaced it.
- The running rule is live-only: it is appended while a compression is in flight and removed when it ends, and it is clickable — the ring-and-bars icon is a button that opens the shared in-page confirm dialog (`openConfirm`). Confirming calls `POST /api/ceo/sessions/{session_id}/compress-context/cancel`; cancelling the dialog changes nothing. The terminal rules are not clickable.
- Terminal states are durable: compression completion and interruption each append one `role="system"` transcript row carrying `metadata.kind = "context_compression"` plus `compression_state` (`completed` | `paused`) and `source` (`manual` | `auto`). `prompt_visible: False` keeps it out of the model's context and `ui_visible: True` keeps the snapshot emitting it, so a reopened session still shows where each compression happened. Automatic (send-time) compression writes the same row at transcript finalize, keyed to the turn that compressed, so one compression yields exactly one rule.
- The frontend learns a manual compression's terminal state by polling `GET /api/ceo/sessions/{session_id}/compress-context` until `status` leaves `running`, then reopens the session websocket so the persisted rule arrives with the transcript. A single failed poll must not end that tracking — the server can hold the loop busy for seconds while it rewrites a large transcript, and abandoning the poll would leave the running rule on screen until a full reload. Polling stops only after `CEO_COMPRESSION_POLL_FAIL_LIMIT` consecutive failures, and it re-arms when the user switches back to the still-compressing session.
- During a manual compression the browser owns the visible running state, because an out-of-turn compression has no inflight turn to hang it on. That state is *mirrored*, not invented: the server publishes it as a session-level `compression` object (`source = "manual_context_compression"`) on **both** `ceo.state` and `snapshot.ceo` (the latter comes from `_build_live_turn_payload`), and `adoptCeoContextCompression(sessionId, compression)` re-claims it into local tracking — the running rule reappears and polling re-arms. Recovery must not depend on which of the two messages arrives first, and it must not rely on the local `S.ceoContextCompression*` surviving, because a page reload wipes exactly that. Automatic compression keeps reading `inflight_turn.compression` and must not go through the manual adoption path.
- The running rule is a DOM node, not transcript data, so `resetCeoFeed()` deletes it on every full rebuild (`innerHTML = ""`). `renderCeoSnapshot` therefore re-asserts it via `syncCeoCompressionDivider()` *after* the rebuild but *before* `applyCeoFeedViewState()` — dropping that call re-creates the "refresh mid-compression and the indicator vanishes" bug, because `snapshot.ceo` always arrives after the `ceo.state` that first drew the line. The re-assert must not scroll when `S.ceoFeedFollowLatest === false`, or a user reading history gets yanked to the bottom on every rebuild.
- The compression task belongs to the runtime session, not to the connection: a websocket disconnect cancels only that connection's sender/stream tasks, so refreshing mid-compression does not stop it, and its terminal rule still lands in the transcript.
- Pausing the turn during an automatic compression still goes through the primary send/pause button and sends `client.pause_turn`; the backend cancels that compression and discards any late result.
- Tool-wait reminder labels from the reminder sidecar are live-only event data and must not render as transcript lines, assistant bubbles, or persistent notices.

### Manual Context Compression

- Pressing and holding the context-usage brain is a two-stage gesture: the first 200ms is a silent settle window (`CEO_BRAIN_HOLD_ARM_MS`) where nothing is drawn, so an ordinary click — or a hand tremor — never flashes progress it then cancels. After that window the progress travels the button's own edge: an SVG stroke around the control's rounded rect, started at the top and run clockwise, with `pathLength` normalizing the perimeter so `--ceo-brain-hold` 0→1 reads as a percentage of edge length rather than of angle. The browser calls `POST /api/ceo/sessions/{session_id}/compress-context` once a further `CEO_BRAIN_LONG_PRESS_MS` (2 seconds) has elapsed. Releasing early resets the bar and starts nothing; the click that follows a completed hold is swallowed so it cannot also open the model panel. Touch pointers never arm the hold. The bar's corner radius is the control tier's (`--ui-radius-control`), so the stroke stays on the button's border at every skin size.
- Hovering the brain shows `长按压缩上下文` below the icon and nothing else: hover must not brighten the icon's glow or lift it — that feedback belongs to the open panel only, and the hint chip is neutral rather than accent-tinted. This is the only hover text on the brain; usage figures still appear only inside the panel.
- The hold is refused, with a toast explaining why, only while an attachment upload is in flight or a compression already runs. Channel (`ext:` / `china:`) sessions are compressible too: the feed is read-only there, but a long channel history presses the same context window, and the durable baseline, continuity snapshot and actual-request artifact all already cover those keys. A channel key with no transcript is `session_not_found` rather than a silently created session, and the compression endpoints resolve channel runtime sessions without loading that (potentially tens-of-MB) transcript into the request handler.
- The endpoint never waits on the session: it records `running`, emits one state snapshot and returns. The detached task first pauses (`session.pause(manual=True)` — stops background tool executions and cancels in-flight requests) only when the session was running, then compresses. Keeping the pause out of the request body is a hard requirement, not an optimization: pausing and the terminal rule write both rewrite the whole transcript, and on the multi-tens-of-MB channel transcripts that exceeds the browser's request timeout, which would make the UI give up on a compression that later succeeds.
- A hold that finds nothing to compress (no compressible history, or a model without a usable context window) ends with `status: "not_needed"` and writes no transcript rule; the browser then says so in a toast instead of letting the running rule silently disappear. The same applies to `failed` (e.g. the session could not be paused), which carries the backend `reason`.

### Context Window Error UX

- If the estimated provider-bound request is already larger than the selected model's `context_window_tokens`, the frontend shows an error toast instead of attempting a semantic/global-summary fallback.
- The canonical message is `上下文大小超出当前模型<展示名>，请更改模型链配置后继续`.
- `<展示名>` is expected to come from the runtime-selected model's `provider_model`, with model `key` only as fallback.

### Composer Voice Input

The composer carries a mic button (`#ceo-voice-btn`, beside the attach button) that records locally, transcribes on the machine, and puts the text into the input box. The engine and its measured defaults are owned by `speech-to-text.md`; what this surface promises is the following.

- The button is a record/stop toggle and is always rendered: readiness is reported on click (with the exact `g3ku stt prepare` instruction) rather than by hiding the control, so a not-yet-provisioned install explains itself instead of looking broken. While recording it carries `aria-pressed="true"`, the `mic-off` glyph, and the `is-recording` class.
- **Readiness is asked before the microphone is granted.** `startCeoVoiceCapture` calls `ensureCeoVoiceEngine()` first (`GET /api/ceo/voice/status`): a box that is merely switched off gets that sentence and stops, while a box that is allowed but missing its ~157 MB starts the download in place (`POST /api/ceo/voice/prepare`, polled through the same status route) and only then opens the recorder. The reverse order would let the user speak a whole sentence before learning the model was never installed. The download runs as a single-flight background task server-side, so repeated clicks reuse it, and the toast quotes measured byte counts per stage instead of hiding behind a spinner.
- Two delivery modes, chosen by the 识别后自动发送 checkbox that appears above the input row while recording or transcribing (default on, persisted in `localStorage`):
  - **Auto send**: the text is sent immediately with the `用户语音，机器识别结果：` prefix and the user never gets a chance to edit it — which is exactly why the prefix is required here, and why this lane obeys the same contract as the channel voice lane (`speech-to-text.md`「提示词侧」). If the send lane refuses (session busy, read-only, no active session) the text stays in the composer instead of being swallowed.
  - **Manual**: the text is inserted **at the cursor** without any prefix, keeping both sides of the existing draft and replacing only the live selection. No prefix here on purpose: the user edits the result, and a "机器识别结果" label over human-corrected text would be a false statement to the model.
- Auto send is skipped when the composer already holds a draft. Silently sending text the user had not decided to send is worse than the extra click, so the result is inserted at the cursor and a toast says the auto send did not happen.
- Recording is resampled to 16 kHz mono WAV **in the browser** (`decodeAudioData` + `OfflineAudioContext`, then a hand-written WAV header), which is why this path needs no server-side decoder and why 60 s of audio fits the 2 MiB request cap.
- `POST /api/ceo/transcribe` answers `200` with an `{ok, text, error_code, error, seconds, wall_ms}` envelope for every outcome except an oversized body (`413 voice_too_large`). "No speech detected" is a valid result the composer renders, not a transport failure, so error branches must key off `error_code` and never off the HTTP status. The endpoint itself writes nothing anywhere — it is a pure transcription seam, and the `wav_bytes` the engine hands back are deliberately kept out of its JSON envelope.
- The recording nevertheless becomes a session attachment: only after a successful transcription does the composer upload the same 16 kHz WAV through the ordinary `/api/ceo/uploads` lane, which is what lets the sent message render as a replayable voice bubble. Upload failure is swallowed on purpose — the worst case degrades to a plain text bubble, which beats losing the recognized text. Where the bytes end up and for how long: `speech-to-text.md`「语音气泡与音频字段的存放」.
- The transcription runs off the event loop and is serialized by one global slot, so a long note cannot stall the live CEO websocket lane or overlap a second inference; a concurrent request waits and then receives `stt_busy`.
- `getUserMedia` requires a secure context. `http://127.0.0.1:<port>` works; opening the panel over `http://<lan-ip>` makes the browser refuse the microphone, and the toast says so explicitly.

### Composer Model Mode Panel

The context-usage brain is also the composer's model-and-context entry: clicking it (or Enter/Space on it) opens an upward panel above the composer. The panel leads with the model actually in use and its context numbers, then the `模型链` / `指定模型` choice, then the matching pane. There is no separate model-mode button beside the brain — the numbers live in the panel so they are not shown twice. The one hover text on the brain is the `长按压缩上下文` affordance hint (see `Manual Context Compression`).

- The headline is a single left-aligned pill carrying the display title of the model actually in use. Resolution order is `resolved_model_key` (the binding key the runtime selected for this request) first, then `provider_model`, each resolved against the managed catalog (`name` > `key` > `provider_model`), falling back to the session's pinned binding title, and to `等待 Leader 上下文预估` when neither is known. Binding key first is load-bearing: several bindings can carry the same provider-side model name, and a `provider_model`-only lookup resolves against whichever catalog entry happens to share that string, so the pill labels the wrong binding. The pill is muted (`is-pending`) while it shows a placeholder. Below it sit a ratio bar and an `estimated/total TOKEN` line rendered from the same estimate the brain uses (see `Composer Context Usage Meter`); the model name is never repeated under the bar, and that whole line is hidden when there is no estimate rather than echoing the placeholder a second time.
- Which mode is in effect is shown by the `模型链` / `指定模型` radio state, not by the headline pill.
- The open pane follows the mode actually in effect: a session pinned to a model opens on `指定模型`, a chain session opens on `模型链`, and a pinned state that arrives after opening switches the pane over. A manual pane choice wins for the rest of that opening; closing discards it.
- `模型链` pane: the `models.roles.ceo` chain from `GET /api/models`, one compact row per binding showing only its display title, with a drag handle. The list shows five rows before scrolling. Dragging only edits a local draft and reveals an `应用` button; the chain is written back through `PUT /api/models/roles/ceo` (name-only `model_keys` order, current iteration/concurrency limits preserved) only when `应用` is clicked. Closing the panel discards an unapplied draft.
- Choosing `模型链` while the session is pinned first shows an inline confirm row above the list (`当前会话固定使用 <展示名>，切换到模型链？`) with accept/cancel buttons; only accept sends the `chain` patch, cancel returns to the pinned pane. A session already on the chain switches panes without any confirm.
- `指定模型` pane: the managed binding catalog rendered by display title; disabled bindings render with a `已禁用` chip and are not selectable. It carries a search box filtering on display title, `key`, and `provider_model`.
- Reading and writing the session setting goes through `GET` / `PATCH /api/ceo/sessions/{session_id}/model-selection`. The payload is `{mode: "chain"}` or `{mode: "model", model_key: "<binding key>"}`; unknown keys return 404 `model_key_not_found`, disabled keys 409 `model_key_disabled`, model mode without a key 400 `model_key_required`.
- The setting is stored in the session's metadata (`model_selection`) and persists across restart. Local web sessions run through `normalize_ceo_metadata`; channel sessions (`ext:` / `china:`) are resolved from their session file and get the key added or removed without the web-CEO metadata normalization, so channel-owned metadata is left intact.
- `pinned_available: false` in the response means the pinned key no longer exists or is disabled. The panel then reports the effective mode (`模型链`, with the chain pane) and explains the automatic fallback in a note; the stored pin itself is kept so a re-enabled or re-created key restores the pin. Resolution semantics are owned by `config-and-models.md`「会话级固定模型优先于角色链」.
- Picking a model applies from the next turn: the browser sends nothing extra on `client.user_message`, the runtime resolves the pin when the turn starts. After a successful model switch or chain reorder the browser re-runs the composer usage estimate so the meter and headline reflect the new model's context window.

### Composer Context Usage Meter

- The Leader composer has a live-only context-size signal: a brain-shaped usage meter beside the attachment button (not a textarea border), always visible and clickable — it opens the model-and-context panel (see `Composer Model Mode Panel`). It is backend-driven with two authority lanes that maintainers must keep separate:
  - Idle/non-running sessions: the browser debounces composer edits and calls `POST /api/ceo/sessions/{session_id}/composer-preflight`, whose payload represents the next outbound user batch (existing queued follow-ups plus the current unsent draft/attachments, in FIFO order). An empty composer still calls it with no messages: with nothing pending, the preflight rebuilds the durable baseline itself, so a session that already has history keeps showing a real figure instead of dropping back to the placeholder. Only a session with no history at all is treated as having nothing to read, and only then may the meter show `等待 Leader 上下文预估`. The response carries the current model-facing estimate and thresholds: `estimated_total_tokens`, `context_window_tokens`, `ratio`, `provider_model`, `resolved_model_key`, `trigger_tokens`, `would_trigger_token_compression`, `would_exceed_context_window`. For multimodal drafts the estimate derives image cost from a dedicated image-token heuristic plus text/schema cost — never from the raw `data:image/*;base64` string length, so a large inline data URL must not inflate into millions of text tokens. The figure shown here is the same send preflight the runtime uses, so it is usage-first by the same contract (see `runtime-overview.md`「Frontdoor Context Compression」): the last provider call's effective input plus an estimate of the newly added content, with the full preview estimate only as the fallback when no comparable usage truth exists. A meter that reads consistently lower than the last request's real input size means the comparison fell back to preview — debug the append-only comparison, not the estimator (详见 `context-and-cache-troubleshooting.md`「同 turn 的 append-only 规则被破坏」). The preflight only reads the session's own baseline, so it is not gated by the read-only flag: a channel (`ext:` / `china:`) session gets a figure the same way, and must not be answered with `channel_session_readonly` — a read-only feed is not a reason for the meter to sit empty.
  - Running sessions: composer-preflight stops being authoritative and is not called. The valid source is the current `snapshot.ceo` / `ceo.turn.patch` inflight diagnostics — `frontdoor_token_preflight_diagnostics.final_request_tokens`, `.max_context_tokens`, `.provider_model`, `.resolved_model_key`. The visible meter during a running turn means "the actual next provider-bound request the runtime is about to send", not "draft if sent now"; issuing a fresh browser-side estimate during a running turn is a contract bug. Retention is the exception and is required: between turn start and the first runtime diagnostics, `ceoCurrentUsageEstimate()` keeps displaying the last known reading instead of blanking to `等待 Leader 上下文预估` — a meter that drops to the placeholder every time the model is called reads as "context was cleared". Any runtime value wins over the retained one the moment it arrives.
- The icon's color is a live-activity signal, not a static gauge: `--ceo-context-usage-color` carries the ratio-driven green→red hue only while the session is in progress (`S.ceoTurnActive` or an active compression, manual or in-turn). An idle session renders the brain in `var(--text-muted)` — a saturated green sitting on a session that is doing nothing gets misread as ongoing consumption. Greying the color does not grey the meter: the fill height, the panel numbers and the `aria-label` all keep reflecting the ratio.
- With no data the shell keeps its faint glow while the colored fill stays `height 0` until an estimate arrives ("always lit" refers to the shell, not a fabricated fill). The shell keeps an `aria-label` of `model · estimated/total TOKEN`, where the model part is the same display title the panel pill resolves (see `Composer Model Mode Panel`) and not the raw `provider_model` (`等待 Leader 上下文预估` only when there is no reading at all) and no native `title`; the same numbers are surfaced once, in the panel. Hovering shows only the `长按压缩上下文` affordance hint, and a completed hold opens nothing: its edge progress bar reaching full is what fires the compression request (see `Manual Context Compression`).
- The brain meter is live-only UI state: it animates with the current ratio, clamps visual fill when the raw ratio exceeds `1.0`, and never creates transcript messages, assistant bubbles, or persisted snapshot entries.
- If the meter disagrees with real send-time compression/error behavior, first check whether the browser is in the idle preflight lane or the running snapshot lane, then debug the corresponding backend source. The runtime's additive image-estimation fields (`estimated_image_tokens`, `image_estimation_method`) are observability only and do not change the persisted transcript contract.

## Tool Admin RBAC Contract

Tool management uses a strict persisted-RBAC contract for surfaced tool families. See `tool-and-skill-system.md`「Tool Admin RBAC」 for the backend semantics: policy seeding, empty-list preservation and one-time repair, the `监管模式` approval switch, and `exec_runtime` execution mode.

The frontend responsibilities are:

- reflect the backend-owned `allowed_roles` exactly,
- allow all surfaced action role toggles to be unchecked,
- avoid special-casing CEO for surfaced core tool families,
- and show a clear operator-visible hint when an action is currently disabled for all roles.

The Skill and Tool detail drawers share one save rule: edits persist only when the operator clicks the `保存` button beside `关闭`, which fires the same policy/file write the toolbar save used to. There is no autosave or debounce, and closing the drawer discards uncommitted edits. New maintainers often misread the draft hint (`有未保存的修改`) as an autosave indicator — it only marks dirty state that a `保存` click must commit.

If an operator reports "save succeeded but reopen restored the roles", first inspect:

1. the Tool Admin save payload,
2. the stored `tool_families.payload_json` row for that surfaced family,
3. the post-reload `GET /api/resources/tools/{tool_id}` response.

Do not start with frontdoor prompt debugging unless those three layers already agree.

If an operator reports "Tool 管理 shows one role set but runtime visibility behaves differently", inspect in this order:

1. `GET /api/resources/tools/{tool_id}`
2. the stored `tool_families.payload_json` row
3. the derived `role_policy_matrix`
4. the runtime-side `list_effective_tool_names(...)` result for the affected role/session

Do not assume the browser has a second hidden RBAC source. For surfaced tool families, the API detail payload and runtime visibility are two views over the same backend-owned family/action state.

## Container Deployment Contract

The web/admin stack has an explicit container-safe startup mode.

- `g3ku web --no-worker` is the container-safe web entrypoint.
- In this mode, the web process still owns FastAPI routes, websocket session/runtime integration, heartbeat startup, and cron startup.
- Detached task execution is expected to come from a separate `g3ku worker` process or container rather than from the web-managed local child worker path.

The default local (non-`--no-worker`) path runs a web-managed task worker with auto-restart supervision; its lease/heartbeat/stale semantics and troubleshooting are owned by `operations-and-maintenance.md`「托管 worker 看门狗」.

`/api/bootstrap/status` is also the preferred healthcheck-friendly read endpoint for the web container:

- it is available even when the project is still locked
- it reports both bootstrap mode and runtime readiness
- Compose healthchecks should use it instead of inventing a second ad-hoc web-only route

There is also a new mutable-resource startup boundary maintainers should keep in mind:

- container images may ship immutable baseline `skills/` and `tools/`
- runtime startup may seed missing baseline files into the mutable workspace copy
- that seed path must be missing-file-only and must not overwrite operator edits already present in the shared workspace volume

If operators report "the image has the new built-in skill/tool but the running project still shows the old workspace copy", debug the persistent `skills/` / `tools/` volume contents first. In container mode, the mounted workspace copy is authoritative after startup.

## Heartbeat/Cron ACK Contract

The browser handles a dedicated live-only ACK event for internal turns that called `silent`.

- `ceo.internal.ack` is emitted when a heartbeat or cron turn ends by calling the `silent` tool; detection reads the `silent_reply` flag on `message_end`, never the reply text. It is not a normal assistant reply and must not reuse `ceo.reply.final` persistence or rendering rules.
- The frontend renders the ACK as a distinct non-conversational bubble so operators can see the internal turn was received and intentionally stayed silent.
- That ACK bubble is ephemeral: it is not appended to the CEO session snapshot `messages` list and disappears on full refresh.
- Heartbeat `task_terminal` turns do not reach the browser as `ceo.internal.ack`; `ceo.turn.discard` still only closes a specific visible pending turn by `turn_id`.
- Non-silent heartbeat/cron assistant replies use the ordinary `message_end -> ceo.reply.final` path.

### CEO Turn Silent Reply Contract

A turn that calls `silent` is visible in the session box as one collapsed line, not as an absent turn.

- `ceo.reply.final` carries the real reply text plus `silent_reply: true` and `silent_reason`; the backend no longer blanks the text on its way out. Delivery suppression is the flag's job, and the channel/cron lanes read the same flag, so the web surface and the channel surface stay consistent.
- The whole response collapses into one slim line, `静默消息 HH:MM:SS` with a caret (the label falls back to bare `静默消息` when no completion time is available). That line is a direct child of the turn element, **outside** `.msg-content`, so a collapsed silent turn shows no bubble at all — not a bubble containing one line. Expanding reveals the reply text, stage rail, tool steps and usage as on a delivered turn.
- The `silent` call itself is never rendered as a step: `applyCeoToolEventToTurn` drops the live event and `filterCeoInteractionFlowSummary` drops it from every round before the rail is rebuilt (a round left with no other tool disappears with it). Showing "模型调用了 silent" adds no information once the fold line already says the turn was silent, and while the tool was unresolvable it read as a task error.
- Collapse is CSS-only: `renderCeoSilentTurn` adds `ceo-silent-message` to the turn element and the caret toggles `ceo-silent-expanded`; `.ceo-silent-message:not(.ceo-silent-expanded) > :not(.ceo-silent-line) { display: none }` hides the bubble. Nothing is moved in the DOM and `assistant-text` keeps `hidden = false`, so the fold never fights the loading-state classes.
- The turn element is a flex **row** by default (and `[data-ui-version="v2"] .message` adds `align-items: flex-end`), so the silent rule must also set `flex-direction: column; align-items: stretch` — without it the fold line lands beside the bubble and squeezes the content right. The V2 selector has to be repeated in the rule: a bare class loses to `[data-ui-version="v2"] .message` on specificity.
- There is no separate reason row. For a tool-silenced turn the reply body already *is* the reason (finalize keeps `accompanying_text or reason`), so a second line duplicated it. The reason stays on the transcript row as `silent_reason` for audit.
- The line is created once and held on the turn object (`silentLineEl`), because a turn renders live and then finalizes; it is assembled with DOM nodes and `textContent` — this frontend has no HTML-escaping helper, so interpolating model text into `innerHTML` would open an injection path.
- `renderPersistedCeoAssistantTurn` must pass `silent_reason` into its trailing `finalizeCeoTurn` call: finalize rewrites the cached row from `meta`, and a missing reason there blanks that row's `silent_reason` on refresh.
- A visible turn that ends with no text at all is silent too and renders the same line with a runtime-authored reason and nothing to expand (contract: `runtime-overview.md`「3.3 静默回复（`silent` 工具）」). Such a turn used to surface an English "no visible reply was generated" sentence as an ordinary reply.
- Snapshot rows keep their content for the same reason, so a refresh rebuilds the same collapsed line.
- A silent row with no stage track still renders: the collapsed line is itself displayable content. Dropping track-less silent rows was correct only while the backend also emptied their text.
- `finalizeCeoTurn` and `renderPersistedCeoAssistantTurn` are the two render entry points; both branch on `silent_reply`, and the stage rail, tool steps, usage line and completion timestamp are finalized exactly as on a delivered turn.

## CEO Live Tool Reminder Contract

The CEO browser/runtime integration has a second live-only status lane for long-running direct tools: `ceo.tool.reminder`. It is intentionally different from both ordinary tool interaction steps and heartbeat turns.

- Backend reminder events are emitted only as websocket live events; the payload carries `turn_id`, `execution_id`, `tool_name`, `elapsed_seconds`, `reminder_count`, `decision`, `label`, `source="reminder"`, `next_check_in_seconds` (the self-scheduled interval until the next patrol), and an optional `terminal`.
- The frontend must not create a new assistant bubble and must not append a new interaction step for reminder events. The CEO frontend does not render `label` as a visible reminder block under the pending turn; these events stay live-only bookkeeping signals while the authoritative tool outcome arrives through the ordinary tool/error/final-reply path.

### Persistence Rules

- Reminder events are not part of `snapshot.ceo.messages` and must not be persisted into the transcript-backed CEO message list.
- Refresh/reconnect should not restore an old reminder from cached snapshot state.
- Any ephemeral reminder state is cleared when the tool finishes, the turn finalizes, the turn is discarded, or a `terminal=true` reminder event arrives.

See `heartbeat-system.md`「CEO Inline Tool Reminder Sidecar」 for the self-scheduled patrol and decision semantics (`decision=continue` / `stop` / `unavailable`, observation-aware sidecar review, tool-call-scoped timeout-stop); the universal tool timeout deadline the patrol runs within is owned by `tool-and-skill-system.md`「统一工具 Timeout 合同」.

Operators should treat `ceo.tool.reminder` as a live runtime signal, not durable conversation UI; the authoritative end state still arrives through the normal CEO tool/error/final-reply events.

## Update Notification And Restart-And-Upgrade Contract

This surface tells an installed device that a newer release tag exists and lets the operator apply it from the browser. It owns the web-side reading of one file: the update ledger written by the periodic release-tag check (polling cadence and the check channel are owned by `operations-and-maintenance.md`「新设备首次安装与升级」).

**Endpoints** (`main/api/update_rest.py`, mounted under `/api`):

- `GET /api/update/status` — reads the ledger only. It never touches the network, so the 30s UI poll costs nothing and an offline device keeps answering from the last known result.
- `POST /api/update/check` — one forced manual check (`source=manual`), bypassing the interval gate.
- `POST /api/update/apply` — spawns the detached upgrade runner and returns. It performs no shutdown itself.

**The tri-state invariant.** `has_ledger=false` means "never checked", `error` non-empty means "checked and failed", and `newer=true` is the only state that may light anything. Rendering the first two as "up to date" — or as a red dot — is the failure mode this contract exists to prevent, because it makes an offline device indistinguishable from a current one. The settings line therefore has four distinct texts (never checked / last check failed / newer available / up to date), and the sidebar dot plus the 「重启并更新」 button stay hidden unless `newer` is true.

**Where it lives in the UI.** The dot (`#update-nav-dot`) is a static span inside `#project-settings-btn`, absolutely positioned at the button's top-left corner; that button needs `position: relative` to be its containing block, otherwise the dot anchors to an outer container. The panel row reuses the existing `project-settings-actions` shape (button + one status line), and the poll rides the audit badge's existing 30s interval instead of adding a timer.

**Unlock boundary.** All three endpoints sit behind the `423 project_locked` guard like any other `/api/*` route. A locked project shows no dot and issues no remote request: the check loop only starts once the web runtime bus exists.

**Apply is user-initiated, once.** The button posts, the runner stops the service through the existing `POST /api/bootstrap/exit` (so "running work needs confirmation" has exactly one implementation), waits for the port to be released, upgrades the checkout, then relaunches. If the upgrade fails it relaunches the previous version rather than leaving the device without a service — the sequence and its rationale (an interpreter must never import source mid-replacement) are in `operations-and-maintenance.md`「新设备首次安装与升级」.
