# Negi Heartbeat System

This document describes the maintenance boundary around the Web CEO heartbeat path.

## Responsibilities

- Heartbeat is the session-owned internal turn mechanism for work that must wake an existing CEO session without a new visible user message; typical inputs are a task's terminal result, a task stall notice, an error-paused node, a failed or degraded message distribution, and the shutdown-resume wake.
- Heartbeat runs through `RuntimeAgentSession.prompt(...)` as an internal turn with its own source metadata and rules.

## What Heartbeat Owns

- Internal wake/enqueue/scheduling behavior for existing CEO sessions.
- Session-visible internal turns that may end in `ceo.internal.ack`, `ceo.reply.final`, or `ceo.turn.discard`.
- The repair/fallback path for task-terminal cases that must produce a user-visible reply rather than calling `silent`.
- The maintenance boundary between live UI state and durable transcript history for internal turns.

## Continuation Contract

- Heartbeat and cron are assembled through the session-owned `frontdoor_request_body_messages` / actual-request scaffold used by the next visible CEO turn, not a separate short `ceo_heartbeat` request lane.
- Each internal activation resumes from that same scaffold.
- When the authoritative frontdoor baseline already carries prior contract state, heartbeat and cron inherit the previous callable/candidate/hydrated/provider-tool/visible-skill state instead of rerunning tool or skill selection.
- If no authoritative frontdoor baseline exists yet, internal turns fall back to the ordinary CEO/frontdoor exposure assembly path for that round.
- Recovery of that baseline follows one strict restore order before a heartbeat turn runs: paused snapshot, then inflight snapshot, then completed continuity sidecar, then latest actual-request artifact. A stale sidecar lacking `frontdoor_request_body_messages` does not block recovery from a richer later source.
- Heartbeat appends two hidden durable `user` messages before the model call: a rule message and an event-bundle message. The rule text lives only in the rule message; the bundle message carries the `[SESSION EVENTS]` bundle alone, so the rules text is never duplicated into the user turn. Wire roles: `context-and-cache-troubleshooting.md`「线体角色合同」.
- A rule row (`internal_prompt_kind` = `heartbeat_rule` / `cron_rule`) is never the turn's user content. Every check that asks "is the current user message already the last record" first skips rule rows via `web_ceo_sessions.trailing_turn_record`; without the skip an appended rule looks like a trailing user turn, the bundle stops being appended, and the model runs the heartbeat without the event that triggered it. Bundle rows (`heartbeat_event_bundle` / `cron_event_bundle`) do represent the current turn, so a same-turn re-dispatch is still deduplicated by them.

### Internal-turn time anchors

- Internal injections carry the moment they were assembled, as pre-converted local wall-clock time (UTC offset + weekday, via `g3ku/core/timefmt.py`) — the runtime cannot know what time it will be when the model reads the block. The on-demand source is the resident `time` tool (contract owner: `tool-and-skill-system.md`「fixed builtin tools」); it needs no `load_tool_context`, and both lanes share one clock implementation (`g3ku/runtime/wake_clock.py`). The event bundle header carries the wakeup moment right after the `[SESSION EVENTS]` / `## EVENT BUNDLE` markers (markers stay first — compaction and startswith detection depend on them). The cron rule message carries the delivery moment plus an instruction to read dates from these fields instead of mentally converting epoch milliseconds. The cron event block keeps the raw `*_ms` fields and adds converted `delivered_at_local` / `scheduled_run_at_local` / `last_delivered_at_local` siblings; dispatch metadata `cron_delivered_at_ms` is the single delivery-time source shared by the live seed and the persisted transcript, so both render identical text.
- Timestamps are never backfilled into older rows: a row keeps the moment it was created with, and request-side time decoration is derived only from that stored field (invariant and the two regression paths: `context-and-cache-troubleshooting.md`「用户消息时间装饰破坏前缀稳定或相等性去重」, contract owner `runtime-overview.md`「用户消息时间锚点」).
- Cron appends two hidden durable `user` messages:
  - a cron rule message
  - a structured cron event block
- Those internal prompt messages must be persisted with `prompt_visible=true`, `ui_visible=false`, and an `internal_prompt_kind` that distinguishes heartbeat vs cron rule/event records.
- Because the request is append-only against the previous authoritative scaffold, heartbeat/cron share the same prompt-cache family, token-preflight, token-compression, and continuity rules as ordinary CEO/frontdoor turns.
- A turn that stays silent does so by calling the `silent` tool; there is no silent-reply sentinel string. The tool signal is what suppresses channel delivery, and the turn still leaves a durable, prompt-visible assistant row carrying its text — the session model is the only party that can judge whether a delivered result is still worth sending, so it must be able to see its own previous decision. Contract owner: `runtime-overview.md`「3.3 静默回复（`silent` 工具）」.

## Persistence And UI Boundary

- Hidden heartbeat/cron rule + event-bundle messages are durable prompt history. They participate in later prompt assembly, request artifacts, completed continuity sidecars, and compression just like any other prompt-visible message.
- A failed internal turn's rule + event-bundle messages are flipped to `_transcript_state=discarded` (matched by turn id + `internal_prompt_kind`) and excluded from replay; the jsonl rows are kept for audit. Duplicate still-visible internal prompts are folded at context-build time. Both keep a quota-dead or chatty heartbeat from stacking duplicate rules/bundles into every later request body — mechanism and forensics in `context-and-cache-troubleshooting.md`「heartbeat / cron 上下文残骸」.
- Transcript views, session preview text, message counts, and `snapshot.ceo.messages` hide internal prompt messages by filtering `ui_visible=false` — never by assuming internal turns are transcript-hidden.
- Heartbeat/cron assistant replies, tool calls, tool results, and turn/compression traces remain ordinary visible turn output; a turn that sends nothing to the user does so by calling `silent`, and its own row stays visible in both the transcript and the session box as a collapsed entry.
- Internal turns get the same live reasoning row as user turns, because an xhigh heartbeat turn can spend most of its decoding on invisible thinking. That row is display-only: the inflight snapshot carries one bounded tail line plus scalars, and the thinking text itself is never persisted on any internal lane — the durable side of an internal turn stays exactly the rule/event-bundle rows described above (`web-and-admin.md`「Live Reasoning Row Contract」).
- Manual pause during a running heartbeat/cron turn goes through the ordinary `client.pause_turn` path; the backend treats that internal turn as the current active turn, not a side lane.
- Maintenance boundary: an internal heartbeat/cron request artifact may be authoritative for billing and forensics without replacing the session-owned baseline. If the new durable body is mostly heartbeat rule/event text and poorer than the existing baseline without a `token_compression` explanation, the runtime keeps the richer baseline instead of promoting the internal-only body into completed continuity.

## Cron Reminder Contract

- Cron is a structured reminder mechanism for the future agent, not a natural-language stop-condition engine; a cron `message` is the reminder instruction for that future agent, not a ready-to-send user reply.
- Cron-internal and heartbeat-internal turns are not an internal-only tool lane: they reuse the ordinary CEO/frontdoor tool exposure for the current role (inheriting prior contract state when present).
- Node-pause (`task_node_error`) heartbeat turns inherit the same callable set as any other internal turn; there is no separate first-tool allowance, because no tool carries a stage precondition.
- The prompt-side cron rule is intentionally minimal: the reminder is an internal instruction, not a new user message, to be executed immediately.
- The runtime does not hard-code a prompt-side ban on cron-tool mutations during reminder turns: if the reminded work itself is a currently visible CEO action (e.g. sending a reminder, creating another cron), the model may use the ordinary CEO tool surface — with `cron(remove)` limited to the firing job itself (合同见 `tool-and-skill-system.md`「`cron` 工具合同」).
- Repetition is enforced by service-side counters (`payload.max_runs` / `state.delivered_runs`): a reminder only counts as delivered after the internal prompt is durably accepted by the runtime/session path; when `delivered_runs >= max_runs`, the service removes the job and schedules no further wakeup.
- One-shot `at` reminders are validated against the service clock at creation: a target timestamp already in the past when `add_job()` runs is rejected immediately (the error quotes service-local time and directs immediate execution or abandonment) instead of storing a dormant expired job.
- One-shot `at` creation is guarded against duplicate registration: `add_job()` rejects a new `at` job when an enabled job already exists for the same `(session_key, at_ms)` pair, returning `同一会话在 <time> 已存在一次性提醒 (id: …)，请勿重复创建；如需修改请先用 remove 删除旧任务，或改用其他时间`. The match is structural, not text-based, so reworded re-adds within one turn are caught. Disabled jobs never block a fresh registration; recurring schedules are exempt.
- The CEO-facing `schedule_wake` tool is a second producer of one-shot `at` jobs, and it inherits every guarantee above rather than adding a timer of its own: durable store, self-healing re-arm, at-most-once delivery, and the same restart suppression (a wake-up claimed but not finalized before a restart does not fire again — a duplicate alarm is worse than a missed one, exactly as for reminders). Two things distinguish this family: the delivery body is prefixed `Self wake-up you armed earlier:` followed by the model's own `note`, so an internal turn can tell its own clock from an operator's reminder; and the job `name` carries the `self-wake: ` prefix, which is what re-arming matches on when it retires the session's own still-pending wake-up before creating the new one. That retire-first order is load-bearing twice: without it a session that arms a wake-up every few minutes accumulates one job per arm, and a re-arm onto the same instant would be rejected by the duplicate-registration gate above. Nothing outside the prefix is ever retired, so operator-authored reminders are not reachable from this lane. When the scheduler is absent (CLI-started session, cron disabled) the tool returns `wake_scheduler_unavailable` instead of reporting an armed wake-up that can never fire. Tool-side contract: `tool-and-skill-system.md`「fixed builtin tools」; the node lane uses a different backend (`main-task-runtime.md`「节点信箱与唤醒»).
- If an old cron store uses the previous schema version, the runtime drops those jobs instead of attempting migration; maintainers should treat this as an intentional semantic reset.

Cron job delivery is claim-before-dispatch with a self-finalizing dispatch — the restart/recovery guarantee and the live-process finalize guarantee are one contract:

- Before invoking a job handler, the cron service persists a run claim to `.g3ku/cron/jobs.json` (`state.last_run_at_ms` set, `state.last_status = "running"`). Because `_recompute_next_runs()` never re-arms an `at` job whose `last_run_at_ms` is already set, a one-shot reminder is **at-most-once across restarts**: a crash mid-dispatch cannot re-trigger it.
- Store writes are atomic (temp-file + replace). A crash mid-write cannot truncate `jobs.json`; a truncated store would be read back as corrupt and reset, which would silently drop claims and re-arm already-dispatched jobs.
- Every dispatch runs as an independent asyncio task and is finalized on **every** exit path, so the store never stays in `running` while the process lives (`interrupted` is the live-process equivalent of the startup `interrupted` reconciliation):
  - handler returns → `ok`, `delivered_runs` advances, terminal `max_runs` removal applies;
  - handler raises → `error` (one-shot `at` retries after 60s, recurring recomputes its schedule);
  - cancellation (service `stop()`, shutdown) → `interrupted`; the inner handler task is cancelled too.
  There is **no scheduler-level total-duration budget**: a handler that never returns keeps its run in-flight until the process exits, and the next startup reconciliation marks it `interrupted`. The only deadlines are the provider attempt timeout and the turn's own tool/job timeouts; the `cron` config section exposes no dispatch-timeout knob.
  Unfinished one-shot `at` dispatches (`interrupted`) follow the same at-most-once suppression as the restart case: `next_run` cleared and the job disabled — the dispatch may already have reached the downstream handler, and a duplicate reminder is worse than a missed one.
- One wedged dispatch can never pin the scheduler: the timer tick claims due jobs synchronously, spawns their dispatch tasks, and always re-arms in a `finally`. In-flight jobs are excluded from wake arithmetic (their stale past `next_run` would otherwise spin a zero-delay tick loop); each finalize re-arms the timer to pick up its job's freshly advanced schedule. A tick task that dies unexpectedly logs `Cron: timer task died unexpectedly` and self-heals with a delayed re-arm — the scheduler never goes silent without a greppable trace.
- On startup, any job still marked `running` is a run claimed but never finalized (restart happened between claim and finalize). The service reconciles these into `last_status = "interrupted"`: one-shot `at` jobs are suppressed — disabled, not re-dispatched — because a duplicate reminder is worse than a missed one and the original dispatch may already have reached the downstream handler; recurring jobs simply resume their schedule. New-maintainer caveat: a one-shot reminder that never fires after a restart usually shows this `interrupted` / `running` store state — the *expected* at-most-once outcome, not a scheduler bug, and must not be "fixed" by re-arming a duplicate job.
- An in-flight guard per job id also prevents an overlapping timer tick and a manual `run_job` for the same job from producing a second concurrent dispatch.
- Hang forensics chain (two complementary instruments): the bridge slow-prompt watchdog warns with the live await chain when any `SessionRuntimeBridge.prompt` exceeds `G3KU_SLOW_PROMPT_WATCHDOG_SECONDS` (default 900s); the session finalize-tail profiler (`turn finalize tail slow ...` warning) attributes slow-but-completed tails to a stage (transcript persistence / memory-review bookkeeping / terminal emits). A cron dispatch that never returns has no scheduler-level kill: it stays in-flight until the process exits, and the next startup reconciliation marks it `interrupted`.

## Proactive Message Throttle

- **Scope**: `ext:` sessions only. The external-session registry stores `last_proactive_at`;
  the shared outbound drain updates it when it publishes an `outbound.created` notice
  (heartbeat / cron / task terminal / mention). Ordinary turn replies do not travel that
  bus lane and therefore do not reset the window; `source="outbox_replay"` is a redelivery
  and is skipped.
- **Gate**: `_build_web_cron_service` injects `admit_proactive` into `CronService`. Before
  a due job is claimed, the callback checks the session's last proactive timestamp; if it
  is less than 60 seconds old, the job is deferred to the end of the window and left
  unclaimed. This ordering is load-bearing: claiming a one-shot `at` job before deferring
  would suppress it forever.
- **Deferral record**: `CronJobState` stores `delayed_from_ms` / `delayed_until_ms` /
  `delay_reason` and `last_status="deferred"`; the eventual dispatch carries
  `cron_delay_reason` / `cron_delayed_seconds` into the cron rule and event bundle, so the
  model sees why it woke late. Fields are cleared at finalize.
- **No extra caps**: there is no per-session job count, minimum recurring interval, or
  max-runs cap beyond the existing `max_runs` semantics. The 60-second window is the rate
  limit; manual `run_job` bypasses it as an explicit operator action.
- **Availability**: `cron` / `schedule_wake` are in the limited/jailed tool surface
  (scheduling is not task dispatch); `create_async_task` / `send_message` / `task_*`
  remain denied in restricted tiers.
- **Platform ceiling**: a group without the QQ “主动推送消息能力” permission still wakes
  the session, but the proactive message is rejected by the bridge as `active_denied` and
  is recorded as undeliverable; the throttle does not change that.
- **Delivery-failure wake**: the bridge ack carries `kind` / `shape` / `passive_window_open`
  / `text_preview`; the ack route records the capability on the external session registry
  and enqueues a `delivery_failure` heartbeat event. Dedupe is by `outbox_id` only — every
  distinct failed message wakes the model, with no time cooldown. The event bundle tells
  the model not to retry the original message, to use `mention_member` only when a passive
  window is open, and otherwise to call `silent`. A turn whose events are all
  `delivery_failure` does not notify the channel at all; the model's text stays in the web
  transcript. This prevents a failure notification from generating another failing
  proactive reply.

## Task Terminal Repair Contract

- Task-terminal heartbeat only repairs or produces the session reply for an existing terminal event; it never auto-runs `continue_task`, creates replacement tasks, or retries failed tasks in place.
- If a task still needs more work after terminalization, that must come from a later explicit frontdoor/user decision, typically via `create_async_task`.
- Task-terminal callback persistence and heartbeat queueing have separate duplicate boundaries: the outbox row is the durable callback boundary, and the heartbeat event queue only dedupes currently enqueued in-memory events.
- Both boundaries key on the canonical dedupe key `task-terminal:{task_id}:{status}:{finished_at}`. `normalize_task_terminal_payload` always recomputes this key server-side and ignores any caller-supplied `dedupe_key`/`dedupeKey`; probe/retry key variants cannot bypass exact-key dedupe. Do not reintroduce caller-controlled dedupe keys.
- The queue carries two dedupe layers: `_dedupe` for events still queued and `_consumed` for events already injected. `/api/internal/task-terminal` additionally rejects a repeated callback when the same outbox row is already `accepted=true` (even if `delivery_state` is not yet `delivered`), and the session's injected event-bundle metadata is the durable guard across restart. Debugging "same failed task spawned two heartbeat replies": inspect the outbox row and the session's `heartbeat_event_dedupe_keys` before blaming prompt behavior.
- A node row rewritten after terminalization re-opens the task: `refresh_task_view` derives status from the current node rows with no terminal-sticky rule, so `task.terminal` can publish twice for the same task. `finished_at` is written once on the first terminal transition and preserved, and the canonical `task-terminal:{task_id}:{status}:{finished_at}` key makes the second event a duplicate — the outbox row already exists, `/api/internal/task-terminal` rejects it (`already_accepted` / `already_delivered`), and the session-level `handled_terminal_dedupe_keys` guard suppresses a second reply.
- Terminal-event delivery durability: the worker posts the callback with a short retry ladder and a per-attempt timeout shared with the stall and distribution-error lanes (5s — the web process also serves model probes and SQLite write traffic, and a tighter bound turns a busy moment into a lost event). When the ladder exhausts, the row stays pending and is re-driven on the same 60-second reconciliation tick that re-arms distribution drivers, so a failed delivery self-heals within a minute instead of waiting for a process restart. Past that attempt ceiling the row becomes `abandoned`: it leaves the pending query, keeps `attempts` and `last_error` for forensics, and is never silently deleted.
- Pending selection is `delivery_state = 'pending'`, never "not delivered". A row rejected at enqueue (`invalid_payload`, `duplicate_event`) keeps `accepted=false` and must not be re-driven forever by that tick. `mark_task_terminal_outbox_delivered` is written at **injection**, not at reply persistence: `delivered` means the event bundle reached the session context, and a model failure after injection does not reopen the row. `attempts` / `last_attempt_at` / `last_error` still describe the worker→web callback lane, not the heartbeat turn. The transition preserves `last_error`, so "delivered late after repeated failures" stays visible to an investigator.
- Staleness is not a delivery gate: an old pending terminal event is still handed to the model, which decides whether to report it. Suppressing or dropping stale events at the machine layer withholds results the user may still be waiting for, which is the heavier failure than a redundant message.
- Debugging "the session answered about an hours-old result right after startup": a stranded `task_terminal_outbox` row is being replayed. Compare `created_at` with `delivered_at`, and read `attempts` / `last_attempt_at` / `last_error`.
- Session-level injection dedupe: heartbeat records the `dedupe_key` of every `task_terminal` event **when its event bundle is injected into the context** into `session.metadata["handled_terminal_dedupe_keys"]` (bounded, string-only, de-duplicated). A later delivery of the same key is consumed silently (`consume_many` + `mark_task_terminal_outbox_delivered`) without running the agent or re-publishing `ceo.reply.final` — guarding the crash window between injection and queue-pop/outbox-ack, and a restart replay. A visible reply is not a prerequisite: a model failure after injection leaves the key in place.
- The heartbeat final event (`ceo.reply.final`) carries the same `turns` payload as the user-lane relay: the completed turn's `turns[]` (narration + tool records) appears on the transcript row and in the reply payload, and an empty ledger omits it so the browser renders a plain reply bubble rather than resurrecting older rails.
- The task-terminal event payload has two result lanes: `terminal_*` describes the true terminal node (when final acceptance fails this stays the acceptance-node result), and `root_output` / `root_output_ref` carries the root execution deliverable so the full root-node output reaches the main agent even when the terminal node is `acceptance`. A third lane `user_node_supplements` carries the 定向通知 the user appended to task nodes during the run (`[{node_id, node_title, message, epoch_id, created_at, epoch_state}]`, derived from message-distribution epochs' `queued_root_messages`/`target_node_ids`; failed/cancelled epochs are skipped). The worker precomputes the lane from its store and ships it in the payload; `normalize_task_terminal_payload` preserves it, and web-side enrichment re-derives it from the same store when available, falling back to the shipped value — so `--no-worker` container topologies do not lose the lane. `prompt_lane` renders it at the end of the event bundle as 「User node supplements」 lines (`- Node {title} ({node_id}): {message}`, non-`completed` epochs get a `[distribution state: …]` suffix) so the session model aligns its final report and acceptance judgment with what the user appended to which nodes.
- Heartbeat task-terminal prompt assembly renders both pieces when final acceptance fails: the acceptance-node result (`Result output`, `Result check`, `Result failure reason`) and the root execution deliverable (`Execution output`, `Execution output ref`); the full-root-output requirement applies to the event bundle the main agent reads, not to every later summary surface. The bundle also renders `Finished at:` from the payload's `finished_at`, so a late wakeup is not misread as "the task just completed", plus `Failure class:` (payload `failure_class`: `engine_failure` / `business_unpassed` / `non_retryable_blocked`) right after `Status:` and `Final acceptance:` (payload `final_acceptance_status`, omitted while `pending`). The frontdoor post-failure rules branch on that classification, so carrying it in the payload without rendering it leaves the model to infer a class from summary prose and report a terminal failure as "still retrying".
- Externalized terminal output that fits the content-open inline budget is re-inlined: enrichment resolves `terminal_output` / `root_output` through their `*_output_ref` and, when the referenced text is textual and within 16000 chars / 260 lines, replaces the summary with the full text so the turn can deliver the complete result without a follow-up `content_open`; oversized or non-textual output keeps summary + ref.
- External-bridge reply delivery: for an `ext:` session, the persisted reply is also handed to `reply_notifier` → `_notify_heartbeat_channel_reply`, which publishes an `OutboundMessage(channel="ext")`; the shared drain resolves it via the external session registry and emits `outbound.created` on the session's event hub. Reply text passes sticker resolution before both the transcript write and the frame publish: the transcript row and `ceo.reply.final` carry image markdown (refresh and the live frame land on the same deterministic pick), and the drain turns the same marker into an `after_text` image attachment for the channel — the raw marker has no user-visible landing on either surface. Rule: `external-agent-api.md`「事件流」. Legacy `china:*` sessions lost their delivery path with the China channel subsystem removal and are skipped silently (transcripts stay readable archives). Session-meta derivation must never use a naive first-colon split — see `_derive_session_channel_chat`. Reply persistence failure (e.g. disk-full during transcript save) never skips the notify: the reply stays on the in-memory session (written out by the next successful save) and both `ceo.reply.final` and the channel notifier still run — a failed save must not silence the only user-facing surface. The wake loop (`SessionHeartbeatWakeQueue._run`) tolerates leaked handler exceptions the same way: log, then retry on a bounded backoff instead of letting the task die and strand every queued event for that session. Contract details: `external-agent-api.md`「出站路由」; delivery durability across pump outages and restarts: `external-agent-api.md`「持久 outbox」.
- Repair rounds and the frontdoor re-ask are two different budgets and one turn only ever spends one of them. A turn whose final hop carried reasoning but produced neither visible text nor a tool call is re-asked once inside the frontdoor (contract: `runtime-overview.md`「Chat provider 超时与重试边界」); when that re-ask still produces nothing, the turn arrives here with `reasoning_only_reask_exhausted` set and empty output, and this layer substitutes the fixed fallback text on the spot rather than running its repair rounds — that hop's thinking was already quoted into the re-ask, so re-delivering the whole request body five more times adds no new information for the model and only deepens the quota pressure that degraded the chain in the first place. The branch reads the flag on the turn result; it never matches reply text. The event bundle was consumed before this loop starts; exhausting repair rounds changes the user-visible fallback only, never the event's consumption state.
- Heartbeat service instance reuse: `build_web_session_heartbeat` reuses the live instance bound to the same agent/runtime-manager/task-service/session-manager. The reply-notifier closure cannot be compared by identity (callers pass a fresh one); an identity-based reuse check rebuilds a not-started instance, orphaning the started one and stranding enqueued events on it.

## Task Node Error Delivery

- It scans at startup and every 60 seconds for undelivered `pause_reason=error` rows **on the task root or on an acceptance node** whose nodes remain `in_progress` and `is_paused`; non-root execution error pauses are delivered to the parent mailbox by the write-side choke point, see `main-task-runtime.md`「节点信箱与唤醒（现行）」. Acceptance nodes are the exception because a parent in `waiting_acceptance` is not woken by anything except a verdict: the verifier's own fault would otherwise wait for the stall timer. Consequence to keep in mind: an error pause on a **non-root execution node** is never marked delivered — its `task_node_pauses` row keeps `delivered=0` for life, because the delivery for that shape goes to the parent mailbox and this scanner deliberately does not select it. Those rows are inert (the predicate filters them out in SQL, so they are not re-scanned), but widening the predicate later would hand the session a backlog of ancient undelivered rows in one pass; if it is widened, clear the stale rows first. Two scar shapes are filtered out before enqueue: the inspected execution node is already terminal (the T15 close-out path), or the handshake is neither in a verdict-pending state nor carries a resolvable `latest_execution_result_ref` (there is no submission to judge).
- It groups rows by source session and enqueues `task_node_error` items with task/node identity, error text, reason, remark, and dedupe key `node-error:{task_id}:{node_id}:{pause_row_id}`. An acceptance row additionally carries `node_role=acceptance`, `inspected_node_id`, `inspected_node_status`, `handshake_state`, `submission_ref` and `final_acceptance`; fields that cannot be read are omitted rather than filled with placeholders, and a failed per-row read never blocks the other rows or the root-node escalation.
- `frontdoor_message_scanner.py` polls `frontdoor_node_messages` (the durable root→frontdoor inbox) and enqueues one `frontdoor_node_message` event per row with task/source/content/ref. It does **not** mark the row consumed on enqueue: the heartbeat marks it consumed after the event bundle is injected. The event bundle renders it as a signed node message and tells the session to reply with `send_message(to="<node_id>", ...)`; a crash before injection leaves the row pending and readable through the frontdoor message-history tool. Re-scans before injection are rejected by the queue's in-flight dedupe.
- Node-error pause rows follow the same rule: the scanner leaves `delivered=0` until the event bundle is injected; the heartbeat writes `mark_task_node_pause_delivered` at injection. Failed injection retries on the next scan; delivered rows are not resent after restart.
- `prompt_lane` renders the event as a decision to use `manage_task_nodes` for resume, keep-paused-with-remark, fail, or related-node pause. Tool validation belongs to the tool contract; delivery belongs here. The rendered bundle also carries the node's `Retry state` (`consecutive_failures`/cap, `last_attempt_at`, `next_eligible_at`) and deduped `Previous errors` — sourced from `heartbeat_node_retry_state` + `list_task_node_error_logs` and injected by `session_service._enrich_event_payload_for_lane` — so the model can tell which attempt this is instead of treating every re-delivery as the first. Once the cap is crossed the bundle adds an `ESCALATION` directive that replaces the "resume it yourself" guidance with "report to the user and ask whether to fail the node"; `heartbeat_rules.md`「对于节点错误暂停事件」carries the matching policy (re-delivery is expected, prefer `resume` when unsure, `keep_paused` for wait-to-recover errors like rate limit / quota, and `fail` only once the user has decided or the bundle itself carries `ESCALATION` — the machine keeps re-delivering for five failed rounds, so a `fail` before that point ends a node that was still entitled to retry, and `fail` has no undo). An error text carrying a runtime fault marker additionally renders a `Failure class: <class>` line (`runtime_fault` / `model_config_fault` / `window_integrity_fault` / `provider_payload_fault` / `send_preflight_fault`). The class line carries the fault *shape* only; the disposition and the observed numbers come from the `Error` body, which is the same `blocking_reason` string — one contract, one copy. `runtime_fault` is the deliberate exception: its body is an exception repr with no remedy, so that line alone names the operator action (restart the worker, do not `resume`). `heartbeat_rules.md` branches on the class for the rest: `runtime_fault` must not be resumed, the two configuration-shaped classes (`model_config_fault`, `window_integrity_fault`) are pauses a plain resume re-fires and the named fix is a model-config change or a report to the user, and `provider_payload_fault` means the hop reached a provider and came back with the gateway's own tool-call markup spliced into the argument block — the thing to check is that member's endpoint or the chain, not whether the node authored a valid delivery, and re-dispatching the node re-buys the same fault — and `send_preflight_fault` means the hop never reached a provider so the node burned zero model calls. Chain-level numbers never appear in either the class line or the body: they describe the whole chain rather than the member that served the hop, and one such reading sent a session agent to edit three unrelated model records. The breaker that produces these pause classes is owned by `main-task-runtime.md`「Node-Level Pause and Recovery」, and the window-clamp body's own readouts (which model served the hop, its declared window, the node's observed `input+output` floor, how many hops of that class the ledger already holds) are described there. Acceptance rows render a `Role: acceptance node (the verifier itself paused; this is not a verdict on the inspected node)` line, an `Inspected node: <id> [<status>], handshake=<state>` line and a `Final acceptance: yes|no` line; `heartbeat_rules.md` uses that branch to prefer resuming the verifier and to route the no-revival exit to the inspected execution node, never to the verifier itself. No model-facing line names a task-level `cancel`: the action surface reachable from a session is `resume` / `keep_paused` / `fail` / `pause`, and task-level cancel is an operator action on the web side. `Retry state` and `ESCALATION` describe injection failures only: once the event bundle is injected, a model failure does not re-deliver the event or advance that counter.
- 正文超过内联额度时不丢内容：节点错误、分发失败、降级跳过的消息本体、以及终态事件里的用户定向补充，四条渲染道都改成「头 70% + 尾 20% + 一行说明」，全文交给 content store 外置，说明行给出 `content_open(ref="…")`。额度本身不变（`build_heartbeat_prompt_lane(output_inline_limit=4000)`），所以这一步只补回被截掉的中段，不放大发送体。渲染器不自己碰存储：外置由 `session_service._heartbeat_event_text_externalizer()` 注入，存储取不到时行内如实写「外置不可用，未内联的部分此刻取不回」，不给一个假 ref。旧做法只留前 N 字——故障正文的关键句（该核对哪条记录、观测值是多少）都写在后半段，截断同时让它不可读与不可搜；检索面（`heartbeat_retrieval_query`）拿的是头+尾。终态交付正文（`Result output` / `Execution output`）不在这条里：它自带 `… ref:` 行，超限也能取回。
- A heartbeat turn that fails **before the event bundle is injected** keeps its events, and the wake queue re-delivers them. A model failure **after injection** (provider error, runtime exception, empty output, `silent`) does not re-deliver: the event is already consumed, its bundle stays prompt-visible, and the next user turn or a new event handles it. The per-node counter, backoff and escalation below therefore describe **injection failures only**.
- `task_node_error` injection failures are bounded by a **per-node persisted counter** (`heartbeat_node_retry_state` table, keyed by `node_id`; survives restart and node re-pause). Re-delivery backs off 1→2→4→5→5 minutes (the run returns the backoff as its wake delay). The counter resets when the event bundle is injected (or when a turn for that node succeeds); give-up does **not** reset it, so a re-paused node continues from its persisted count instead of reopening a fresh budget.
- After 5 consecutive **injection** failures the node enters escalation: events stay queued and keep retrying at the 5-minute cap, a visible "these nodes failed 5 times — fail them to let the task continue?" reply is emitted once when the cap is crossed, and the node stays paused for the user or a later turn to decide. A model failure after injection does **not** produce this escalation; the node stays paused with its event bundle already in context, and the next user turn or a new event handles it. The escalation reply is delivered even when its own transcript persistence fails (disk pressure): notify is memory-first and the failed save only logs — otherwise the model-unavailable fallback goes silent exactly during the disk-full storms that need it most.
- Non-`task_node_error` **injection** failures (stall / task_terminal / distribution / delivery_failure / shutdown_resume / turn_interrupted / frontdoor_node_message) are bounded too: a per-`(session, reasons)` counter with the same backoff dequeues the batch after the cap. Model failures after injection do not use this counter and do not re-deliver; a still-`interrupted` transcript row is re-enqueued by the next boot's `recover_interrupted_turns`.
- Debugging "node error heartbeats retry forever": the scanner deliberately keeps the pause row undelivered until injection, so it re-scans every interval; the queue's in-flight/consumed dedupe rejects the repeated enqueue. Suspect the per-node counter / injection path or a failed source mark, not the scanner's repeated enqueue.

## Task Distribution Error Delivery（车道已休眠）

> **distribution epoch 与降级分发均已删除**：没有代码再产生 `task_distribution_error` / `task_distribution_skipped` 事件，下面的 outbox 与渲染路径只作为历史合同保留（存量 outbox 行仍可投完）。现行异常暂停走 `task_node_error`（仅根节点）或父节点信箱的 `child_abnormal_pause`。

- A node error pause is escalated to the session only when the paused node is the task root. Every non-root abnormal pause goes to the parent node's mailbox as `child_abnormal_pause`; the write-side choke point (every writer, including `reject_no_progress`, the watchdog, the node-fault exception lane, the orphan reaper and the spawn-round park) and the P8 resend are owned by `main-task-runtime.md`「节点信箱与唤醒（现行）」. If the parent does not act, the frontend 「暂停·异常」 badge is the only visible surface. The heartbeat deliberately does not cover a non-root node at any depth.

- A message-distribution epoch that reaches terminal `failed` (wave crash over budget, or send preflight failed) marks the task paused and delivers one `task_distribution_error` heartbeat event to the task's origin session. It is task-level, not node-level: there is no per-node retry state and no `manage_task_nodes` escalation — the reminder is to stop re-distributing and tell the user the task is paused. Per-node decision-retry exhaustion does not produce this event; it degrades to `task_distribution_skipped` (below).
- Delivery mirrors the stall outbox: the worker writes a durable `task_distribution_error_outbox` row and POSTs `/api/internal/task-distribution-error`; the web-hosted mode enqueues the heartbeat directly. The web endpoint normalizes the payload with the server-recomputed dedupe key `task-distribution-error:{task_id}:{epoch_id}` before `enqueue_task_distribution_error_payload`, so at most one notification is emitted per failed epoch and a caller-supplied dedupe key cannot bypass it.
- `prompt_lane` renders the event as a task-level line naming the `blocking_reason` plus the reminder 「如果多次出现，则不要再分发，通知用户现状任务已暂停」.
- Degraded distribution (`task_distribution_skipped`) is a sibling event on the same route: when one frontier node exhausts its decision-retry budget the epoch still completes and the barrier releases, and every degraded node is reported **once per epoch** with 「已跳过 N 个节点」, each subtree root + reason, and the message body that was not pushed down. The text states the node is not paused and the skip neither auto-retries nor auto-closes — re-delivering to that subtree is the session agent's call via a targeted append notice. Payload carries the lane selector as `notice_kind` rather than `kind` (`kind` is the middle-priority event-reason key in `prompt_lane`; real delivery always attaches `event_reason`, so nothing breaks, but a hand-built or offline event dict holding `kind` would read the lane selector as an event type), shares the per-epoch dedupe key, and renders through `task_distribution_skipped`.
- Distribution-failure delivery shares the generic non-`task_node_error` bounded backoff (same bucket as stall / task_terminal), since a failed heartbeat turn leaves the event queued for re-delivery.

## Task Stall Detection

- The task stall notifier (in the process that runs the task) watches in-progress tasks whose origin session has a live delivery audience — `web:` and channel `ext:` sessions alike; only legacy `china:*` (no delivery path since the China channel subsystem removal) and empty session ids are skipped. The audience is one predicate, `task_notice_audience_ok`, and both gates that historically carried their own `startswith("web:")` copy — the notifier's schedule gate and `build_task_stall_payload` — call it; widening only one of the two leaves a silently rescheduling loop that emits nothing. Visible output — recorded node output, node status change, or check result — resets the silence clock via `last_visible_output_at`. With no output, it escalates in 10-minute buckets starting at 20 minutes and emits a `task_stall` heartbeat event per new bucket. A pass that the classifier blocks as non-actionable (distribution barrier, manual pause, worker offline) re-arms the timer instead of returning silently: dropping it leaves the barrier release as the only revival point, and that single second then reports every bucket that came due during the freeze as separate events.
- The stall lane has one observer that survives a wedged event loop. The worker pressure sampler runs on its own thread, and its lag reading is cumulative — it resets each time the probe round-trips the loop — so a single sample already reports how long the loop has been blocked. At 10 s it appends every thread's stack (including the loop's) to `.g3ku/logs/loop-stall-stacks.log` through `faulthandler`; at 60 s it posts a `task_stall` event per origin session, synchronously from that thread, choosing the in-progress task with the newest `last_visible_output_at` in each session. The two lines are set apart on purpose: the measured startup-window peak (a web start rebuilding nine tasks against a cold store) is 29.3 s, so a normal-but-heavy start leaves a stack behind — which is the evidence for which recovery step is slow — without raising an alert. The payload reuses `bucket_minutes=1` and carries the real cause in `runtime_summary_excerpt` (`worker event loop stalled: lag=<n>s sampled off-loop`), so the rendered notice stays truthful while the dedupe key stays canonical; paused/cancelled tasks and non-deliverable audiences are skipped. Both hooks fire at most once per episode and re-arm when the lag drops, and a hook failure is swallowed so the sampler thread keeps sampling.
- Delivery mirrors the distribution-error outbox: worker mode writes a durable `task_stall_outbox` row and POSTs `/api/internal/task-stall`; the web-hosted mode enqueues the heartbeat directly. The canonical dedupe key `task-stall:{task_id}:{bucket}:{last_visible_output_at}` is recomputed server-side so at most one notice lands per (task, bucket, silence-anchor).
- Silence while a node tool call runs within its universal timeout is expected work, not a stall. When a node tool call starts executing, the loop records the effective universal timeout on the frame's tool live state (`timeout_seconds`); exempt tools (`exempt_universal_timeout`, e.g. `spawn_child_nodes` / `stop_tool_execution`) record nothing because they have no outer bound. The silence baseline is anchored to the latest running tool's deadline (`started_at + timeout_seconds`), and buckets are measured from that anchor: a stall is emitted only if silence persists a full bucket window after the deadline, i.e. the tool neither completed nor was killed by its own timeout. The timeout value follows `tool-hydration-and-callable-chain.md`「统一工具 Timeout 合同」(explicit `timeout_seconds` argument, else the global default). An over-large `timeout_seconds` pushes this deadline out by the same amount and so silences stall detection for that whole window — pair short commands with short values. The deadline comes from the frames' own live state, and that is the only frame-body field this lane reads, so the whole stall lane reads the ledger with `read_runtime_state(..., frame_mode='stall')`: the three node-id tables come from the frame columns, and frame bodies are fetched per-node by SQLite (`json_each` over `$.payload.tool_calls`, filtered to a running call with a positive `timeout_seconds`), so a call returns only the frames that can move the anchor. On a live 161-frame / 6.39 MB ledger the full-frame read costs 121 ms of Python JSON parsing per visible-output event, while the stall read costs 0.2 ms for the columns plus 23 ms inside SQLite (GIL released) — and `tool_calls` is 52 KB of those 6.39 MB. Consequence to keep in mind: in stall mode `frames` carries only `node_id` and `tool_calls`, so any new judgment that needs another frame field must ask for the full read instead of quietly getting a partial frame. The read-side rule is owned by `runtime-overview.md`「运行时里的状态与持久化」.
- Each `task_stall` payload also carries `delivery_index`: how many notices for **this silent window** have been injected. The reading lives in the task runtime meta as the pair `stall_notice_anchor` + `stall_delivery_count`, so a changed anchor restarts the count at 1 and there is no separate reset path (the meta row retires with the task). It is read during lane enrichment (`_enrich_event_payload_for_lane`) and written only at the injection consume point (`_record_task_stall_deliveries`, beside `_ack_task_stall_events`), which makes a failed-injection retry keep the same number instead of skipping ahead. The field is whitelisted in `normalize_task_stall_payload`: dropping it there silently loses the reading on a worker → web hop. The bundle prints `Delivery: <n> notice(s) for this silent window` and prints nothing when there is no reading — `0` would read as "the first one" where the real shape is "no reading". This reading is why the fold can stay exact-content: with copies folded away, counting copies would otherwise be impossible (see `context-and-cache-troubleshooting.md`「heartbeat / cron 上下文残骸」).
- Each `task_stall` payload also carries `perf_window_summary`: one bounded line judging the silent window (silence anchor → now) against the worker performance history — tier seconds per `budget_state`, tool/node queue peaks and oldest wait, machine/library maxima, sampling gaps, plus an explicit "no resource restriction in this window" when nothing was restricted. It is produced by the same aggregator that backs the `perf_inspect` tool, and the storage/sampling contract is owned by `runtime-overview.md`「Worker Performance History」. Two maintenance traps: the field must stay listed in `normalize_task_stall_payload`, otherwise it is silently dropped on the worker → web hop; and `_refresh_task_stall_events` recomputes it at delivery time, because the bucket (and therefore the window) may have moved since the notice was queued.
- Each `task_stall` payload also carries a structured `stall_detail` block — facts only, never an action. `entry_gate` reports the shared node-turn pool (running/limit/queued, how long the pool has been saturated while nodes wait, per-role reserved slots) plus **this task's** own `dispatch_running` / `dispatch_queued`, so "this task is queued at the gate" is readable per task instead of only as a worker-wide number; `turn_queue` reports the queue **inside** the gate — granted model-turn leases, nodes waiting for one, the oldest wait, and when one request owns the grant window how long it has, why it is not being granted, which node it is and how large a context window it demands — because `dispatch_running` only means "holding a gate slot", so a session that reads it as "N nodes are advancing" will conclude "not a real stall" while that layer granted nothing at all; `upstream_rate` reports requests/min, completions/min, the 429 penalty peak and the pressure states; `occupiers` lists the other in-progress tasks with how many slots each holds and how many each has queued; `lane` reports an active distribution barrier, the running tool call's deadline in the tense the clock supports, and the frame phases at emit time. The deadline line takes its tense from the comparison itself (`prompt_lane._running_tool_deadline_line`): while the deadline is ahead it reads `still inside its own deadline until`, and once it is behind it reads `Silence is measured from a node tool call's deadline, which passed at`. The delivery gate discards an event whose deadline is still ahead, so what actually reaches a bundle is an expired deadline — printing it as ongoing work hands the receiver a ready-made reason to do nothing about a node that stopped hours ago. Two rules keep the block honest: it carries **no remedial wording** (the existing guidance lines are the only place an action may appear), because "pause this task and resume it later" is wrong for a waiter — a queued node holds no slot, pausing frees nothing, and a resume re-creates the entry at the tail of the gate queue; and every field is a measured reading or absent, never a zero-filled placeholder, because `0` reads as "the gate is idle" when the real shape is "no reading this beat". Pool capacity and queue semantics are owned by `runtime-overview.md`「节点回合闸（执行器存在的成本也要闸）」and `main-task-runtime.md`「节点调度读数与共享池」.
- The event's duration must be derived from the anchor the event prints: `bucket_minutes`, `stalled_minutes` and `last_visible_output_at` all come from the one silence anchor re-read at payload time. Taking the maximum of a caller-supplied bucket and a freshly read anchor yields a self-contradictory notice ("last visible output: this second" plus "silent for 30 minutes"), which is what a barrier release landing in the same second as a due bucket produces. The bundle labels that printed anchor `Silence measured from:` and not "last visible output": the two are the same value only while no tool call is bounding the window, and whenever a running call's deadline is later than the node's last visible output the anchor is that deadline. `_refresh_task_stall_events` recomputes the numbers at delivery and writes the same anchor back, because the dedupe key was already built from the silence anchor at enqueue — stamping the node's raw meta value beside a duration measured from the later deadline prints two readings that cannot produce each other.
- The event bundle renders the line as `Perf in stall window: …`, and the stall guidance block tells the model to load `perf_inspect` when it needs a wider window. The same block owns the repetition rule and the two task-level exits, because it is the only place stall guidance may name an action: the notice repeats while the task stays non-terminal and unpaused, `keep_paused` on nodes does not stop it, and neither does replying to the user (a session that has written the user a long report still gets the next bucket); the exits are `manage_task_nodes` in the whole-task form — `action=pause` parks the tree and ends the repetition, and `action=pause` followed by `action=fail` closes it, a `fail` answering `subtree_not_fully_paused` while any non-terminal node of the tree is unpaused. Without those lines the receiver has to guess whether "already handled" also means "will stop", and the two readings point at different buttons. Missing coverage is reported as a coverage gap (`no perf rows and no worker heartbeat row` / `no perf rows ever written (worker heartbeat age=…s)` / `perf sampling stopped … ago`) and never as "no pressure" — a stall notice with no perf evidence must not be read as evidence about resources either way. Debugging "the stall notice says nothing about the machine": the line states facts (rows in table, newest sample, worker heartbeat age) and hands the cause over to the worker log anchors `worker heartbeat beat failed` / `failed to record perf sample`; do not re-add a single-cause sentence here or to the report text, because the model quotes it verbatim to the user.
- The web heartbeat refresh path (`_refresh_task_stall_events`) re-validates a queued `task_stall` event before delivery and discards it while a running tool is still within its deadline, so an event enqueued just before a long tool started is not delivered as a false stall.
- Debugging "false stall heartbeat while a long tool (e.g. `exec` with a large `timeout_seconds`) legitimately runs": confirm the running tool call's frame live state carries a positive `timeout_seconds`. Exempt tools and non-node tool paths do not record it, so they keep the plain silence-clock behavior.

## Shutdown Resume Wake

Graceful project shutdown pauses every running session; at the next startup the web runtime wakes each recorded session through the heartbeat lane with a `shutdown_resume` event. The pause/resume lifecycle contract lives in `main-task-runtime.md`「Graceful Shutdown Pause and Startup Auto-Resume」; this section owns the wake lane.

- The event payload is minimal (`session_id` + `event_reason`); the interrupted user request is not re-embedded. It reaches the model through the frontdoor continuation path's paused-turn seed reconciliation, so the wake prompt only instructs the model to continue the work already present in context.
- Prompt contract: empty output on `task_terminal` or `shutdown_resume` is treated as an invalid turn — it re-enters the same repair loop, and exhaustion produces a fixed visible fallback text. `silent` is recognized before that loop, so a deliberate silence never counts toward the failure budget; an empty-looking silent turn carries its `reason` as the final text and closes with no delivery. These decisions govern the **user-visible reply only**: the event bundle is consumed at injection, so a silent or empty outcome does not change whether the event is retried. The two branches differ on purpose: `task_terminal` may stay silent only when a later reply in the same session already covered the same deliverable and the model names that covering id in `superseded_by`, and the instruction tells the model to report rather than silence when it cannot tell; `shutdown_resume` has no silent exit at all, because its whole meaning is "this user request has not been delivered yet". The instruction wording for every branch comes from one helper, so the silence contract cannot drift per-branch.
- Durability: the wake is enqueued from durable shutdown-pause ledger rows; the heartbeat marks a row consumed only after the event bundle is injected. A crash before injection re-wakes on the next startup. A model failure after injection does not re-wake: the event bundle and the paused request stay in context, and the next user turn or a new event handles them.
- Busy sessions are deferred by the ordinary wake-queue busy check; repeated **injection** failures follow the generic non-node-error bounded backoff (see 「Task Node Error Delivery」). A model failure after injection does not re-deliver.
- Turn identity: a wake whose event bundle is only `shutdown_resume` continues the interrupted request under its original `turn_id`, so the paused bubble and the continued reply remain one transcript row and one bubble. A bundle mixed with other events (`reason=mixed`) answers something else and never claims that id. The claim itself, the archive row it rewrites in place, and the per-turn token carry-over are owned by `runtime-overview.md`「`RuntimeAgentSession` 内部做什么」.
- The final reply is persisted and published through the ordinary heartbeat visible-reply path (`ceo.reply.final`, channel notifier included), so the user sees the continued work without sending a new message.

## Interrupted Turn Wake

An abnormal process exit can leave the primary user row of an in-flight turn in the transcript plus an inflight snapshot. That row is not a queued follow-up: replaying it as a user message changes its identity and lets the model treat the same request as a second user send. This section owns the crash-resume wake lane; the transcript state machine and turn-id adoption are owned by `runtime-overview.md`「崩溃中断回合恢复」.

- Startup `recover_interrupted_turns` runs after graceful-shutdown resume and before queued follow-up replay. It scans `pending` / `interrupted` user rows, constructs each session, and reads the session's `interrupted_turn_recovery_state()`. The constructor marks only the primary row whose `turn_id` matches the inflight snapshot as `interrupted`; follow-ups with other turn ids remain `pending`.
- The event is `reason=turn_interrupted`, `source=frontdoor`, dedupe key `turn-interrupted:{session_id}:{turn_id}`. Payload: `session_id`, `turn_id`, `last_activity_at`, `detected_at`, `source=crash_recovery`. The durable marker is the transcript row, not a new outbox: a boot that still sees `interrupted` without an assistant reply re-enqueues the same key; a boot that sees an assistant row flips it to `completed` and enqueues nothing.
- `last_activity_at` is the newest parseable value among the inflight snapshot's `persisted_at`, the user row timestamp, and the last transcript row timestamp. The prompt computes `now` at wake time and renders `last_activity_at`, `now`, and `stopped_seconds`; there is no freshness cutoff — the model decides whether continuing still makes sense.
- Rendering has one author (`prompt_lane.turn_interrupted_lines`; the session-side copy is gone, `session_service._build_heartbeat_stable_rules` produces only the stable guidance/rules section): state that the process restarted, the user did not send the request again, print the three time values, and tell the model to inspect the turn ledger and background job state before retrying side-effecting work. If it cannot continue safely, it must tell the user what remains.
- `turn_interrupted` forces a user-visible reply and has no silent exit; a bundle that also carries `task_terminal` still may not use the silent tool. The final reply is persisted and published through the ordinary heartbeat visible-reply path.
- Turn identity: a bundle whose only reason is `turn_interrupted` adopts the original `turn_id`; a mixed bundle does not claim it. Successful recovery transcript persistence marks the interrupted row `completed` even when the reply landed under a new internal turn, so a later boot does not re-enqueue it.
- Boot queued-follow-up replay skips a session that has an interrupted-turn recovery state. The recovery turn can consume pending follow-ups through `take_follow_up_batch_for_call_model`; otherwise they remain for the next idle / WS dispatch. Manual pause and graceful shutdown keep their `paused` / `shutdown_resume` lanes and are not converted to `turn_interrupted`.

## Tool Job Heartbeat Events

Frontdoor tool calls that exceed the foreground wait window are handed off to a background job (`runtime-overview.md`「Frontdoor Tool Job Handoff」). This section owns the heartbeat lane that tells the model the job's terminal state.

- A terminal job enqueues one event with `reason=tool_job`, `source=frontdoor`, and status `success` / `error` / `timeout` / `interrupted` / `stopped_by_user`. Dedupe key is `tool-job:{job_id}:{status}`; a job emits at most one terminal event, so a stop followed by a late completion does not produce a second one.
- Payload: `kind`, `job_id`, `session_id`, `tool_name`, `status`, `started_at`, `finished_at`, `elapsed_seconds`, `timeout_seconds`, `turn_id`, `tool_call_id`, `result_preview`, `result_ref`, `log_path`, `recovery_policy`, `stopped_by`. `kind=tool_job` 是超时交棒的调用；`kind=process` 是用户从 Web UI 停掉的 `exec background=true` 进程，额外带 `pid` 与 `cmd`，`job_id` 是 `proc:<pid>`。The preview is clipped; long output is externalized by the ordinary event renderer.
- Rendering has one author (`prompt_lane.tool_job_lines`, for the same reason as `turn_interrupted_lines` above): success/error/timeout say the job finished or timed out and tell the model not to re-call the tool with the same arguments before inspecting the result; `interrupted` says the process restarted, the job may have stopped or may still be running, and the model must inspect result/log before retrying; `stopped_by_user` says the user manually stopped it (用户手动停止) and the model must not restart it unless the user asks. A `kind=process` stop renders as “Background process pid N (command)” rather than “Background tool job …”, because the model already received the process's pid when `exec background=true` returned. A `rerun_safe` recovery policy is stated explicitly; otherwise the model is told to inspect before retrying.
- `tool_job` never forces a user-visible reply. When the same bundle also carries `task_terminal`, `shutdown_resume`, or `turn_interrupted`, those branches' stronger visible-reply rules still apply.
- Durability is two-phase through `tool_job_outbox`: the terminal payload is written before enqueue, and `_consume_heartbeat_events_at_injection` marks it delivered only after the bundle is injected. Startup replays pending rows; a crash before injection re-wakes, a model failure after injection does not. `kind=process` stop events have no `tool_jobs` row to anchor an outbox entry; they live only in the in-memory queue (the process is already dead, so the only stake is informing the model).
- Startup recovery of `tool_jobs` rows (owned by `runtime-overview.md`「Frontdoor Tool Job Handoff」) creates the same event for rows left `running`/`stopping`: a running job becomes `interrupted`, a stopping job whose stop event was never written becomes `stopped_by_user`, and an already-written event is repaired without creating a second one. The per-job event dedupe key is the guard.
- Session pause/stop does not cancel a background job, so it produces no event at pause time; the job's own terminal state wakes the session later. Only the session-delete path cancels jobs without an event.
