# G3KU 本地语音识别架构说明（whisper.cpp）

## 1. 定位与边界

这个子系统负责把音频字节变成文字，仅此一种能力，服务两个入口：Leader/CEO 输入框的语音按钮，以及官方 QQ 适配器收到的语音消息。

它是**输入侧的预处理**，不是模型车道：推理全程在本机完成，不碰 provider 配置、不需要任何 API key、不在运行时联网。产出是一段文本，交给既有的输入通道（网页侧回到输入框由用户确认，QQ 侧并入回合正文）。

代码边界：`g3ku/stt/engine.py`（引擎生命周期、单槽串行、就绪判定、分发下载）与 `g3ku/stt/audio.py`（音频几何与时平）。ASR 本体是**外部的官方 whisper.cpp 可执行文件**，不是 Python 依赖——仓库里没有任何语音模型权重。

新维护者容易误读的两点：`stt.enabled=true` 只代表允许使用，真正可用还需要 `g3ku stt prepare` 落下二进制与模型（就绪与否由 `engine.status()` 的 `ready` 单独表达）；以及语音文本进的是普通回合，没有任何"这是语音"的特殊运行时分支。

## 2. 引擎形态：每次调用起一个子进程

形态是被测量选出来的，不是默认偏好。基准环境是该产品的下限机器（2 vCPU / 4 逻辑核、7.7 GB 内存、无 GPU），素材是 22.9 秒普通话音频、`base` 模型：

| 形态 | 一次 23 秒音频 | 峰值 RSS | 空闲常驻 |
|---|---|---|---|
| `whisper-cli` 子进程 | 6.9 s | 318 MB | 0 |
| 常驻 `whisper-server`（回环 HTTP） | 6.2 s | 274 MB | 269 MB |

常驻只换来 0.7 秒，因为耗时主体是 whisper 固定 30 秒窗的解码，不是模型加载。于是常驻形态要为这点收益全天候占 269 MB、多一个受管进程和一个回环端口。子进程形态顺带带来一个结构好处：**Python 侧没有任何 ASR 依赖**。

转写被一个全局槽位串行化（`_QUEUE_WAIT_SECONDS` 排队预算，超时回 `stt_busy`）。理由是单次调用就要用完被允许的逻辑核，两段语音并发只会互相拖慢并挤掉正在跑的回合——多 QQ 账号同时来语音时尤其如此。

## 3. 数据流

网页侧：浏览器录音 → 前端解码重采样为 16 kHz 单声道 PCM WAV → `POST /api/ceo/transcribe` → 引擎 → 文本**追加进输入框**，用户在发送前看得见、可编辑。前端做重采样是为了让 60 秒音频落进 2 MiB 上限，并让网页这条路上完全不需要解码器。

QQ 侧：桥下载语音附件字节 → **进程内**直接调用引擎（桥与 web 在同一 event loop）→ 成功则把文本并入本条消息正文并带 `[语音转文字] ` 前缀；识别失败并入 `[语音转文字] [未能识别：<原因>]`；STT 未就绪时音频按原样作为 `file` 附件转发。前缀是契约的一部分：没有来源标记，听错的语音和手打文字在模型眼里无法区分。

音频字节**不落盘**：引擎只在临时目录里活一次调用，`finally` 里删除。这与 `/api/ceo/uploads` 有意不同——上传是用户主动附加，语音是尚未决定要留下来的个人数据。

## 4. 音频几何与门控

- WAV 直通，但**时长以实际数据块字节数换算，不信头部声明**：ffmpeg 向管道输出时无法回填长度字段，信它会得到 134218 秒并把正常录音误判为超限。
- 非 WAV（网页的 webm/opus、语音条可能带的任意容器）走 `ffmpeg` 兜底转成 16 kHz 单声道 PCM；没有 ffmpeg 时返回稳定错误码 `audio_decoder_missing`，不静默丢消息。ffmpeg 子进程带超时并清掉继承的环境变量。
- 静音在进二进制之前按声级拦（`min_rms_dbfs`，默认 −70 dBFS）。实测留在这条门下的最轻语音是 2% 音量的 −57.6 dB，正常语音 −23.6 / −16.9 dB，数字静音 −120 dB：它是省时间的粗筛，不是质量门。
- `language` 默认 `auto`。实测 `-l zh` 快 33%（6.9 s 对 9.2 s），但把 3 秒静音听成了两句话；`auto` 返回空。静音防护不能押在采样参数上：`-sns` 保留，`-bo 1` 不提供（best-of 降到 1 后静音同样出流式句子）。
- whisper 的 `base`/`tiny` 对中文一律输出繁体（`small` 输出简体），而繁体偏置 prompt 在 v1.9.4 上**不升反降**，所以繁简转换是出词后的独立一步（`simplify_chinese`，实测 48 微秒），不是模型档位选择。

## 5. 分发与就绪

上游只把预编译产物挂在**构建号 tag** 上：`b5130` 与 v1.9.4 同日发布，含 `whisper-bin-x64.zip`（8.18 MB）。解包 21 MB，实际需要的 13 MB（CLI + 动态库），其余是示例与测试可执行文件，抽取阶段就丢掉。

版本与摘要都是钉住的：`binary_release_tag` 与 `binary_sha256` 写在配置里，摘要不过就地拒绝解压。原因是"最新"在本机既不可静默获取也不可信任——产物必须来自一个可审计的决定。

下载源默认值来自实测网络：**模型走 `hf-mirror.com`（约 20 MB/s），因为 `huggingface.co` 在这类网络里直连超时；而 GitHub 产物 CDN 实测只有 ~20 KB/s**，所以二进制下载必须支持 Range 续传，且 `prepare` 是显式的运维动作而不是首次使用时悄悄下载。

操作员动作：

```bash
g3ku stt prepare            # 下二进制 + 模型，不动开关
g3ku stt prepare --enable   # 顺带打开 stt.enabled
g3ku stt status             # 就绪矩阵：开关 / 二进制 / 模型 / 转换器
```

落盘位置跟随数据根（`stt.model_dir` 默认 `.g3ku/stt`，二进制在其 `bin/` 子目录），因此自定义数据目录的安装会把 150 MB 量级的模型放到体积侧而不是安装根。

## 6. 配置字段

`stt` 段的字段与默认值的完整依据见 `g3ku/config/schema.py` 的 `SttConfig` 文档串；配置系统层面的归属说明在 `config-and-models.md`。字段的语义要点：

- `model`：`tiny` / `base` / `small`。`base` 是交互可用的默认；`small` 中文更准且原生简体，但在这台下限机器上比实时还慢（20.9–32.9 s 跑 22.9 s 音频）并要 854 MB。
- `threads`：默认 2。给到 4 只快 26%，代价是饱和整机。
- `max_audio_seconds` / `timeout_seconds`：前者是输入侧上限，后者是单次调用的硬止损（超时杀进程树）。
- `min_rms_dbfs`：声级门，见第 4 节。设得很低即可实质关闭。
- `language`：`auto`（正确性优先）或 `zh`（快 33%，静音会幻觉）。
- `simplify_chinese`：需要 `zhconv`；缺包时原样返回，不影响可用性。

## 7. 已知边界

- 时延下限由硬件决定：23 秒音频 7–10 秒。UI 必须显示进行中状态，否则看起来像卡死。
- `base` 档中文实测约 5% 字错（"生成"→"声称"、"发到"→"发道"、"密钥"→"密要"）。网页路径可复核，**QQ 自动转写路径用户没有复核机会**——错字会直接进模型上下文。
- 网页录音需要安全上下文：`http://127.0.0.1:18790` 可用，用局域网 IP 走 http 打开面板时浏览器直接禁麦克风。前端把这条原因显式说出来，否则按钮像坏了。
- `/api/ceo/transcribe` 与既有 `/api/ceo/*` 同处一个鉴权面（只有启动锁 423 闸门）。上限、时长与单槽就是它的成本控制，能访问该端口的人即可消耗本机 CPU。
- QQ 平台侧语音消息**已经确认收发支持，但容器格式没有实测依据**：官方文档只写 `content_type` 区分类型、未列取值。本机 ffmpeg 8.1.2 **没有 silk 解码能力**（demuxer/decoder 清单里都不存在），所以如果 QQ 传的是 silk，需要的是一条独立解码车道而不是现有兜底。这条要用真机发一条语音取证。
- 非 Windows 的二进制抽取路径未实测（Linux 产物名与 so 依赖只能按命名规则推）。

## 8. 常见排障入口

- 点按钮没反应／报"当前页面不是安全上下文" → 第 7 节安全上下文一条
- 提示"语音识别未就绪" → `g3ku stt status` 看是哪一道闸门：开关、二进制、还是模型
- 一切正常但结果繁体 → `simplify_chinese` 或 `zhconv` 缺包
- QQ 发来语音只有"[未能识别：…]" → 看错误码：`audio_decoder_missing` 是缺 ffmpeg，`stt_silent` 是没录到声音，`stt_too_long` 是超上限
- 识别很慢 → `stt.threads` 与 `stt.model`；`small` 在 2 核机器上不适合交互
- 转写期间其它语音条一直等到 `stt_busy` → 单槽是设计，不是故障
