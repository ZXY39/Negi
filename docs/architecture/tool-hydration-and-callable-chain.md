# Negi 契约在场与 callable 链路

本文负责"工具凭什么在这一跳可调用"这条链：契约在场判据与它的唯一载体、契约不在场时的投递与入参暂存/复用、派发时预置契约、参数错误与状态分类、外置工具结果信封、统一工具 Timeout 合同、严格纯文本打回与固定内置集合，以及从上下文到 callable tools 的完整链路。
四个概念的边界定义、fixed builtin 工具的逐项合同与 RBAC 如何得出候选集合，归 `tool-and-skill-system.md`；前门与节点的上下文压缩合同归 `runtime-overview.md`。

## 1. 契约在场与 callable

一个工具在这一跳能不能被调用，只由一件事决定：**它的 toolskill 契约标记块在不在这一跳的模型可见请求视图里**。没有台账、没有"提升"步骤、也没有需要模型先完成的加载动作——契约不在场的调用照样被受理，那一跳把契约交回并把入参暂存，下一跳才真执行。`load_tool_context` 因此从"能力的前置门槛"变成"想先读说明时的可选动作"。

### 在场的唯一载体

- 载体只有 `[TOOL_CONTRACT:<tool_id>:<fingerprint>]` 标记块（存量请求体里的 `[TOOL_CONTRACT_V1:…]` 同认），三条投递道都产出它：`load_tool_context(_v2)` 的结果行、「契约不在场却直接调用」那条投递回执，以及派发时预置进节点 bootstrap 的独立消息（见「派发时预置契约」）。前两条落在工具结果正文里，第三条落在一条独立 user 消息里——三条经**同一个**渲染函数产出，逐字节相同，所以判据不需要知道是谁送的（`g3ku/runtime/tool_contract_block.py` 渲染、`g3ku/runtime/tool_context_presence.py` 解析）。
- 判据按**当次请求视图**现算，每跳只扫一次（`main/runtime/react_loop.py` 的 `loader_contract_revisions` 与 `g3ku/runtime/frontdoor/_ceo_runtime_ops.py` 的在场索引各算各道的那一次），结果下传给本跳全部消费点：执行准入、投递判据、观测读数。同一跳里出现两个答案是这层设计禁止的。
- 历史正文里出现过的工具名**不算在场**：正文不在模型眼前就不算。第二个"在场"载体正是"看得见名字却调不动"这类漂移的来源。
- 常驻内置与循环自己注入的控制信号不进判据（`CEO_NEVER_CONTRACT_TOOL_NAMES` / `NODE_NEVER_CONTRACT_TOOL_NAMES`，`g3ku/runtime/tool_visibility.py`）：`silent`、`wait_tool_execution` 这些没有 toolskill 的名字一旦进判据就被判成"契约不在场"，整个回合锁死。名单漏一处就是一起事故。
- 判据缺失（调用方压根没交当次请求视图）时**不**走投递路径，也不摘任何能力：读不到不等于不在场。

### 契约不在场时发生什么

- 这一跳不执行工具，改为返回：该工具的契约块 + 一句"已受理、本次未执行"的回执（`This call did not run the tool - call it again to execute it.`）。这句否定必须留在回执里：契约在场与执行分属两跳，回执只写"契约已加载／入参通过校验"时，模型会把它读成执行成功并直接向用户宣布结果。这条结果行带运行时标记 `contract_delivery`（值 `staged` / `invalid`），Web 面据此把它画成"加载 tool"而不是一次普通工具调用——会话侧弹 loader 同款 notice 且不上轨道，节点详情用 loader chip；展示合同归 `web-and-admin.md`「Context Loader Notices」。入参校验通过时**同批暂存**该调用；回执**只报份数、不抄入参**——发起这些调用的那条 assistant 行就在同一请求视图里，抄一遍是纯重复。份数在**这批最后一条**回执里给最终值（投递是逐条发生的，第一条那一刻只看得见半批；末条本身校验失败也照报），两数不等时写成 `2 (from 3 calls)`：同批同签名会折叠成一条，校验失败的那条也不入库，两种都会让份数少于调用数——回执只给两个事实，原因由模型对着自己的行判。校验失败时不暂存，只把参数错误原样贴回。
- 同一跳同一工具只发一份完整契约块，第 2..N 份只说"见本批第一条"。按调用次数放大正文等于把同一篇东西复制进历史。
- 这一批若一个工具都没真执行，本轮按"只投递契约"记账，不产生工具步。
- 裁撤或压缩把块移出上下文 ⇒ 该名字立刻不在 callable 里，同时重新回到候选。这条不通知、不报错：下一次调用它就走上面那条投递路径自愈。**能力面随上下文收缩是当前设计的正常形状**，不是抖动缺陷。
- 声明面与准入面不同源：钉住的 `tools[]` 提供参数表（渲染面），执行准入按在场判据取实例。差出来的那批名字——`tools[]` 里带着参数表、块却不在场——本轮调用**不撞墙**，而是走投递路径拿契约。`availability_hint` 与 `denied_tools` 的文案按这个口径写。
- RBAC 收回与资源下架仍当场生效：治理实时读不放行的名字当跳从 callable 与派发字典摘除，尾块用 `denied_tools` 提前点名（`denied_tools` 的语义是"`tools[]` 里带着参数表、但实时授权读不放行"）。"契约在场"从不覆盖权限判定——在场是必要条件，授权也是必要条件。
- skill 不走这条判据：`load_skill_context` 的正文同样随裁撤/压缩离开上下文，但 skill 没有 callable 面可摘，正文不在场只是"需要再读一次"。
- 声明面（可加载面）与准入面不同源，两条车道各自有个咽喉点：前门 `_frontdoor_dispatch_tool_names` = 钉住的 `tools[]` 声明 ∩ 当轮治理可见，它是**可加载面**；模型可见参数表的**名字源是 state 里那份钉住声明本身**（`provider_tool_names`，按钉住顺序渲染，见 `tool-and-skill-system.md`「Provider Tool Surface」），派发名单只在 state 带不出钉住声明时当播种一支的兜底。准入面另算——`_frontdoor_executable_tool_names` = **本轮 callable**（常驻内置 + 契约在场的名字），声明名再与当轮治理可见求交（RBAC 收回当跳生效），非声明名（mid-turn 注册后由 load 落账的）不受回合初快照误拒；`tool_names` 键缺失的旁路才退回派发名单。`_registered_tools_for_state` 按准入名单取实例，供执行束与调用准入用。模型可见面与执行准入面分源，这是钉死 `tools[]` 的直接推论。
  渲染面不读执行束的准入视图：`_frontdoor_tool_schemas_for_state` 从声明面单独解析出的实例渲染，参数表来源链与回落顺序归 `tool-and-skill-system.md`「Provider Tool Surface」。拿准入视图 `visible_tools` 渲染会把参数表随 callable 一起从 32 收窄到十几个，钉住语义当场失效，而 `tools[]` 一旦逐跳增删名字，前缀缓存每跳都断。
  两层差出来的那批名字（`tools[]` 里带着参数表、块却不在场）本轮调用**不撞墙**：走「契约不在场时发生什么」那条投递路径，同一跳把契约拿回来。第四态才是禁止形态——"既调不动、又发现不了"；声明面始终是可发现、可按名 load 的，`availability_hint` 的 `declared_names` 为钉住清单里没进本轮 callable 的声明名补指引，不落成"未知名字"。
  节点把能力收窄做在选择之前：判据不在场的名字直接摘出本轮 callable 组，选择组出的 callable 与执行准入用同一份收窄结果；收窄只作用执行面，钉住的 `tools[]` 里那个名字由声明侧自带的参数表继续供着，模型真去调它拿到的是契约投递。
- 非声明的名字（mid-turn 注册的工具）被 RBAC 收回时的出口在工具态收尾的实时卫生：治理实时读不放行的名字当跳从 `tool_names` 摘除（它不在 `tools[]` 里，`denied_tools` 点不到名），callable 不含它；RBAC 重新放行后由发现出口重新送回候选。声明名的收回仍走 `denied_tools`（名单源＝钉住声明）+ 重印边界。

### 重读与指纹

- 指纹 `tool_context_fingerprint`（形如 `tcf:<16 hex>`）由**源字节**算出：`tool_id` / 契约正文 / 参数契约 markdown / 必填项 / 示例 / warnings / errors / exec 运行模式。它同时是块头的一部分，所以在场判据与"这份正文变过没有"用同一个号。刻意不含 `callable`、`available`、`callable_now` 这些本次调用视角——掺进去会让同一份正文每轮算出不同指纹，重复读守卫与"块是否过期"的判定一起失效。
- `load_tool_context` 的成功 payload 自带一行 `promotion` 结论（`promoted_next_hop` / `already_callable` / `not_in_this_hop_candidates` / `not_promotable`）与 `promotion_help`：`ok:true` 不承载"不承诺"。这里的 `hop` 指**一次模型调用**：同一条用户消息内可以有多跳，"下一跳"是工具结果返回后的下一次模型调用，不是下一条用户消息。`callable_this_hop` 表示这一跳真能调用（读的是本次调用的 callable 视图，不回退到"已授权"名单），`callable_now` 只表示"该执行器对这个角色可调用"（治理层视图）——新维护者最常把这两者混为一谈，混了就会反复给模型"说它可用、调它报错"的回执。
- **说明可读性 ≠ 调用授权**：请求的名字不在本角色可见集里，但只要它注册过 toolskill（`ResourceManager.load_toolskill_body` 有正文），load 照常返回正文，并带 `documentation_only: true`、`callable/callable_now: false` 与一条 warning「本角色不可调用该工具，本次仅返回说明正文」。典型是 `exec`：节点道的常驻内置、同时带 `tools/exec/toolskills`，验收角色不可调用它却需要读契约判断子节点命令是否合规。旧门槛把"不可调用"误答成"没有可加载的 toolskill"（实盘 `task:d657c1f554e3` / `node:6c826522f86f`）。**说明在场不会让名字变可调用**：`contract_present_tool_names_for_node` 仍按 `list_effective_tool_names` 过滤。
- 重复读守卫按块头指纹跨轮比对：块已在场且指纹未变时软拦截重读，提示模型复用既有 toolskill；指纹变了，或旧结果已被 `token_compression` 移出上下文，则放行重读。

### 入参暂存与 `reuse_args` 批量执行

- 契约投递那一跳把**校验通过的入参**暂存起来：容器按 scope 分格（节点 `(task_id, node_id, tool_id)`，前门 `(session_key, tool_id)`），每条目记 `args` / `args_digest` / `staged_at` / `staged_hop` / 指纹。载体与跳序同刻落盘（节点进 `node.metadata`，前门进会话态），所以 pause/resume 之后暂存照旧可用。实现集中在 `g3ku/runtime/tool_arg_stash.py`。
- **暂存与销账是存储层的原子读-改-写**：节点道三条写点（`MainRuntimeService.stage_node_stash_entry` / `consume_node_stash_entries` / `drop_node_stash_scope`）都在 `store.update_node` 的 mutator 内对**库内当前容器**做合并或删除，调用方手里的容器只当读视图，绝不整份写回。这是同批多个冲动调用能各自存活的前提：批内每条调用拿到的都是同一份批前快照（节点道 `_call_runtime_context` 是浅拷贝），谁把自己那份快照写回，谁就覆盖掉兄弟调用刚暂存的条目（实盘 `task:ca4661223a7a`：一条消息里 3 个未水合 `filesystem_write`，最后只剩第 3 份）。前门道的会话载体同形：销账前现读会话当前载体，再按 digest 精确删除。末条回执的 `staged_count` 取**落盘后的容器**，不按本调用自己的半批算。
- **严格一跳**：条目只在其 `staged_hop == 当前跳 - 1` 时可消费，且指纹必须与当轮在场指纹一致。时钟推进发生在投递之前（本轮落的条目按推进后的跳序记），因此"下一跳"正好是它那一跳。
- 下一跳把 `reuse_args=true` 传给同一颗工具即整批执行：该 scope 里**全部**可消费条目按暂存顺序跑完，聚合成**一个** tool_result（`{"ok": true, "executed": N, "failed": K, "items": [...]}`）。每份结果先各自走单次调用的渲染与外置闸门，再进 `items`；**聚合体本身不过外置闸门**：它是逐份限界后的最终模型面文本（`PreRenderedToolResult`），节点投递层原样透传，前门道直接投递，整包完整进入上下文。一份抛异常只让那一项 `ok:false`；顶层 `ok` 表示"这批跑了"，`failed` 是失败份数，逐项成败看 `items[*].ok`。整批 raise 出去，模型读到的是"没跑"，于是重发一次把已成功的再跑一遍。前门道的逐项 `ok` 取执行侧状态，不从外置后的文本反推。
- 不支持选择性消费。要只跑其中几份，就别用 `reuse_args`，带新参数直接调；那一跳按显式入参执行一次，并按 digest 销掉此前暂存的那几份。整批复用同理：只销**执行过**的 digest（`tool_arg_stash.remove_digests`），不按消费时刻的可用全集——复用批逐份执行有 await 窗口，这段时间同批另一条调用暂存的新入参还没跑过，不能被顺手删掉。
- 执行侧仍按当轮重新认定可得性：名字不在本轮实例表里（无权限/已下架）时整批交回普通路径，出那条带名单的拒绝回执，一份都不撞。
- 三类非法复用各有文案，且都**不计一轮预算**（字段误用不是任务失败，计预算会让模型从此绕开这条通道）：无暂存可复用、契约已离场（连带清掉该 scope）、`reuse_args` 与显式入参同时给（按显式入参跑一次并说明被忽略）。前两类把调用 id 记进"本轮未执行"集合，由同一条轮末退款通道退还预算。
- 跳针推进时清扫过了严格一跳的条目，并把被清的名字交给观测读数（`staged_swept_tool_ids`）：模型暂存过却再没调用，是"批量语义没生效"的唯一证据，清扫本身静默进行，没有这个计数就查不到。节点道它随请求 trace 整份落库；纯 CEO 回合的那份按跳重写，读到的只是最近一跳，所以跨跳要数缺口得靠下面那两格逐行计数。
- 每次调用实际走的道按 call id 记在执行行上（D15）：`execution_path` ∈ `normal` / `reused` / `corrected` / `illegal_reuse`，节点道落 `task_node_tool_result.payload`，前门道落阶段记录里的工具行。`corrected` 一词把两件相反的事混成一个数——把**同一份**已暂存的入参原样重发（该用 `reuse_args` 没用），和换了参数再调（`reuse` 会跑全部份数，本来就该重发）——所以另有一格 `staged_replay` ∈ `identical` / `new_args`，只在当轮确实为该名字暂存过时才写。判据是 `tool_impulse.staged_replay_kind`，摘要由调用方交 `tool_arg_stash.args_digest`（暂存条目里存的那个才是权威，另算一份就会在折叠规则变化时静默错配），两条车道共用同一份。记号只在知道真相的那一层写一次，两条车道都不许下游拿回执文本反推。第四格 `arguments_coerced` 记的是**参数名列表**：当次调用确实被读侧归一剥回过容器的那些参数。归一本身对模型不可见、回执文本里也不留痕迹，所以换一颗上游之后"容器档到底坏没坏"只能从这一格数；没剥过就不写这个键（空串不是一档状态）。`arguments_text` 保留模型那条原文，两者各记一件事、互不覆盖。侧表 `tool_argument_coercions` 按 call id 索引，列在 `LOOP_INTERNAL_RUNTIME_KEYS` 里，不进工具可见的 `__g3ku_runtime`。第三格 `reuse_flag_ignored` 分的是"打了 `reuse_args` 又同时给显式入参"（标记被忽略，按显式入参跑一次）与"根本没打标记"：两者同为 `corrected`，方向却相反——前者多是形状不允许（那颗工具的 `required` 里业务参数照旧必填，"只给标记"在模型看来就是非法调用），后者是模型的取舍；没有这一格，两种成因只能混着猜。

### 派发时预置契约

省掉「契约不在场那一跳」的唯一主动手段：派发方在派生时点名几个工具，运行时把它们的契约块直接写进目标节点的 bootstrap。

- 名单**只来自派发方声明**，入口只有 `spawn_child_nodes.children[].seed_tools`（父节点给每个子执行节点声明，可选数组，缺省即不预置）。前门没有这条车道：`create_async_task` 不带工具名单字段，根节点的契约照旧由投递那一跳交给它，节点从派发那一刻起有什么能力都由它自己的候选名单与契约在场判据决定。运行时也不给任何机械默认——按 node_kind 猜、按历史高频填都不做。猜错的预置是纯上下文浪费，而机械表会把一次猜测固化进持久历史。验收节点没有这条车道。
- 预置闸门读的是**治理登记表的按角色可见集**（`list_effective_tool_names`），而节点道那批内部工具（`send_message` / `view_message_history` / `enter_wait` / `view_node_tree` / `manage_child_nodes` / `list_child_nodes` / `read_child_progress` / `submit_final_result` / `spawn_child_nodes`）由 `NodeRunner._build_tools` 在登记表之后另行注入，不在那张表里；同名资源工具（如前门车道的 `send_message`，`allowed_roles: ceo`）在两张面上是两个对象。所以把这些名字声明进 `seed_tools` 一律落 `not_visible_for_role`。**这条回执只说「这份契约没预置成」，不说「该节点没有这项能力」**——节点照旧能用它，判别在场与否的永远是契约在场判据。派发方把回执读成能力判决，就会把节点间直接通信改写成共享文件轮询，这是本车道最贵的误读形状。
- "这个字段该怎么用"写在**工具级 description** 上（`SpawnChildNodesTool.model_description`），不是写在字段 description 上：`sanitize_provider_parameters_schema` 会递归删掉 parameters 里的每一处 `description`，实测到模型的 `tools[]` 里字段只剩名字和类型。字段级文案留在权威面（校验与治理读它），模型面靠工具级那一句——搬回字段里就等于删掉说明。
- 载体是**一条独立 user 消息、正文恰好一个块**。块头必须落在 `lstrip()` 后的第一个字符处，多块塞同一条只有第一个被认；块前垫任何说明文字都会让它认不出。不用 `role=tool`（没有配对的 `tool_use`），也不塞进 bootstrap 的那份 JSON payload——判据在 dict 上只取 `content` 键，且整串以 `{` 开头就不是块头。
- 落位在 `system + payload` 之后、每跳重写的活状态块之前，因此进的是稳定前缀。同一节点两次构造逐字节相同的前提是 **toolskill 源在这两次之间没变**：块在构建时现渲染，节点行里不存原文。
- 渲染复用唯一那条链（`get_tool_toolskill` → `build_tool_context_fingerprint` → `render_tool_contract`）。另写一份渲染或自算指纹的后果是在场判据认不出预置的那一份，而症状只是「节点仍然两跳」，一路没有报错。
- 预置只投递契约，**不写 `tool_arg_stash`**：没有入参可暂存，写了会让首跳的 `reuse_args=true` 命中一份不属于它的暂存。
- 陈旧块**不自愈**。在场判据按名字判、不按指纹判，所以 toolskill 源改动后该节点照旧首跳执行，只是读到一份过期契约；`stale_rev` 要同一视图里出现两个不同修订才有读数，也就是要等一次当前修订被投进来。新维护者常把它读成「旧块会被判不在场、自动重投」——不是这条。
- 两个字符上界（`NODE_SEED_CONTRACT_SINGLE_CHAR_LIMIT` / `NODE_SEED_CONTRACT_TOTAL_CHAR_LIMIT`）是**预算不是闸门**。外置判定只作用在 `source_kind=tool_result:*` 上，预置这条 user 消息根本不经过它，所以超限的后果是前缀变胖，不是块被换成信封。超限削名单，不上调上界。
- 丢弃必须回执。每个被声明的名字都出现在 `accepted` 或 `dropped` 之一，`dropped` 项带八种 `reason` 之一：`already_always_callable` / `unknown_tool` / `repair_required` / `not_visible_for_role` / `no_toolskill` / `render_empty` / `single_char_limit` / `total_char_limit`。优先级有两处不可交换：`unknown_tool` 与 `repair_required` 都早于 `not_visible_for_role`——拼错的名字与待修复资源在治理可见集里同样缺席，顺序反了就把「改名」「可以提示修复」两类不同的纠正动作都说成「这个角色用不了，别再报它」。判据按**目标节点角色**的实时可见集走，与名单来源无关。
- 回执落在派发方的工具结果里：`spawn_child_nodes` 在每个 child 结果上带 `seed_tools: {accepted, dropped}` 对象。两键恒在（`dropped` 为空时是空数组），但**只在派发方真的声明过时才出现**——没声明却回一份空回执，与「全被丢弃」在派发方看来同形。预置被拒不阻断派生；解析自身失败时回执整份缺席，只在节点行留 `seed_error`，不替读不出来的名字编原因。
- 两份读数落 `node.metadata` 并同步进 runtime frame：`seeded_contracts`（`tool` / `rev` / `chars`）与 `seeded_dropped`。派发时写初值，首跳构建时按**实际交付**覆盖 `seeded_contracts`、并把新出现的丢弃并进 `seeded_dropped`，于是「派发时就被拒」与「派发时被接受、构建时印不出来」在同一处看得见。帧字段按枚举过沙，写记录 / hydrate / 公开投影各建一份字典，漏一处不是报错而是**永远读不到**。
- 这两份读数在帧里是**写一次、后续继承**的量：首跳之后每跳的 `upsert_frame` 都不带它们，而枚举式 sanitize 会把"没带"补成空列表——不继承的话实时那一份就在首跳后被抹平，而节点行照旧是对的（两条面不一致时只有帧会骗人）。保留规则与 `messages_ref` 同源：写方没带就不换存量。
- 前门车道不接这条：长会话的首跳成本被后续几十跳摊薄，节点是每个节点都付一次。

### 交付被切割时的复开提醒

- 节点道上 `exec` 的交付被切割时，运行时在该条 exec 结果尾部附上复开方法（`ReActToolLoop._remind_content_open_reopen_on_exec_truncation`），使下一轮能按区间精确读取。触发判据取"模型没拿全"这一件事：`output_truncated`（内联额度切割）或 `stdout_truncated` / `stderr_truncated`（捕获环丢中段）。只判后两者会漏掉绝大多数实际切割——正文短于 64 KB 捕获环却超出内联额度时它们恒为 false。被切割的载荷同时已被统一信封外置，信封文本给的是 `content_open(ref=...)`；提醒里的按路径重开用于尚未外置的本地文件目标。同一结果重复处理不二次注入（按已写入的提醒文本幂等）。

### 参数错误与状态分类

- 校验之前有一步**读侧形状归一**：`g3ku.json_schema_utils.coerce_arguments_to_schema`（经 `Tool.coerce_arguments` 暴露）按工具的**权威** `parameters` 把"容器参数的 JSON 文本"换回容器本身。上游部分档位把 `array` / `object` 参数发成它自己那段文本，联合声明（`['string','array']`）尤其如此——模型两次都想发列表，差别只在到达形状，不剥就是让工具按字面量去读一个不存在的地址或路径。判据有四条边界，缺一条就会把"修形状"变成"猜意图"：只有声明里含 `array` / `object` 的参数才进入判定（声明是 `string` 的参数即便正文能 parse 成 JSON 也原样保留，否则消息正文、文件内容这类字段会被悄悄改掉）；只有严格 `json.loads` 成功且结果种类与声明一致才替换（`array` 声明收到 dict 不算）；只走顶层参数；`json_repair` 不参与——它会把半截值补成一个合法的容器，把传输故障伪装成一次内容错误的执行。剥不动的原样交回给工具，由被调用方的拒收文本点名真实原因（节点信箱那一层的档位划分见 `main-task-runtime.md`「信箱投递、重激活与上行传播」）。
  - `validate_params` 与 `execute` 必须吃同一份剥完的参数。校验放行一种形状、执行另一种形状，等于把刚修好的东西在台账里藏起来，也是这个仓库反复踩过的"读路径与写回不同源"。入参字典不被就地修改，归一返回新字典。
  - 四条调用道在校验前各接一次：节点 `ReActToolLoop`、CEO/frontdoor 直接工具执行、`ToolRegistry`、契约暂存道（`MainRuntimeService` 的 impulse 校验——暂存的形状与下一跳 `reuse_args` 真执行的形状同源）。DSML/参数块车道共用同一判据：`main/runtime/tool_call_repair._coerce_xml_parameter_value` 按声明类型的**成员**判容器档，而不是拿整串 `str(schema['type'])` 去等值匹配（联合声明在等值匹配下永远不命中，容器文本被原样放行）。判据与用例见 `tests/test_tool_argument_coercion.py`。
- 工具参数校验错误在 `ToolRegistry`、CEO/frontdoor 直接工具执行、节点 `ReActToolLoop` 之间共享同一维护契约，咽喉是 `g3ku/runtime/tool_error_guidance.parameter_error_guidance`：`validate_params(...)` 返回错误、`validate_params(...)` 自身崩溃，或工具执行抛出 `ValueError` / `TypeError` 时，错误文本保留原始错误，再按「本次错在哪 → 去哪儿看契约」的顺序追加修复材料。三条调用道都传 `tool` + 本次 `arguments` + 每次调用的 runtime payload，新增调用点必须同样传齐，否则指针分支会静默退化成加载模板。
  - 指针按工具与状态取三分支。资源工具（实例带 `_descriptor`）且其 toolskill **已在本轮上下文中**（当次请求视图的在场索引命中该工具名）→ 给出 `content_open(path="<descriptor.toolskills_main_path>")` 定点读，并明确不要再调 `load_tool_context`：同版本重复读取被节点道与 frontdoor 的重复守卫直接拒绝（文案「上下文中已有该工具当前版本的未压缩 toolskill，禁止重复读取」），把模型指向那条调用等于指向一堵墙。资源工具契约不在场 → 仍是 `load_tool_context(tool_id="<tool_name>")`（或直接调用它，那一跳交回契约）。无 `_descriptor` 的纯内部控制工具（运行时注入的 `spawn_child_nodes` / `submit_final_result`，门禁见 `tool-and-skill-system.md`「3.2 candidate tools」）没有任何可加载文档，不给指针，直接以 `Tool.parameters`（`validate_params` 拒收时用的就是它，不是可能被裁剪的 model-visible `model_parameters`）渲染必填参数名、类型、enum 取值与数组元素结构，**可选字段同样带类型**（`可选:start_line=integer(>=1),note=string`）：被 `X should be integer` 这类类型拒收打回时，只列字段名不给类型的契约等于把同一次猜测再让模型做一遍。整份契约有长度上限，超限或渲染不出必填项时退回泛化的核对入参提示。
  - 未识别参数名提示列出本次提交中 schema 未定义的键并给近似建议（上限 5 个）。它存在的原因是校验器只遍历 schema 认识的 `properties`、多余键被静默放过，所以键名拼错（`status`→`startus`）的表象是 `missing required status` 而不是"这个键你不认识"；该提示只补因果，**不改变校验结论**——这些键在提示前后都同样被忽略。
  - 提交里一个参数都没有、且走的是内联契约分支时，额外说明"参数 JSON 可能没有被成功解析"：`_normalize_tool_call_arguments` 与 `base_chat_model_adapter` 都把解析失败静默降级成 `{}`，从结果上无法与"模型真发了空对象"区分，不说破就会让模型逐字段去补一个根本没收到的参数串。这句只在内联契约分支出现，指针分支下不出现（那里下方没有结构可指）。
  - 这条分支链的不变式是"原地可修"：只提醒「核对必填项」而不给出必填项等于没有可核对的材料，给了必填项却漏掉被拒字段的位置（类型只写在必填一侧时，可选字段的类型错无从核对）同样等于没有材料，而指向一条必然被拒的加载链路比不指向更糟。运行时能等价补齐的部分不走到这里：大小写/空白的枚举、数字串行号、执行节点由 `status` 唯一决定的 `delivery_status` 在进校验器前就被 `_normalize_final_result_payload` 收掉，合同主体见 `main-task-runtime.md`「Node-Level Pause and Recovery」。权限错误、路径策略错误、超时停止、watchdog 停止、pause/cancel 信号与普通 `RuntimeError` 保持原语义，不误标为参数错误。
- 一条错误文本要保住它自己那跳的**原话**，还要在诊断需要因果时保住前一跳。`main/errors.describe_exception` 只渲染 `类型: str(exc)`，因此两类信息在它手里必然消失：`CancelledError` 这类 `str()` 为空的异常退化成裸类型名；在 `except` 体里抛出的新异常把原异常降成 `__context__`，于是「什么把什么顶掉了」读不出来。需要一手诊断的三个落点——交付给模型的结算文本、节点错误行正文、看门狗的取消诊断——用 `describe_exception_chain`，它按 `__cause__` 优先、其次未被 `from None` 抑制的 `__context__` 逐跳渲染，深度封顶并自环即停。`describe_exception` 保持单跳不动：它有二十多个调用点都在写日志标题与诊断 detail，全量跟链会让那些行暴涨，而它们本来也不需要因果。取消诊断的由来不靠异常自身携带，由 `tool_watchdog._attach_watchdog_cancel_reason` 写入、`read_watchdog_cancel_reason` 读出——`request_tool_cancellation` 的 `reason` 只流向 `cancel_token.cancel(...)`，在没有登记 cancel token 时会被整个丢弃，所以「谁因为什么中止了这个工具」这件事必须由看门狗自己留在异常上，否则到读者手里就只剩一颗无源的 `CancelledError`。
- 模型可见投影裁的是篇幅，不是判定：`Tool.model_parameters` 必须原样带上 `Tool.parameters` 在同一键位声明的边界约束（`minimum` / `minLength` / `minItems` / `maximum` / `enum` / `required`）。拒收按权威 `parameters` 判、模型只看投影，投影少一条边界就等于让模型去撞一堵它看不见的墙（`evidence[].start_line=0` 撞 `minimum: 1` 是实发形态，与「filesystem_edit 契约」里把 `start_line=0` 当自动填充噪声读是同一类噪声）。字段级 `description` 不要求镜像：`g3ku/json_schema_utils.sanitize_provider_parameters_schema` 在 provider 出口逐层剥掉 `parameters` 内的全部 `description` 并压平组合关键字，所以能到达模型的说明只有 `function.description`（工具级）与提示词 / toolskill 正文两处；把字段语义写进 schema description 是死文字。平价由 `tests/resources/test_control_tool_model_schema_parity.py` 对全部注入式控制工具断言，不靠注释维持；新增控制工具若重写投影，同一断言自动覆盖。
- 任何顶层为 `{"ok": false, ...}` 的结构化工具结果，在三条路径上都按 error-lane 工具结果处理；这条规则有意比参数引导规则更宽，让以 JSON payload 编码失败的内嵌工具也进入错误车道。

### 外置工具结果信封

- 超出内联闸门的工具结果统一外部化为 `artifact:` 内容引用，信封摘要对所有工具一视同仁（不按工具类别特殊化）：显式标注调用成败（`Tool call succeeded` / `Tool call failed`，成败由执行路径按 error-lane 判定后随投递元数据传入）、外置 ref、总行数与总字符数，要求用 `content_open(ref=...)` 读取完整输出，并附结果正文头部预览（6 行、≤800 字符）。信封不回显调用入参——入参是模型刚提交的内容，回显只挤占上下文并诱发「载荷过大导致调用失败」一类误读；嵌套信封的 canonical summary / origin ref 行保留。信封以 `content_ref` 形态进入上下文，重复外部化免疫（已是信封的结果原样透传）。
- 头部预览只露出结果**开头**，所以一次交付多个落点的工具把定位字段排在条目数组之前：`web_fetch` 的 `save_dir` / `summary` 就在 `items[]` 前面，整批结果被外置后模型当场还能看见落点目录去列文件，而不是必须先打开整份 ref 才知道文件在哪。
- 内联闸门另有一条按工具开的小例外：`_ALWAYS_INLINE_TOOL_RESULT_SOURCES`（`memory_note` / `create_async_task` / `task_failed_nodes` / `task_list` / `task_node_detail` / `task_progress` / `task_summary`）在结果不超过**一屏正文上限**（`OPEN_EXCERPT_CHAR_LIMIT`，16000 字符）时直接内联，让派发与验收那一回合当场看到结果，不必再花一次 `content_open`；超过该上限照常外置——同一颗 `task_node_detail(detail_level="full")` 实测可达 7,024,971 字符，无上限内联等于一次调用打穿上下文窗口。键的形态是 `tool_result:<模型面工具名>`，两处投递点（frontdoor 与节点 ReAct 循环）都按这个串生成 source_kind；写成资源目录名（`*_cn`）不会报错，只会静默永不命中，所以参数化用例直接按白名单自身取参（`tests/resources/test_resource_runtime_smoke.py`），拼错的条目当场变红，另有一条用例把键逐个对回 `tools/*/resource.yaml` 的 `name`。
- 二进制/图片内容目标另有一套展示契约：路径目标解不出 UTF-8 文本时，正文位置放占位串（`[二进制文件：…]` / `[图片文件：…]`），`content_describe` / `content_open` 结果随之带 `binary` / `content_display_replaced` 标记，`size_bytes` 是**磁盘真实字节数**，而 `line_count` / `char_count` 只描述占位串。读端不得用占位串统计推断文件的体积、类型或有效性——合法 PDF 与 34 字节空壳在文本通道里输出逐字相同；判定二进制交付物只能依据 `size_bytes` 与字节级证据。二进制目标上的 `content_search` 扫原始字节：结果带 `byte_level`、命中为 `byte_offset` + 上下文片段、`line_count` / `char_count` 归零，`%PDF` 一类签名可被实证，文本搜索的 `line` 语义对它们不成立。
- content 车道的**行号栏**是引用行号的唯一解释来源：`content_open` 的行模式（默认、`start_line`/`end_line`、`around_line`/`window`）与 `content_search` 的命中 preview，每行前缀 `N: `，`N` 是该目标的**绝对行号**，与 `rg -n`、编辑器、`content_search` 的 `line` 字段同一个数。不加栏的两类正文：字符模式（`start_char`/`end_char`，切的不是整行，标行号等于标一个假事实）、上一条的二进制/图片占位正文。首行超限的单行字符兜底仍带栏，那一段确实是目标的第 `start_line` 行。栏宽计入上限累加，所以"一屏正文"不会因为加栏被推过 `OPEN_EXCERPT_CHAR_LIMIT`；`excerpt_shown_chars` / `remaining_chars` / `total_range_chars` 仍只数原文字符，内联闸门与截断提示的读数口径不变。为什么必须有栏：交付物要求「路径 + 行号范围」类证据时，无栏正文只能靠肉眼数行，数错以两种形状出现——窗口起始行被当成第 1 行（偏移等于 `start_line-1`），以及 preview 的 `before`/`after` 上下文行没有号（偏移等于上下文行数）。判据是"被引行号能不能指回一次返回里带该数字的行"。模型侧与网页侧读同一份正文，实现不分支，节点详情抽屉与 CEO feed 同样显示行号。
- 只读测量通道 `filesystem_stat`：`paths` 逐条返回存在性、`size_bytes`（磁盘真实字节数）、`mtime`，目录另给 `file_count` / `total_bytes` / 最大最小文件与有界条目清单；只做 stat/遍历，不写不删。它是一条独立治理记录，`allowed_roles` 含 `inspection` 而写类工具不含——与 `write` / `edit` / `delete` / `propose_patch` 等写动作的 inspection 拒绝互不影响，验收节点因此能测量「这批产物有几个、多大、哪些是本轮写的、真实文件名是什么」，而不必依赖内容通道的占位串统计或凭清单外推文件名。同一套测量口径也写给**产出方**：执行节点「结束前自检」点名这个工具与验收只认的三类二进制证据（`size_bytes`、`binary` / `content_display_replaced` 与 `mime_type` 标记、`content_search` 的字节级命中）。只告诉裁判而不告诉选手，产出的证据形态天然不合规，代价是持续返工与重跑。

### 统一工具 Timeout 合同

- 每次工具调用都有最大运行时长保底：显式传入的 `timeout_seconds` 参数（秒，**支持小数/亚秒、无上限**；下限 `MIN_TOOL_TIMEOUT_SECONDS=0.05s`，更小的值抬到下限）优先，否则用全局默认（`agents.tool_default_timeout_seconds`，默认 600，热更新生效；`G3KU_TOOL_DEFAULT_TIMEOUT_SECONDS` 环境变量是应急覆盖）。参数名自带单位（`_seconds`）以杜绝秒/毫秒歧义：裸 `timeout` 名一旦被模型误当毫秒就会把上限放大千倍（想要 60s 却传 60000，在秒语义下 ≈16.6h，既卡住工具、又把失速判定截止一并推到同样 16h 之后，见 `heartbeat-system.md`「Task Stall Detection」）。解析只认 `timeout_seconds`，不读旧名 `timeout`（无兜底）。`timeout_seconds` 经 `Tool.to_model_schema()` 统一注入模型可见 schema，两类工具不注入：瞬时内部协议工具（`silent` / `time` / `schedule_wake` / `spawn_child_nodes` / `submit_final_result` / `submit_message_distribution` / `submit_notice_inspection_decision` / `task_append_notice` / `stop_tool_execution` / `process_kill`）与内部入队工具（`memory_update` / `memory_note`）带 `hide_universal_timeout_parameter`（按类属性声明，落在 `main/runtime/internal_tools.py`、`g3ku/agent/tools/tool_execution_control.py`、`g3ku/agent/tools/process_control.py`、`g3ku/agent/tools/memory_*.py` 与 `main/service/runtime_service.py`），不向模型暴露该参数，但机械保底仍然适用；长时编排/控制类工具带 `exempt_universal_timeout`，整体豁免外层时限（见下条）。
- 执行分工按工具标志三分：**自持工具**（`self_enforced_timeout`，持有子进程/网络会话、需要结构化收尾的 `exec` 与 `web_fetch`）自己消费统一解析后的有效值（执行层以 `timeout_seconds` 入参显式传入 handler）并负责收尾——`exec` 走进程树终止（Windows `taskkill /T /F`、POSIX 进程组 `killpg`，仅对进程组组长杀组，绝不误杀宿主进程组）+ 管道排空 + 部分输出抢救；单次调用墙钟有界 ≈ `timeout_seconds + 排空宽限`：`timeout_seconds` 约束「等进程退出」，进程退出后的尾部排空另有 `_POST_EXIT_DRAIN_GRACE_SECONDS`（5s）宽限——孙进程继承输出管道写端、管道迟迟不到 EOF 时，到点杀进程树释放句柄、返回已抢救的部分输出并打 `drain_timed_out` 标记 + 反应式指引（要常驻进程就 detach、把输出重定向到文件再轮询，别让它继承 exec 管道）；`web_fetch` 把统一值当作**整次调用**的墙钟（一次调用可带一批 URL）：到点即算，还没开跑的 URL 在自己的行里报预算到期，已开跑的 URL 只拿剩余预算喂给 `httpx.Timeout`（连接段另留 ≤10s 小分段），因此一次批量调用的耗时不随条数线性拉长。外层强制层对自持工具让位，但 pause/cancel 轮询照旧。**豁免工具**（`exempt_universal_timeout`）不叠加任何外层 deadline：`spawn_child_nodes` 在一次调用内跑完整个子节点流水线（含嵌套派生与验收节点），运行时长天然无界；`stop_tool_execution` 自带受控停止窗口，外层保底会与它赛跑并把停止动作中途掐断。豁免工具的合法中断途径只有任务级取消链（cancel_token 级联 / pause / stop）——这条链上的 pause 检查由看门狗每次轮询触发（`ReActToolLoop._on_tool_watchdog_poll`），而它本身是一次库读。**观测旁路失败不得升级为工具取消是这条链的通用规则，由结构保证而不是逐个回调包**：看门狗只有两个观测载体（`snapshot_supplier` 与 `on_poll`），二者一律经 `g3ku/runtime/tool_watchdog._safe_observe` 调用，非控制异常在里面降级成「这一拍没查到」并留下可数日志，永远到不了 `run_tool_with_watchdog` 的 `except BaseException`（那个分支的动作就是 `request_tool_cancellation`，一次存储抖动因此能把正在正常跑的长时编排工具连同其整批子节点管线取消掉）。哪些异常属于「节点该停」由调用方声明：`main/runtime/react_loop` 通过 `observation_control_signals` 把 `TaskPausedError` / `NodePausedError` / `DistributionHoldError` 交给看门狗——本模块不得反向 import `main.errors`，所以这个集合是注入进来的；新增观测回调时必须同样经 `_safe_observe`，并在需要停摆时把自己的控制信号加进这个集合。`asyncio.CancelledError` 等非 `Exception` 的 `BaseException` 永远冒泡，不在降级范围内。读侧另外按 `observation_only` 调用 `_check_pause_or_cancel`，让「读不到」与「读到了暂停请求」保持区分。取消动作的由来（`watchdog_aborted:<tool>`）通过 `_attach_watchdog_cancel_reason` 挂在异常上、由 `read_watchdog_cancel_reason` 读出，否则被取消的协程只能看到一颗无源的 `CancelledError`。标志由三条执行路径（节点 `ReActToolLoop`、CEO/frontdoor 直接执行、`ToolRegistry`）同等生效，包装层（`ManifestBackedTool` / `EmbeddedMCPTool`）透传该标志。**其余所有工具**由外层在 deadline 硬停（取消令牌级联 + 任务硬取消，无宽限），覆盖三条执行路径，包括验收（inspection）节点。
- 清单声明式 timeout 策略：`resource.yaml` 顶层 `timeout_policy` 块可声明 `exempt_universal` / `self_enforced` / `hide_parameter`（布尔），服务清单/内嵌 MCP 添加的工具——其 handler 是普通 `build()` 对象或 `execute()` 函数，通常不携带标志类属性。`ManifestBackedTool` / `EmbeddedMCPTool` 按「handler 属性 OR 清单声明」解析三个标志，OR 语义有方向性：清单只能追加 opt-in 特殊行为，不能撤销 handler 代码级已声明的合同。清单声明 `self_enforced: true` 要求 handler 自行消费 `timeout_seconds` 入参并结构化收尾（统一参数会并入 FastMCP 注册 schema），否则该工具处于无任何时限状态。
- 注册 schema 与实现签名的漂移防线：`EmbeddedMCPTool` 按注册 schema 构建 FastMCP 签名，FastMCP 会对每次调用做**默认值填充**——schema 里声明、实现不接受的参数（如退役残留的 `timeout_ms` 带 `default`）会被强注进每一次调用，让工具对所有入参组合无差别报错。防线有两道：构建期把「schema properties − handler 实际 dispatch 签名」的差集打成 WARNING（handler 带 `**kwargs` 时豁免）；执行期把 handler 签名不接受的参数过滤掉再调用（同一漂移键只告警一次）。契约测试 `tests/resources/test_tool_schema_signature_contract.py` 断言全仓 `tools/*/resource.yaml` 的 properties ⊆ handler 签名参数（含参数名卫生：非标识符且非关键字的键视为清单损坏）、自持 handler 必须接受统一 `timeout_seconds`，并复刻 `timeout_ms` 事故形态做回归。
- 工具级独立超时配置已并入本合同：`ExecToolSettings.timeout`、`AgentBrowserToolSettings.default_timeout_seconds`、`web_fetch` 的旧 `timeout_ms` 均已移除，统一模型可见参数是运行时注入的 `timeout_seconds`；`web_fetch` 的 `resource.yaml` `parameters` 块声明 `url` / `urls` / `max_chars` / `include_text` / `save_dir`（清单不得自行声明带上限的 timeout）；`skill-installer` 的下载/git 超时与 filesystem 校验子进程超时属于内部操作性超时，不在本合同内。
- 超时被停止的工具结果必须带延长指引：统一文案 `Error executing {tool}: timed out after {N}s ... 请在下一次调用时显式传入更大的 "timeout_seconds" 参数（单位秒、支持小数）`，亚秒上限按小数渲染（不压成 `0s`），由外层与自持工具共用同一构造器保证口径一致；该文案按 error-lane 处理，但**不**附加 `load_tool_context` 参数修复指引（超时不是参数错误）。
- 已知边界：同步阻塞型工具的超时只能在下一个 await 点生效；模型可传任意大 `timeout_seconds`（无上限是合同的一部分），串行化调度下的队头阻塞由 pause/cancel 兜底。`exec` 的两段等待都已有界（`timeout_seconds` 约束等进程退出、5s 宽限约束退出后排空，孙进程吊管道时到点杀树自愈），但「进程根本不退出」这一段的上限仍等于模型传的 `timeout_seconds`——短命令配大 `timeout_seconds` 会让卡死等到那个上限才自愈，故短命令务必配小值（无进度时长的失速提前告警属另一条防线，尚未接入）。

### 工具可重放声明（恢复车道档位）

- 进程被硬杀时正在跑的工具批，恢复后逐条决定"能不能替模型重放这一次调用"。唯一的判据是工具自己的声明：`Tool.rerun_safe` 类属性，或 `resource.yaml` 顶层 `recovery_policy.rerun_safe: true`（布尔）。两条车道与 timeout 标志同构，`ManifestBackedTool` / `EmbeddedMCPTool` 按「handler 属性 OR 清单声明」解析；代码内置工具（无清单目录的那批，如 `spawn_child_nodes`）只能走类属性。
- **缺省即最重**：没有声明的工具一律按"副作用可能已经落地"处理，判给模型裁定，运行时不代劳重放。这条是合同的全部价值所在——今后新加的工具（含用户装的、外部注册的）默认落在这一档，作者想让它可自动重放就必须先证明重复调用无危害再声明。本轮取不到该工具对象（契约不在场，实例还没进本轮执行束）同样按无声明处理。
- 声明放不轻两条代码判档，它们先于声明执行：`exec` / `shell` 固定交给模型；filesystem 写族按磁盘证据判，证据必须是**那次调用真正要产生的终态**，不是"目标那儿有东西"——`filesystem_write` 比正文与请求内容相等，`filesystem_copy` 比目标字节等于源字节（覆盖拷贝被打断时目标本来就在，按存在判完成会把半截正文钉成已结清、永不重试；目录拷贝一次 stat 证不了整棵树，因此走模型裁定），`filesystem_move` 要求目标在且源已消失，`filesystem_delete` 要求目标不在。能证才记 `verified_done`，证不了记模型裁定，"已经写对了"比"再写一遍"更安全。判档语义与整条恢复链路的其余部分归 `main-task-runtime.md`「Node-Level Pause and Recovery」。
- 一句声明要对应一种可证明的理由，而不是"看起来无害"：纯读（`content*` / `filesystem_stat` / `load_*_context` / `task_*` 读类 / `memory_note` / `perf_inspect_cn` / `time`）、写但按 `tool_call_id` 归键（`spawn_child_nodes` 命中父节点 `spawn_operations` 缓存）、写但**按调用方归键的替换**（`schedule_wake`：两条车道的写点都是"每个调用方至多一份待触发唤醒"——节点道以 `(task_id, node_id)` 为主键 upsert，前门道先把本会话 `self-wake:` 那一族摘掉再建，所以重放换掉的还是同一份，排不进第二次）、或重跑可由已有副作用证明（`filesystem_edit` / `filesystem_move` / `filesystem_delete`：恢复车道的 `recovery_check.py` 直接对磁盘现状取证，判 `verified_done` 就只补结果、不执行；编辑那条与工具自己的 `Already applied:` 用同一条判据）。会另起一行记录、再发一条消息、再排一个**新**定时器的那类（`cron` 的 add、`task_append_notice`、`create_async_task`、`memory_update`、`manage_task_nodes`、`model_config`、`skill-installer`、`task_delete`）都不声明——"排定时器"本身不在免死名单里，是"至多一份且按调用方替换"这个附加性质把它救回来的。全仓名单由 `tests/resources/test_tool_manifest_contracts.py` 钉住；工具作者在 `skills/add-tool/SKILL.md` 的清单里逐条对照。

### 严格纯文本打回与固定内置集合

- 节点车道（execution / acceptance）把纯文本回复判为未交付：交付只能由 `submit_final_result` 工具调用表达。纯文本到达时 `main/runtime/plain_text_reply.py` 注入打回提醒并自动续跑；连续 `_PLAIN_TEXT_REPLY_STRIKE_LIMIT`（3）次仍未改用工具，节点以 `failed + blocked` + `failure_disposition='pause'` 收口，即转入可恢复的错误暂停而不是正常交付。任何普通工具轮都把计数归零。提醒必须给出合法出口——继续调用普通工具（需要时派生节点）、直接 `submit_final_result`——否则打回会把没有可用出口的节点逼成死循环；提醒原文里写明"写计划、进度说明、下一步打算都不算提交"。`node_execution.md` / `acceptance_execution.md` 的纯文本条款与本合同同口径。
- CEO/frontdoor 的车道相反：前门把纯文本当交付，`normalize_model_output` 直接 finalize；派发后的 Reply naturally 尾注只做提示，不拦文本。两侧共用同一套 frontdoor/节点的提交合同（唯一调用、JSON 形状、`status` 与 `delivery_status` 各管一件事、`evidence` 行号、`failed + blocked` 必带 `blocking_reason`），正文只写在 `main/prompts/shared_final_result_protocol.md` 一处，两份提示词各经 include 取用（`main/prompts.py` 的 `_load_prompt` 展开，循环引用与目录逃逸都拒收）。
- 固定内置集合在两类车道上恒可调用，与历史里有没有前置工具轮无关：`submit_final_result`、`spawn_child_nodes`、`silent`、控制工具（`stop_tool_execution` 等）与上下文加载器（`load_tool_context` / `load_skill_context` 及 `_v2` 变体）；`memory_update` / `memory_note` 在前门同样不需要前置动作。`time` / `schedule_wake` 是另一族：它们没有 `tools/<name>/resource.yaml`，因此不在上面任何一份 fixed-builtin 常量里，而由 `SYNTHETIC_RESIDENT_TOOL_NAMES` 在两条车道的执行束里就地构造实例（"无需 load 也调得动"要落满五处，少一处的两种症状见 `tool-and-skill-system.md`「为什么"常驻"需要独立机制」）。两颗都不进契约在场读数，也不参与 `reuse_args` 暂存。其余工具沿候选 → 契约在场 → 提升的链条收敛（见本文「契约在场与 callable」）。`memory_note` / `memory_update` 这两类"模型对上下文动一次手"的调用不在回合卡里画工具行，改成右上角那条 live-only pill：读笔记显示 `已加载 note:<句柄>`（kind=`note`），写记忆按入队门返回的真实结局分两档（kind=`memory`，`risk-low` / `risk-medium`）；入队门不做内容判定，所以 pill 上没有"被拒绝"这一档，工具级失败两种 kind 都不出 pill。
- 内部轮次继承：当前 session 已有权威 frontdoor baseline 与前序 contract state 时，`heartbeat_internal` / `cron_internal` 不重跑 candidate/skill selection，而是直接继承上一轮的 callable / candidate / provider-tool / visible-skill 状态；从 agent 视角看，它们就是在上一轮 frontdoor contract 上追加隐藏内部提示后的普通 CEO/frontdoor 轮次。尚无权威 baseline 时，内部轮次回退到普通 exposure assembly。`cron_internal` 的其余特例只有两点：reminder 正文是隐藏的结构化 `system` 事件块；cron 任务的停止与删除由 scheduler 侧的 `payload.max_runs` / `state.delivered_runs` 计数器负责。
- 前门要区分两份工具集合：`tool_names` 保存可恢复的完整 callable pool；"当前轮合同暴露给模型的 callable tools"由前门 callable-tool helper 结合当轮可见集与契约在场再算一次。不要把前者直接当作当前轮模型可见函数列表，也不要把它同步成 provider `tools[]`（那份是按角色钉住的声明，见下节）。
- `compression_state`、`tool_arg_stash`（暂存载体与跳序）是受保护运行时状态：工具合同刷新不能覆盖、清空或重置这些字段。

### 钉住的 `tools[]` 与它的滞后出口

- `tools[]` 是按角色**钉死**的声明，不是当轮能力集：重印边界（token 压缩、手动压缩、空闲窗口第一跳）之前一个名字不增删，回合起点也不并入新增，换车道同样不重印（内部轮共用冻结清单、收窄落在执行准入）——节点道冻结分支的语义见 `tool-and-skill-system.md`「Provider Tool Surface」，前门与之同形。钉死期间 load 准入、提升准入与执行准入不受声明约束，各按治理实时可见读。清单滞后不影响安全：撤销当跳就拒（合同见 `tool-and-skill-system.md`「Provider Tool Surface」）。
- 滞后有两个方向，两个各有出口：**收回**方向名字还挂在 `tools[]` 上但已无权限，一次性 `[RUNTIME_NOTICE]` 的 `denied_tools` 提前点名，免得模型反复重试或改着名字试；**放行**方向名字能 `load_tool_context` 但参数表还没上清单——两条车道都用通知里的 `candidate_tools` 点名（前门在工具态收尾把治理实时放行、声明未吸收的名字并回候选；节点道候选池上界是每跳活的治理读）。mid-turn 注册的工具的完整生效链是四步，任何一环断了它就退化成"重印后才生效"：① 加载门槛的实时探针（`load_tool_context` 的 snapshot 门槛失败时按 `list_visible_tools` 实时复核，与 `load_skill_context` 的技能探针同构；RBAC 与 repair 语义仍由 `load_tool_context_v2` 下游强制）；② 投递准入按当次请求视图判在场，不加 candidate 快照门槛——回合起点算出的候选快照永远没有 mid-turn 注册的名字，拿它当门槛就造出"load 成功却调不动"；③ 执行准入只认本轮 callable（常驻内置 + 契约在场的名字；`_registered_tools_for_state` 按它取实例），声明里没 load 的名字这一步走投递路径；④ 模型调用的参数契约由块内正文承载——payload 自带 `parameters_schema` / `parameter_contract_markdown` / `example_arguments`，模型照它拼调用，声明等重印边界才吸收参数表。常驻内置不进在场判据的规则在 ②③ 两处都保留。
- `undeclared_candidates` 每次渲出都意味着"模型手里有一个可加载的名字而没有它的参数表"。它是发现出口的形态，不是常态：非空持续出现说明钉住规则该在压缩跳把那张参数表带上。这条差集由 `tools[] − 契约在场 − denied_tools − 控制工具` 定位（`callable_tools` 那行已从两个尾块删掉，尾块因此不抄整份候选表，也不另抄一份 callable 名单）。拿不到本次声明名单的装配路退回渲全量候选，判据在 `g3ku/utils/helpers.py:render_candidate_tool_line` 一处，两条车道共用同一份文本。
- **参数表的字节也走同一条滞后**：`tools[]` 里那份 `function.description` / `parameters` 的权威来源是钉住整表，不是当轮实例（来源、三档计数与两种重建次序见 `tool-and-skill-system.md`「Provider Tool Surface」的「参数表的来源」）。于是 Tool Admin 改一颗工具的参数定义，在跑会话与在飞节点到下一个重印边界才拿得到新字节——边界那一跳渲染才读实例。运营侧的读法：改完参数立刻在同一条链上取请求体，看到的仍是旧字节，这不是 bug；`wire_tool_schema_item_hashes` 里那个名字的逐名哈希变了，才说明边界到了。同一条滞后也管那颗合成控制工具（`silent`）的文案：它们的整表字节是类内常量，改它们的代码要等边界。
- **模式与授权不进工具说明**：exec 的 `function.description` 不写 `execution_mode`、`allowed_roles`（也不写"有/无 guardrails"这类模式同义词）。`tools[]` 按重印边界钉住，把模式写进说明就是第二份权威且切模式后不刷新；唯一权威是运行时合同里的 `exec_runtime_policy:`（前门与节点都钉在头部快照，变化由一次性通知纠正），执行侧按治理记录逐次判。两条车道共用同一个 `model_description`（`g3ku/agent/tools/shell.py`），改这里即两车道同步。

## 2. 一条从上下文到 callable tools 的链路

1. 节点/CEO 进入一次新 turn。
2. `runtime/context` 模块根据 query、历史、治理规则挑出候选工具/技能。
3. prompt builder 把它们以 candidate 列表形式展示给模型。
4. 模型要用某候选工具时，可以直接调用它，也可以先 `load_tool_context(tool_id="...")` 读说明——两条都不被拦。
5. 契约块不在这一跳的请求视图里时，这一跳不执行：返回该工具的契约块，校验通过的入参同时暂存（治理实时可见是前提；本回合候选命中，或回合中途注册、由加载门槛的实时探针放行）。
6. 下一跳契约块在场 ⇒ 该名字进本轮 callable（= 常驻内置 ∪ 在场名字），可以直接调用；要跑上一跳那批入参就带 `reuse_args=true`。
7. 调用真正执行的那一跳，工具才产出它自己的结果。

四条不变量：

- “看得见名字”不等于“这一跳就执行”：契约不在场时那一跳交回契约，不产出结果。
- “调用被受理”不等于“这一轮已经执行”——投递那一跳同样返回 `ok` 形状的回执。
- “RBAC 可见且 surfaced”是**授权**面，在场是**能力**面，两个都得成立才真执行。
- prompt 里的候选池与实际 callable tool 集合是两套集合。

frontdoor 边界：

- frontdoor 的 callable tool 集合不只来自 fixed builtin，还包含当次请求视图里契约在场的那些名字；`candidate_tool_names` 是"已授权 − callable"。一个工具同时出现在 candidate 列表和在场名单里，说明同一跳算了两次判据。
- 在场读数按**每跳装配后的请求视图**重算，写点在 `call_model`：`prepare_turn` 每回合只跑一次，本轮 `load_tool_context` 的工具行只在后续跳进入请求。读数随完成态快照落进 `.g3ku/web-ceo-continuity/<session>.json` 的 `frontdoor_selection_debug`（白名单装配），CEO-only 回合没有 task/node 帧，这份侧车是它唯一的落盘点；`contract_present_tool_names` 是装配前交给 builder 的输入，与读数各算各的，两者不一致不表示判据分裂。
- 排查"`load_tool_context` 之后仍调不动"：先看当次请求视图里那块契约的**抬头**是否真的在（`tool_contract_presence` 读数，落在 `frontdoor_selection_debug.tool_contract_presence` 与 runtime frame 的 `model_visible_tool_selection_trace.tool_contract_presence`），再对照 `tool_names` / `candidate_tool_names`；稳定 bootstrap 文本与当前 snapshot 冲突时以 snapshot 为准。模型反复对同一 callable / fixed-builtin 工具再次 load 时，先检查消息历史里是否还保留同一 resolved `tool_id` 且 fingerprint 未变化的未压缩结果——那是预期中的 duplicate direct-load 软拦截，不是 registry 丢失。
- 线上 frontdoor 表现与测试 helper 不一致时，先确认 runner 是否真的走自研步骤循环；生产只有这一条执行路径。

节点边界：

- 对执行/验收节点，当轮合同作为一块尾部注入：`node_runtime_tool_contract` 承载 callable / candidate / 修复名单与 `denied_tools`，后面才是当轮 turn-only note。skill 全量名单钉在节点 system 首条（与会话道同一渲染函数、同一 epoch 语义），重印点之间新变为可读的 skill 走一次性持久提示，合同见 `tool-and-skill-system.md`「Pinned Static Declarations」。稳定 bootstrap user JSON 只保留稳定节点上下文。与运行时合同同轮出现的 overlay / repair overlay 只允许作为 request-tail 临时消息追加，不原地改写 bootstrap user 或任何更早的持久化消息，否则破坏稳定前缀与 prompt cache 命中。
- `candidate_tool_names` / `candidate_skill_ids` 是唯一 gate truth source；`candidate_tool_items` / `candidate_skill_items` 只是描述文本投影（`candidate_skills` 不渲染进合同正文，payload 字段保留供派发侧消费）。canonical 列表为空时，重建后的合同也必须把 `candidate_tools` / `candidate_skills` 渲染为空，不从旧 contract item 列表或旧 frame item 缓存复活失效候选。
- 恢复链路：restored `selected_tool_names` 保持“恢复的 callable 工具 ∪ 恢复的 candidate concrete 工具”，不塌缩成“仅 callable”，让下一轮 node tool-provider 能把两个集合一起交回 schema selection；node tool provider 也要把恢复的 candidate executors 作为可见工具暴露，即使当前只有 `callable_tool_names` 立即可调——否则一次成功的契约投递就可能把下一轮候选池清空，后续 `load_tool_context(tool_id="content_open")` / `load_tool_context(tool_id="filesystem_write")` 会在人为缩小的候选集上失败。暂存载体与跳序随 `node.metadata` 一起活过 pause/resume，恢复后的第一跳仍按严格一跳判它。
- 区分“当前轮对模型暴露的 callable 合同”与“内部可恢复的完整 callable pool”：前者是当轮真正下发的名单；后者只保留在本地 `model_visible_tool_selection_trace.full_callable_tool_names` 供排障。节点 `runtime frame`、动态 `node_runtime_tool_contract` 与 `runtime-frame-messages:{node_id}` artifact 必须写入同一份 callable 列表；三者不一致按运行时合同分裂排查，而不是先怀疑 prompt 文本。frame 与重建合同对 skill 候选也必须一致：`candidate_skill_ids` / `candidate_skill_items` 在 frame 中存在时，不应因 `token_compression` 的窗口裁剪而在下一轮合同中无故清空；但“从 frame 恢复”的前提是 frame 本身已是 authoritative skill-contract frame——当前 frame 只是初始化的默认空字段、而本轮已携带 fresh skill 合同时，rebuild 必须优先保留 fresh 合同。

CEO/frontdoor 合同载体：

- `turn overlay` / `repair overlay` 属于 dynamic appendix 一侧的当前轮临时内容；请求体中它们排在全部携带正文之后（尾部），不能回写已有 stable/request user 消息。
- `dynamic_appendix_messages` 的持久化形态只保留当前 `frontdoor_runtime_tool_contract`；retrieved context 这类需要在同一 turn 后续模型轮次保留的内容，留在 `messages` / frame 的重建链路里，不作为第二份 appendix 尾插。每个 provider-bound request 在动态区域只携带一份最新 contract：每轮重建先剥掉携带历史里的旧 contract 与 turn-only note，再把当前 authoritative contract 追加到请求体尾部（为什么必须在尾部、断点在哪儿的判据详见 `context-and-cache-troubleshooting.md`「同 turn 的 append-only 规则被破坏」）；turn 结束写回 durable transcript 时全部剥离。同一 turn 内，最新摘要块就是权威合同。
- 模型面向的运行时合同由头部快照 `## Runtime Contract (pinned)` 与一次性 `[RUNTIME_NOTICE]` 组成（旧 `## Runtime Tool Contract` 尾块已退役，识别/剥离仅用于旧 transcript）（运行时元数据、非对话内容：线体只允许一份 system 且必须在首位，中段注入用 system 会被严格网关 400，用 assistant 又会让模型把它当成“自己上一轮说过/发给用户的消息”；角色合同见 `context-and-cache-troubleshooting.md`「线体角色合同」），用紧凑文本向模型解释 candidate / 修复 / 附件 / 临时目录 / 执行策略（头部快照或一次性通知；旧尾块已退役）与 `denied_tools`（旧尾块的活状态段，现在由通知承载）；provider 原生 callable schema 仍走 provider `tools[]`。静态行为规则（`load_tool_context` 怎么用、别复读 toolskill、候选 skill 不走契约块、静默没有文本写法、临时目录落盘纪律）不在这里重复——它们只在基础提示词说一次，实测发送体 system 头部携带；一处规则一个载体，压缩块里才不会只剩唯一权威。合同识别有一条硬不变量：运行时注入的合同消息从不携带 `tool_calls`，因此任何携带 `tool_calls` 的 assistant 消息都是模型回合本身——即使其文本回显了合同抬头或合同 JSON，也不得判为合同消息而剥离，否则该回合只剩孤儿工具结果，会触发节点孤儿子工具结果熔断。execution / acceptance 节点使用同样的摘要式合同车道：详细 provider-call schema 留在节点 `provider_tool_names` 与 provider `tools[]`。摘要块还可携带：`attachment_reopen_targets`（runtime-owned 的上传 reopen 元数据，覆盖当前轮与 transcript 历史上传，是模型可见引导，不是浏览器/UI 表面；`kind=audio` 刻意不进这条车道——语音的内容已在正文转写里，音频句柄只服务气泡回放，见 `speech-to-text.md` §3；创建 detached 任务需要 reopen 上传文件/图片时，模型应把精确目标字符串抄进 `create_async_task.file_targets`，运行时不自动注入任务记录）；`repair_required_tools` / `repair_required_skills`（agent-facing-only 的修复车道，让模型看到“先修复再使用/查看正文”的资源，而不误读成普通能力）；`session_temp_dir`（CEO 会话级临时目录的绝对路径，仅在运行时解析出会话临时目录时渲染；落盘纪律只在 `ceo_frontdoor.md` 说一次，并反过来指向这里给出的路径；交付落点（含默认落点）归 `tool-and-skill-system.md`「Model Path Anchoring Contract」，模型侧从同一条 `path_anchor_rule` 读到它；目录解析见 `runtime-overview.md`「任务侧」）；`path_policy`（含 `path_anchor_tokens`：`{workspace}`/`{temp}`/`{data}` 三个 token 恒定列出）同在头部，落点规则本身归 `tool-and-skill-system.md`「Model Path Anchoring Contract」。两类候选的不对称语义口径：`candidate_tools` 是 candidate executor 摘要，通常仍需 `load_tool_context(...)` 后等待下一轮 hydration/promotion；`candidate_skills` 是 loadable skill 摘要，列出的 `skill_id` 应直接理解为 `load_skill_context(skill_id="...")` 的正文入口——这套措辞由基础提示词承载，块里只给名单。
- CEO/frontdoor 还把下一轮 body baseline 持久化为 session-owned 的 `frontdoor_request_body_messages`：body-only，写回 session state 时剥掉动态 `frontdoor_runtime_tool_contract` 消息，让下一轮重建一份新的权威尾部合同。fresh visible CEO/frontdoor turn 通过直接 continuation 路径消费这份 baseline；在记录任何显式 shrink 原因之前，fresh visible turn 却从 transcript 重建，就是 frontdoor continuity bug。direct-reply turn finalization 必须保住这份权威 baseline，并在 session sync 前追加最终 assistant 回复。baseline 变短只在 `token_compression` 这一种自动理由下合法（外加操作员的 `user_edit_truncation`）（记录在配套的 `frontdoor_history_shrink_reason`）；没有这两个理由的变短按运行时上下文丢失处理，不是正常合同重建。
- approval interrupt 与 pause/recovery payload 携带这些 runtime-owned frontdoor 字段：`frontdoor_turns`、`compression_state`、`tool_arg_stash`、`tool_call_payloads`、`frontdoor_selection_debug`；恢复后丢失按“frontdoor runtime contract / runtime state 损坏”排查。

排查顺序：

- 当前轮合同先看 request 动态区域中唯一的 `frontdoor_runtime_tool_contract`，它排在请求体尾部；再看 internal state 的 `tool_names` / `candidate_tool_names` / `candidate_tool_items` 与 `tool_contract_presence` 读数；稳定 prompt 前缀、旧 overlay 文本、旧 transcript 里的 tool/skill 名单都不是当前轮权威合同。“load 成功但下一轮没调用”时，对照 canonical runtime frame / frontdoor state 与 runtime messages snapshot；旧 bootstrap 文本与当前 snapshot 冲突时，以当前 snapshot 为准。“某工具为什么没进前门候选集”看 `frontdoor_selection_debug.tool_selection`（命中项为什么没进 `candidate_tool_names`）。
- 排查 CEO/frontdoor cache drop 时区分：`messages` 保存的是“下一次重建 request body 的基线”，`dynamic_appendix_messages` 只是“当前轮唯一尾部合同”；两边都出现完整候选/合同副本，说明 runtime contract 重复注入。

优先级边界：

- 前门动态提示里的“如需完整 workflow 正文可调用 `load_skill_context`”“如需工具契约可调用 `load_tool_context`”与固定内置集合同口径：加载器与记忆工具随时可调，不需要任何前置动作；能否调用普通工具只看当轮 callable 名单与契约在场。

- restore / recovery 只接受 frame 或 CEO/session state 中的 canonical callable / candidate / `tool_arg_stash` / skill 字段；缺失时直接视为“运行时工具合同损坏/缺失”，不回退 bootstrap 或旧动态文本。
