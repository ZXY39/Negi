# Negi External Agent API 架构说明

本文档是 External Agent API（`/api/v1`，渠道无关的 headless agent 面）的唯一契约归属文档。渠道通信重建的第一期产物：默认保留 web 会话，IM 平台接入交给第三方桥接应用，g3ku 只暴露本契约。

## 1. 定位与边界

- 消费方是第三方桥接应用（IM bot、自动化桥）；唯一内置例外是官方 QQ 适配器（见「内置官方 QQ 适配器」），它同样只经本契约消费。web CEO 面（`/api/*`、`/ws/ceo`）不受本面影响。
- 本契约之上另有两个开箱即用的 agent 对接面（OpenAI 兼容端点 `POST /api/v1/chat/completions`、MCP stdio 网关 `negi mcp serve`），契约详见 `agent-gateway.md`。
- 平台协议、消息分段、频控、触发词识别全部属于桥接层；g3ku 核心不出现随平台变化的代码。判别准则：换一个 IM 平台就要改的代码不属于核心。
- 参考实现：`bridges/qq-onebot/`（独立包，零 g3ku import，行为对拍表见其 README）。

## 2. 启用与鉴权

- 配置段 `externalApi`：`enabled`（默认关，显式 opt-in）、`tokens`（bridge_id → `{token, label, enabled, crossSession}` 的字典）、`eventBufferSize`（每会话事件环形缓冲，默认 512）。
- token 密文走 bootstrap secret overlay 三件套（保存时剥离、落盘只留占位、解锁时回填）；配置文件落盘时 `tokens[].token` 剥离进覆盖层。
- 请求带 `Authorization: Bearer <token>`；`require_external_api` 依赖（`g3ku/runtime/api/external_auth.py`）做常量时间比较，匹配启用的条目即注入 `bridge_id`。enabled=false → 403 `external_api_disabled`；token 缺失/错误 → 401。项目锁定仍由全局 423 中间件兜底。
- 作用域**只按号裁决**，判据在鉴权依赖里算好一次，之后每条车道按它分支。`cross_session` 取自 `tokens[].crossSession`，是布尔、**默认放开**，没有全局档也没有继承态。
  - **关闭时**：一个桥只看得见/操作得动自己 `bridge_id` 名下的会话，别名一律 404 `session_not_found`（不区分"不存在"与"不属于你"）。
  - **开启时**：`GET /sessions?scope=all`、`GET /sessions/{id}/state`、`GET /sessions/{id}/events`、`POST /sessions/{id}/messages`、`POST /sessions/{id}/cancel` 认全部真实存在的会话键——别桥的注册会话，或有转录文件的 `web:*` / 渠道会话键（没有转录就 404：拿到 token 的人不能凭空造一个新会话键）。跨桥寻址产生的条目把 `bridge_id` 记成**发起方**，所以那一轮的归属、幂等位与回复路由都跟着发起它的那个桥走，不落到目标会话原来的桥名下。
  - **不受作用域放宽影响的车道**：`PATCH /sessions/{id}`（改名）、`DELETE /sessions/{id}`（清除）、`POST /sessions/{id}/outbox/{outbox_id}/ack`（销账）始终只认本桥名下——注册表生命周期与账本归属不能由第三个桥代管，这条界线由 `tests/resources/test_external_api_session_scope.py` 钉住。判据分两个函数（`_resolve_entry` 放宽、`_own_entry` 不放宽），别在一处合并它们。
  - 为什么默认开：这条车道本来就要 operator 亲手签发 Bearer 且服务只绑回环，"能拿到 token"与"能读机器上的会话"之间没有新的信任边界；跨桥读写需要单独 opt-in 只会让每个桥都去申请一个全权 token。
- 管理面：Web「外部接入」页（`g3ku/web/frontend/org_graph_external.js`）背后是 `main/api/admin_rest.py` 的 `/api/external-api/settings`（GET/PUT，总开关与缓冲大小）与 `/api/external-api/tokens`（POST 签发——自定义 token 可省略、省略时服务端自动生成，与存量 token 重复返回 409 `token_exists` / PATCH 改 label·enabled·`crossSession`·`regenerate` / DELETE）。面板只在每个 token 行给一颗「可会话范围」下拉（全部会话 / 仅本桥），没有面板头的全局档。`crossSession` 的写判据按 key 存在与否、不按真值：`false` 是真要关；显式传 `null` 回 400 `invalid_cross_session`（把跨会话请求静默折成 `false` 会悄悄关掉这一号）。明文 token 只在签发/重新生成的响应里返回一次，其余读取只回掩码；保存走统一的 `save_config` + overlay 剥离链路。契约由 `tests/resources/test_external_api_admin_tokens.py` 锁定。只读诊断命令 `negi external status` / `negi external sessions` 提供掩码与注册表视图（锁定时显示占位提示），供 shell 与 agent exec 验收连通状态。渠道对接总纲（架构边界、token 交付纪律、协议速览、新桥构建清单、排障）由 skill `skills/negi-bridge-onboarding/` owning，其中 `references/integration-manual.md`（接入手册：curl 样例与事件/错误码参考）、`references/building-a-bridge.md`（适配层编写指南）为权威正文；web CEO 目录对 `ext:*` 会话只读分组展示，详见 `web-and-admin.md`「External Agent API」段。

## 3. 会话注册表与 key 命名空间

- `ExternalSessionRegistry`（`g3ku/runtime/external_sessions.py`）维护 `(bridge_id, external_key) ↔ session_key` 双向映射，原子持久化在 `.g3ku/external-sessions/registry.json`。条目另带 `title` 与 `hidden`：`title` 是该会话的显示名，群记忆作用域按它命名，网页会话栏的「命名」也写这个字段（两条写入口落同一格：本 API 的 `PATCH /sessions/{id}` 与网页管理面，见 `web-and-admin.md`「Channel Session Clear Contract」）。`hidden` 只是网页列表上的隐身标记，映射照旧参与路由。谁打这个标记见 `web-and-admin.md`「Channel Session Clear Contract」；摘掉它有两条车道——`resolve_or_create` 命中既有条目时，以及 `ExternalTurnService.submit` 收到该会话的入站回合时。后者是必需的：MCP 网关把 `conversation → session_key` 缓在进程内，命中缓存时不 `POST /sessions`，只长在注册车道上的判据对这种桥永不触发。两条车道摘完标记都尽力推一次全局 `ceo.sessions.snapshot`（`external_v1._publish_ceo_catalog_best_effort`），否则网页要刷新才看得见。**出站重放不摘标记**：`_route_external_outbound` 与 60s 对账会把无人 ack 的滞留记录反复重新注入，按出站判定的话整批隐身行在一分钟内就全复活了。`/api/v1` 的读写面不受该标记影响——桥看得见、也发得进自己名下每条会话。
- session key 形态 `ext:{bridge_id}:{sha1(external_key)[:16]}`（文件名安全；键里不含外部标识原文，真相只在注册表）。`build_external_session_key` 的 digest 长度参数只是注册表碰撞逃生口。
- `POST /sessions` 按 `external_key` 幂等 get-or-create；转录复用共享 `SessionManager`（`sessions/ext_*.jsonl`），无独立持久化机制。首次创建成功与 `PATCH` 改名成功后，以尽力而为方式向 web CEO 端推送一次全局 `ceo.sessions.snapshot`（web 运行时未就绪时静默跳过，不影响接口返回）——浏览器只在页面加载时拉取 REST 会话列表，新渠道会话的实时可见性依赖该推送。
- `ext:` 前缀在 `session_agent.py` 的 frontdoor 连续性前缀表中。目录分组与「历史不可改」两轴收口在 `g3ku/runtime/session_keys.py::is_channel_session_key`（legacy `china:` 归档同语义）。第三轴「能否向该会话投递输入」由注册表决定，与只读判定无关：`/ws/ceo` 对 `ext:` 会话按 `get_external_session_registry().get_by_session_key()` 解析一次（连接期），有条目即接受网页输入、按「回合契约」提交，无条目（`china:*`、注册表丢失的孤儿转录）回 `channel_session_readonly`。
- 会话 key 编解码的规范实现位于核心模块 `g3ku/runtime/session_keys.py`（`china:*` 格式与历史转录字节级一致，存量转录保持可读）。
- 注册表条目与转录文件是两个轴，`GET /sessions` 的每一项因此带 `has_transcript`（判据=该会话键在 `SessionManager` 里算出的转录路径存不存在，两个档位都有：`scope=all` 并进来的本地行同样带）：桥一注册就有线上条目而还没有转录，网页侧「删除渠道会话」则相反——转录照清、条目按该桥在 `externalApi.tokens` 里还有没有条目决定留着打 `hidden` 还是整条摘掉（两种出口与闸门见 `web-and-admin.md`「Channel Session Clear Contract」）。
- `GET /sessions?scope=all` 是**另一份形状**：它不读注册表，而是复用网页侧的会话目录装配（`ceo_catalog_offload.build_ceo_session_catalog_async` → `web_ceo_sessions.build_session_summary`），因此每一项直接带 `preview_text / message_count / updated_at / is_running / status / session_family / session_origin / can_message`，再加一个 `transcript_path`。这么切的理由是"别开第二条枚举道"：网页侧已经有带 TTL 缓存、在专用线程里跑的全量装配，重写一份按注册表枚举的会既看不见 `web:*` 会话又要自己处理数十 MB 的转录遍历。代价照旧——目录构建遍历全部转录，必须留在那条卸载车道上，不许搬回事件循环。
  - store 取的是**运行时那一份** `agent.sessions`（没有活运行时时才退回新建实例）。新起一个 `SessionManager` 指向同一目录是这条道最贵的错法：目录构造逐键 `get_or_create`，异常被 `except: continue` 吞掉，结果是一份**空 items 配 200 状态码**，看不出任何失败痕迹。
  - 目录把 `items`（本地 `web:`）与 `channel_groups`（渠道会话）分两半给，本接口把两侧合进同一个 `items` 返回，"全部会话"才真是全部。
  `transcript_path` 由运行时算出（含 `safe_filename` 转写与键长超限的 digest 逃生），调用方不得自己把 session key 拼成文件名。没有跨桥作用域时该参数回 403 `cross_session_scope_required`，不带 `scope` 的请求仍是本桥名下的注册表视图。

## 4. 回合契约

- `POST /sessions/{id}/messages` 异步提交：空闲 → 启动回合并返回 `{turn_id, status:"started"}`；会话被 hold（有回合在跑、该会话正在跑一次手动上下文压缩，**或上一回合的收尾尾段仍在进行——running 已复位但回合锁仍持有**）→ `queue_follow_up_batch` 排队并返回 `{status:"queued", receipt:"收到，将在当前任务中一并处理。", running_turn_id, queued_position}`。后两个字段是给调用方在**提交那一刻**分辨"追加还是撞车"用的：`running_turn_id` 就是你排在后面的那个回合（要停它走 `pause`/`cancel`），`queued_position` 是入队后的序号。渠道不因此丢消息：排队条目以转录 `pending` 行为 durable 记录，会话回到空闲后由派发通道发出（合同见 `runtime-overview.md`「压缩窗口：入站闸门与基线写入仲裁」）。
- `GET /sessions/{id}/state` 除运行档位外，还给"在不在动 / 在做什么 / 有没有在跑的任务 / 这轮怎么结束的"四档读数，合同与时间形状纪律见本节末「会话状态读数」。
- `GET /sessions/{id}/turns/{turn_id}` 按回合 id 回读**转录里那一行的可见原文**（`text`/`created_at`/`usage`/`task_ids`/`source`/`silent_reply`）。判据是 assistant 行上的顶层 `turn_id`（落盘时写入），**它不等于外部提交回包里的 `turn_id`**——调用方要用 `reply.final` 带出的 `transcript_turn_id`，所以它 durable：调用方自己的上下文被压缩之后仍能取回原文。没有转录 → 404 `session_not_found`；有转录但该回合没存过 → 404 `turn_not_found`。内存里的 `TurnRecord` 只留 256 条终态记录且会淘汰，**不能**当历史读口用。
- 执行走 `SessionRuntimeBridge.prompt/prompt_batch`（与 web/CLI/cron 同一语义基座）。
- 提交方可以是 HTTP 桥，也可以是 `/ws/ceo` 的网页输入车道（进程内经 `get_external_turn_service()` 调 `submit`，不经 Bearer 鉴权中间件）。两条发起方共用 `submit` 这一处裁决：入站 hold、幂等位（网页发起方不带 `Idempotency-Key`，`duplicate` 分支对它不可达）、排队回执、以及「回合契约」的终态不变量。回合的出站能力长在车道上而不是发起方上：`make_session_event_relay` 只在 `_execute_turn` 挂载，所以网页输入必须走这条车道，否则 hub 上没有 `reply.final`，表现为「网页看得到回复、渠道端什么都没有」。这条车道上产出的每条可见回复在进 hub 前都登记进持久账本并带上 `outbox_id`，因此"当时没有消费者"只是延迟而不是丢失（判据与重放见「持久 outbox」）。
- 出站只承载 agent 回复与主动推送：**发起方的用户消息不回显到渠道**（事件集合里没有 user-echo 类型，投递它需要经总线走 `outbound.created`，那是主动消息额度）。网页在渠道会话里的接管只在转录与 web 侧可见。
- **终态不变量**：每回合在全部路径上恰好发一个 `turn.completed` 或 `turn.failed`；`asyncio.CancelledError` 单独捕获、先发终态再上抛（缺终态曾卡死旧宿主的按会话串行队列，此为硬契约）。`turn.failed.error` 是用户可读全文（空则回退友好文案），`detail` 供排障。失败不作废这次提交：该输入在转录里保持未回答态，由下一个可见用户回合接回后回答（状态机见 `context-and-cache-troubleshooting.md`「残留 paused / pending 转录条目与未回答的用户输入」）。**失败必须对用户可见**：`RuntimeAgentSession._prompt_locked` 的终态失败支在把可读正文写进 `latest_message` 与转录之后，用同一个字符串调 `publish_channel_notice`（`g3ku/runtime/external_sessions.py`）投一条渠道通知，门件是会话键属 `ext:`（只有这条车道有投递路径）且正文非空——用户轮与 cron/heartbeat 内部轮共用这一处，两条发起方（渠道入站、网页接管）也共用；暂停与取消按 `turn.completed(cancelled=true)` 收尾，结构上落在 `except Exception` 之外，因此不推。宿主侧的机器判据仍是 `turn.failed`，通知是给人看的那一份，二者同一次失败各一份、不互相替代；投递形状与登记见「出站路由（主动推送）」。
- 排空兜底：prompt 返回后循环 `drain_queued_follow_up_messages` → `archive_follow_up_chain_transition` → `prompt_batch` 续跑，整条回合链对外只有一个终态。`prompt_batch` 只以批次最后一条输入驱动回合，较早输入的内容块在请求构建期并入（合同见 `runtime-overview.md`「prompt_batch 批次回合内容合并」）。
- 回合任务以 `register_task(None, task)` 注册：以真实 session key 注册会在暂停时被 `cancel_session_tasks` 的 gather 自聚集死锁。
- `Idempotency-Key` 头去重（进程内有界映射）：同会话同键重复提交返回 `status:"duplicate"` + `original_status`——原回合记录仍在则回报其状态与 `turn_id`；排队条目回报 `queued`（无 `turn_id`）；记录已被淘汰的带 id 条目回报 `completed`。排队提交同样占幂等位：否则同一条渠道消息在回合运行期间重试/重发会反复入队，用户收到多份重复回复。回合记录表有界，超限从最旧终态记录淘汰、运行中记录永不淘汰；幂等条目不随记录淘汰失效。
- 附件：`data_base64` 落盘 `.g3ku/external-uploads/<session>/`，双上限——`kind:"image"` ≤5MiB（与 web 上传同一常量），其余文件类 ≤20MiB（`EXTERNAL_FILE_UPLOAD_MAX_BYTES`），超限一律 413 `attachment_too_large`；桥侧按同值预过滤。图片构造 `image_url` 块，能否进模型由本轮这一发落到的那颗模型是否勾选多模态决定（与 web 上传同语义：不收图时降级成"绝对路径 + 点名配置"的文本行，见 `web-and-admin.md`「Image Upload Gating」）；非图片附件只以「本地路径提示」文本块告知模型（落盘路径可直接用工具读盘），不构造多模态内容块。该目录按会话 slug 分片，随会话删除/清空一起被 rmtree（`clear_web_ceo_session_artifacts` 同时清 web 侧与渠道侧两个上传根），所以渠道附件的寿命等于会话寿命。附件说明行（`Channel attachments:`）只属于模型输入：显示侧的三条道（在飞实时帧、刷新快照、前端按字段克隆）都从同一份描述符把它剥掉并抬成附件气泡，正文与单一作者见 `web-and-admin.md`「Attachment Bubble Rendering Contract」。
- 控制端点复用桥语义：`POST /turns/{turn_id}/pause`（running guard，空闲返回未暂停）、`POST /sessions/{id}/cancel`。取消面覆盖**两半**：在跑的回合，以及按 `tasks.session_id` 属于本会话、还没落终态的任务（逐个走 `main_task_service.cancel_task`，"暂停未恢复"的任务也在这半里）。回包 `cancelled_turns`/`cancelled_tasks`/`task_ids`/`skipped:[{target,reason,how_to_clear}]`/`tasks_still_running`；`cancelled` 是对接手册里的已发布字段，等于前两者之和。**取消是请求式的**——分离部署下节点在下一个检查点才落终态，所以紧随的几次读数里 `tasks_still_running` 可能仍为正，不是失败；真被拒的目标把原因原样带在 `skipped` 里。
- `DELETE /sessions/{id}` 默认是清除语义（对齐 web-and-admin.md「Channel Session Clear Contract」）：转录清空、内存失效、side artifacts 全清，注册表条目保留；`?purge=true` 才是连条目一起忘掉（`agent-gateway.md`「MCP stdio 网关契约」的 `negi_delete_conversation` 走这条）。摘除身份时的闸门与后果一律归 web-and-admin.md 那一节：网页侧按该桥的 token 条目分流隐藏/注销，`/api/v1` 这条只认 `_own_entry` 的归属限定，不重复一遍闸门。

### 入站身份契约（`sender` / `chat_type`）

`POST /sessions/{id}/messages` 的请求体可带两样身份信息，服务端据此派生会话信任级（契约在
`sandbox-execution-plane.md`「信任分级」）：

- `sender: {id, name}` —— 发送者身份，`id` 上限 128 字符（超限 400 `sender_id_too_long`），`name` 截断到 128。
- `chat_type` —— 白名单 `group` / `dm` / `guild` / `guild_dm`，非法值一律 400 `chat_type_invalid`；
  `POST /sessions` 也接受它并记在注册表条目上。缺省时按 `external_key` 前缀回退（`qq:group:` / `qq:guild:`
  是多人会话，`qq:c2c:` / `qq:guilddm:` 是私聊）。

服务端把派生结果写回消息 metadata：`external_trust`（`owner` / `third_party_dm` / `third_party_group`）与
`chat_type`。**桥不能自报信任级**：请求体里的同名字段会被覆盖，白名单来自服务端配置
（`externalApi.tokens.<id>.trustedSenders`；官方 QQ 适配器读 `qqBot.accounts.<appId>.ownerOpenids`
的**跨账号并集**——openid 按 AppID 隔离，每号各填一条，任一账号里填过的 openid 在任何 QQ 桥上命中，
比较大小写不敏感）。「外部接入」页 QQ 账号行的「操作员」入口写的就是这份名单。

三条判定不因桥的声明而放宽：群聊整会话按第三方（发送者在白名单里也不升级）；信任只降不升
（注册表记最受限的那一档）；缺 sender 永不等于操作员。

投影层的 `Master` / `第三方 0002` 编号与网页气泡上的 `sender_label` 都是**显示层派生**
（规则见 `sandbox-execution-plane.md`「来源标注」）：它们解释"谁在说话"，不参与准入；
`external_trust` 仍是唯一判据。气泡标签只对渠道会话的用户行下发，web 会话没有。

MCP 网关的身份由 `sender.id = "negi-mcp"` 表达（常量 `GATEWAY_SENDER_ID`，`g3ku/runtime/session_trust.py`），
**每回合都带**而不是只在建会话时带：信任是逐条入站按 min 合并的，所以撤掉授权后下一条消息就把会话降回第三方。
这个 id 在不在白名单里由「外部接入」页 token 行的「当操作员」开关决定——开启要项目解锁口令、收回不要，
写入的就是 `externalApi.tokens.<id>.trustedSenders`（控件契约见 `web-and-admin.md`「External Access Page Contract」）。
命中时该桥的会话按操作员处理：档位默认 `unrestricted`、长期记忆可读可写、人设取操作员那份、任务族可派，
四扇门读的都是同一个信任级。

### 会话状态读数（`GET /sessions/{id}/state`）

四档读数都由既有状态投影出来，不新增状态。它们的共同由来：调用方（MCP 网关、外部桥）手里只有一个 SSE 事件游标时，分不清"在跑一个长活"与"已经卡死"。

- **在不在动**：`started_at`/`elapsed_seconds`（在飞回合，取自 `TurnRecord.started_at`）、`last_activity_at`/`silence_seconds`（hub 最后一条事件的 `ts`）、`last_event_seq`，以及 `last_activity_kind`/`last_activity_text`（此刻的活动文本，先过出站消毒再截 160 字）。
- **在做什么**：`latest_model_text`（最新一段模型输出，过 `sanitize_channel_outbound_text` 后截 300 字，`latest_model_text_total_chars` 报截断前的字符数；消毒只剥思考段/契约尾，实测**不剥**其他内部标记）、`recent_tool_calls`（读 `progress` 事件的结构化 `tool_name`，不从 `🔧 xxx started` 的人读文本反解）。`recent_tool_calls` 是**最多 5 项 `{tool_name, calls}`**，次数覆盖整个会话事件缓冲：只报去重名字回答不了"是在磨还是要收了"（实测一条 87 分钟的审计把 114 轮花在同样几颗名字上，名单看起来一模一样）；算次数就**不许提前 break**，否则报出来的是假数。`stage_totals`（`stages_total`/`stages_completed`/`rounds_used_total`/`rounds_budget_total`）是同一份账本的求和，存在的理由很直接：只给最新 3 条 goal 会被读成"这个会话一共 3 个阶段"，而累计轮数没有别的口给出。
- **有没有在跑的任务**：`tasks_running`/`tasks`（本会话仍未完成的任务，逐条带 `task_id`/`status`/`model_calls`/`last_hop_at`）与 `task_activity_at`/`task_silence_seconds`（各任务最近一跳时间的最大值）。派发回合几十秒就收尾而节点要跑几十分钟，这段时间会话侧本来就没有新事件——只读 `silence_seconds` 会把在跑误读成卡死，任务侧的跳次时间才是活性的正证。读不到任务服务时这几键整组省略："不知道"与"没有在跑的任务"是两回事，不折成 0。每个任务还带 `nodes`（最近至多 6 格的 `node_id`/`node_kind`/`status`/`depth`/`updated_at`，按更新时间倒序）与 `node_count`（真实条数）：一个任务是执行节点 + 验收节点的树（实测每任务 p50=2、p90=3），任务级那句 `in_progress` 说不清卡在哪一格——遗留样本 `task:37a79544ee37` 至今 `in_progress`，只有节点级时间读得出执行节点停在 00:18:41、验收节点停在 00:13:48。节点格走 `sqlite_store.list_task_node_activity` 的平铺列窄读，**不许**换成 `list_task_nodes()`：那会把整任务的 `payload_json` 逐行建模（实盘单任务 1227 个节点），而轮询只要最近几格。读不到节点服务时 `nodes`/`node_count` 整键省略，同上一条纪律。
- **这轮是怎么结束的**：`stop_reason` 原样透 `RuntimeAgentSession._last_stop_reason`（值如 `user_pause`；正常交付轮是空串），`unconsumed_replies`/`turn_left_unconsumed_reply` 数的是持久账本里本会话还没销账、且拉取式消费方可取的记录（`reply.final` 与 `outbound.created` 两类，判据单点在 `g3ku/runtime/external_outbox.py::is_pull_consumable`，见「持久 outbox」）。这一档专为一种实盘误读存在：`last_activity_kind:"turn.completed"` 与阶段 `status:"active"` **同时**出现时，调用方分不清"交了付"还是"中途早退"，按最保守解读重派会把几十分钟的活白做一遍；这里有两个可判读数，加上 `GET /sessions/{id}/wake` 能把没取走的正文捞回来。

三本时间源的 ISO 串形状不同：事件 `ts` 与 `TurnRecord.started_at` 是本机 naive 串，任务跳次 `created_at` 带本机偏移（生产者 `main/monitoring/log_service.py::_now_iso`）。所有"距现在多少秒"统一走 `external_v1._age_from_iso()`，它按被减数的形状对齐减数。拿 naive 的 now 直接减 aware 的串会 `TypeError` 打死整条 `/state`，而失败的恰好是"任务在跑、正想看它活着没"那一刻——状态端点因此必须把这三种形状都当可达输入。

### 唤醒读数（`GET /sessions/{id}/wake`）

回答"**我没在听的时候发生了什么**"：`tasks`（本会话在该时刻之后落终态的任务，逐条 `task_id`/`status`/`finished_at`）与 `replies`（持久 outbox 账本里属于该会话、`is_pull_consumable` 成立且还没销账的记录，带 `outbox_id`/`ts`/`event`/`text` 全文；`event` 标出来路是回合答案还是主动推送），外加 `replies_pending`/`tasks_truncated`/`next_since`。

它存在的理由是既有投递面的两个空洞：事件 hub 是进程内存里的 512 环、`turn.completed`/`turn.failed` 根本不入账本，而回复的取法只听活 SSE——桥或 stdio 网关断开半小时再回来，没有任何一口能回答"我那两个任务结清了没"。这里**不新增写侧记录**：终态行落在 `tasks` 表（落库后不变），未消费回复落在 outbox 账本（销账才消失），两边都是既有 durable 事实，所以唤醒不依赖"当时有没有人在听"。`since` 是调用方自己的游标（用上一次返回的 `next_since`），空串＝没有历史，回最近 `WAKE_TASKS_MAX` 条终态，首次调用因此能 bootstrap。

机器**不**往出站账本写"任务已结束"这类文本：pump 会把账本记录当渠道消息投给用户（`g3ku/qq_official/bridge.py`），替模型决定推送是禁区。所以唤醒是**读侧**能力（含 MCP 侧的 `negi_wait_wake` 长轮询），服务端不另开推通道。`tasks` 只认 `status IN ('success','failed','canceled','cancelled')`——`paused` 不算结束，它归任务命令。

水位线只认一种形状：`_wake_wall_second()` 把每个候选时间归一成**本机墙钟到秒**的裸串（账本 `ts` 是 naive 带微秒，`tasks.updated_at` 带 `+08:00` 且只到秒，活体读到的就是这两种），比较全程用字符串、不做减法，下界取**包含式** `>=`。混形状直接比会出事：同秒内 `+`（0x2B）排在 `.`（0x2E）前，aware 串被判成"更早"，于是严格大于的游标能把边界那一秒的终态**永久漏掉**。归一 + 包含之后不丢，但同一秒内的多条行在时间上分不开"报过"与"没报过"——网关因此**按身份去重**：`task_id`/`outbox_id` 随游标存在 `wake-cursor.json`，游标推进到新的一秒就丢掉旧的去重集。只按时间判会把边界那一秒变成永久重报（游标停在 12:37:12，而 `12:37:12+08:00` 永远满足 `>=`），实盘真出现过"会话再也不出现 `woke:false`"。调用方把原始形状串当游标递回来也会被归一；归一不动就当"没有历史"，回最近一批而不是报错。

## 5. 事件流

- 每会话一个 `SessionEventHub`（`g3ku/runtime/external_events.py`）：有界环形缓冲 + 单调 `seq` + 订阅扇出；事件形态 `{type, seq, ts, turn_id?, ...}`。会话键是 `(bridge_id, external_key)` 的确定性散列，所以**身份被注销时缓冲必须一起退役**（`drop_session_event_hub`）：同键日后重新注册会落回同一个路径与同一批文件名，留着旧缓冲就等于让新身份能 `Last-Event-ID: 0` 重放出上一世的回复。只清历史不退役缓冲——那条身份还在用。
- `GET /sessions/{id}/events` 为 SSE（`id:` = seq）；断线以 `Last-Event-ID` 回放续订；15s 心跳注释行保活。hub 的 seq 是内存态、随服务端重启清零：`Last-Event-ID` 若越过本进程已发布 seq（旧进程遗留的大序号），端点按全量重放处理——第三方桥重连即收到缓冲内全部积压，不因旧序号被静默过滤。
- 事件集合：

| 事件 | 来源 | 说明 |
|---|---|---|
| `turn.started` / `turn.completed` / `turn.failed` | 回合执行器 | 终态恰好一个；`turn.completed.cancelled=true` 表示被暂停/取消。`turn.failed` 只供机器读取，给用户看的那一句由运行时另投一条渠道通知（见「回合契约」终态不变量） |
| `reply.delta` | `assistant_stream_delta` | text 为最新思考段权威全文（桥做全量替换而非追加） |
| `progress` | `message_delta`（progress/analysis）、工具开始/出错 | `kind: milestone/tool/tool_error`；**g3ku 发全量，节流是桥的职责**。节流只决定"一次发几行"，不决定归属：`reply.final` / `turn.failed` 到达时桥必须先把该会话的缓冲整段排空再交付终态正文，否则残余里程碑会排在答案之后落地（读起来像答案还在自述过程，还会串进下一回合），而按回合寿命留下的空缓冲永不出队。`kind=tool` 的那条额外带结构化 `tool_name`（人读文本 `🔧 xxx started` 会随文案漂，要工具名的调用方读这个键，不做反解） |
| `reply.final` | `message_end` | 权威全文：只调用了成功 `show_sticker_category` 的那几轮正文在发 `message_end` 前已拼回出站正文（`RuntimeAgentSession._sticker_sheet_turn_text_prefix`；转录与模型上下文仍存模型原文），所以渠道端读到的回复与网页气泡一致；经出站清洗 + 附件提取（见下）+ 剩余本地引用改写为签名媒体 URL（`ceo_media` HMAC token）；可携带 `attachments`；发布前进持久账本登记并携带 `outbox_id`（合同见「持久 outbox」）；内部心跳 ack（heartbeat_internal）不转发。`usage` 是**发出 `message_end` 的那条会话自己盖章带出的**一份（形状见 `web-and-admin.md`「Per-Turn Token Usage Contract」），relay 只透传事件负载里的这份、绝不按 turn id 反查会话累加器，因此会话名下的第一回合与后续回合同形；本轮没有可报数字时该键不出现。本回合派发出的任务号以 `task_ids` 数组项随同出现（取自运行时自己写的 `create_async_task` 工具结果，不经"那行是否已落库"的存在性闸门——闸门只管模型可见的那句派发尾注 `verified_task_ids`；本轮没有派发时该键不出现，桥与 MCP 网关都只透传，不自行按正文反查）。事件里同时有**两套回合 id**：外层 `turn_id` 是 `ExternalTurnService` 的记录 id（`turn.started`/`turn.completed`/`turn.failed` 与暂停、续取定址都用它），`transcript_turn_id` 是**转录行的** `turn_id`（`GET /sessions/{id}/turns/{turn_id}` 唯一认得的键）；两者不同时才带出 `transcript_turn_id`，同一套 id 的发起方（网页/cron）不会多出这个键。曾有调用方拿外层 id 回读原文得到 404，这就是两套命名空间的原因——实测也证明"把 record id 盖进消息 metadata 当作盘键"盖不住（转录行仍是另一个 id），所以这里选择把两个 id 都交出去而不是强行合一 |
| `outbound.created` | 出站总线（见「出站路由（主动推送）」） | 主动推送，可携带 `attachments` |

出站附件契约（`reply.final` 与 `outbound.created` 通用）：正文中以 markdown 链接/图片语法引用、且解析为**存在的本地文件**的条目，在事件发布前被提取为 `attachments` 数组项 `{name, mime_type, kind, size, url}`，另有两种可选键：`kind` 取 `image`/`file`，桥据此决定发图片还是发文件（OneBot 的 `[CQ:image]` 分支只认 `image`；缺省时按 mime 推断）；`after_text: true` 表示这条附件要**等正文发出后**再投递（表情包用，否则用户先收到一张图、再收到那句话）。`url` 是根相对的签名媒体链接（`/api/ceo/media/original?token=...`，24h 时效，桥按自己的服务端 origin 拼绝对地址下载），原 markdown 标记在正文中替换为其标签文本（无标签用文件名）。表情包标记（`[[sticker:<pack>/<category>]]` / `[[sticker:<pack>/<category>/<N>]]`）在提取前先按该包注册表解析成本地图片路径（索引形式还会复验 sha256，不符按"未发出"处理），然后走同一条附件通道——正文里不留标记，附件带 `after_text`。判据是**整行以 `[[sticker:` 开头**而不是"能解析成功"：语法不成立的（多两段的 `pack/cat/extra/more`、`_` 开头的隐身分类、未知形状、超出注册表的序号）也整行剥掉并记 warning。把原始标记漏给用户比不发这张图更糟，而 `_` 开头的分类在导入 AstrBot 包时是会真实存在的。单条事件最多提取 4 个附件（超出与重复路径保留原样，走签名改写成为可点击兜底链接）。**仅** markdown 引用触发，裸路径不提取；引用形态上 `file:///C:/…` 与 `file://localhost/…` 先归一成裸路径（`%20` 一类转义一并解开）再判——模型抄一条本地文件链接时给的就是这个形状，不归一的话这条引用既不成为附件也不成为链接，用户收到的是原样的 markdown 文本。归一只换形态、不放宽闸门：越界路径照旧既不转附件也不签链接（`ceo_media._file_url_to_path`）。桥收到 `attachments` 时应作为真实文件/图片消息投递，投递失败的条目降级为签名链接文本行（详见「内置官方 QQ 适配器」与桥自身文档）。普通回合的 `reply.final` 在 relay 侧解析标记并提取附件；`outbound.created` 在出站 drain 做同一套标记解析与附件追加（见「出站路由（主动推送）」）。两条车道共用 `g3ku/runtime/external_events.py` 的解析与每消息附件预算实现，标记的可见性因此只有一个落点：图片以附件走，正文不留语法。

中继的失败合同：`make_session_event_relay` 跑在会话事件分发路径上，永不阻塞、永不外抛，但**每一次吞事件都留下一行 WARNING**，带 `type`/`session`/`turn`——被吞掉的正是「渠道始终没收到那句回答」的唯一现场（`reply.final` 与它的账本登记一起没落）。账本登记失败是另一条独立降级：回复照发，只是不带 `outbox_id`，并单独打一行「falls back to memory delivery」。

## 6. 出站路由（主动推送）

- 投向 `channel="ext"` 的运行时侧消息有两类生产者——会话键为 `ext:` 的 heartbeat/cron/task-terminal 回复（`_notify_heartbeat_channel_reply` 的 ext 分支），以及回合终态失败通知（判据与门件见「回合契约」终态不变量）——两者都经 `publish_channel_notice(bus, session_key, text, source=...)` 发布 `OutboundMessage(channel="ext", chat_id=<ext session key>)`：这条消息形状只在这一处构造，drain 只认 `chat_id` 是会话键还是 external_key（`_derive_session_channel_chat` 对 ext 键保留完整会话键为 chat_id），`source` 只进 metadata 供日志辨认来源。cron 零改动（payload `channel="ext"`、`to=<session key>` 即达）。失败通知走这条车道的理由是可达性而不是省事：`turn.failed` 是只进内存 hub 的瞬时事件，而这条车道自带清洗、账本登记、`outbox_id` 去重与重连重放。
- 共享出站 drain（`g3ku/shells/web.py::_start_outbound_drain`）只路由 `ext`：注册表 `find_by_any_key`（接受会话键或 external_key；**external_key 不保证全局唯一**，同一键命中多条时按 `created_at` 取最新并落一条 WARNING——被点名说明有推送/定时任务仍指着已被取代的旧会话键，需要改指）→ **持久 outbox 登记**（见下）→ 该会话 hub 发 `outbound.created`（事件携带 `outbox_id`，提取到的附件携带 `attachments`，见「事件流」出站附件契约）；其他 channel 无消费方，告警跳过。附件提取发生在 drain 这一统一出口：首次出站从正文提取；启动重放/对账重注入的消息自带账本持久化的 `attachments`（正文已是提取后文本），直接透传不二次提取——心跳、cron、任务终态等全部主动推送因此自动获得文件投递能力，`reply_notifier` 与 `OutboundMessage` 形态保持纯文本。贴纸标记在同一出口解析（markdown 提取之后）：整行剥掉并追加 `after_text` 图片附件，预算与 markdown 附件共用，不经过 relay 的推送因此与普通回合同形；解析不出来的标记也整行剥掉，原始语法绝不投给渠道。重放副本同样过这一步——正文已剥过的副本不变，账本里仍带标记的副本在这一步被修掉。日志 `external outbound published to hub` 只代表事件已进内存 hub，**不代表已送达渠道**；送达以桥侧回执日志为准（QQ 适配器为 `qq-official delivered ...`）。发布时 hub 无任何订阅者则升级为 WARNING（`no live subscriber`）：live 扇出必然蒸发，投递交由持久 outbox 周期对账兜底（见下）。
- drain 生命周期：`ensure_web_runtime_services` 拉起，仅进程关闭时取消。outbox 对账循环（`_outbox_reconcile_loop`，60s）与其同生命周期、同款幂等启动器（`_ensure_outbox_reconcile_running`），关停时先于桥服务收割（防对账在 shutdown 后复活桥）；每轮先幂等复活 drain——drain 死亡时重放进总线无人路由，对账把它降级为 ≤60s 自愈。
- 未知目标告警丢弃；清洗后为空的纯内部文本静默 ack（不触发重试）。

### 持久 outbox（`.g3ku/external-outbox/outbox.jsonl`）

bus/hub 全是内存态：桥 pump 断连或进程重启窗口里滞留的消息会随内存清空蒸发。`g3ku/runtime/external_outbox.py` 是这条链路的持久账本，覆盖两类出站——主动推送（`outbound.created`，由 drain 登记）与**回合回复**（`reply.final`，由 relay 在发布 hub 前登记，见「事件流」）。投递语义 **at-least-once**，且**账本唯一的出口是 ack**：

- 记录形状：`{"kind":"msg",...}` 登记记录含 `id`/`ts`/`event`/`session_key`/`external_key`/`text`，以及提取到的 `attachments` 描述符与可选的 `mentions`（当前会话花名册里的 sender id，QQ 桥渲染成群 markdown `<qqbot-at-user id="..."/>`）；`{"kind":"ack","id":...,"status":...}` 为销账 tombstone。登记失败（如磁盘满）降级为仅内存投递并记 error，绝不阻断 hub 发布——回复本身比它的兜底副本重要。
- 两条登记点各自的位置：drain 在发布 hub 前登记 `outbound.created`；`make_session_event_relay` 在发布 `reply.final` 前登记并把 `outbox_id` 放进该事件。回合回复必须登记的原因长在 pump 的建立时机上（见「内置官方 QQ 适配器」）：pump 只由渠道入站或"账本里有该会话的 pending"唤醒，而**网页在渠道会话里发起的回合两个条件都不满足**，没有账本记录时它的回复就是一个无人消费的内存事件。`external_key` 取不到（注册表里没有该会话的孤儿转录）时不登记，只走内存投递。
- 销账方：桥在渠道 API 确认送达后调 `POST /sessions/{id}/outbox/{outbox_id}/ack`（会话作用域防越权、幂等）。ack body 可带 `shape`（`passive`/`active`）、`kind`、`detail`、`passive_window_open`、`text_preview`：主动形状送达成功清除该会话的 `active_message_state`；主动推送被判 `undeliverable` 时，服务端记录 `active_denied`/`quota` 能力读数，并按 `outbox_id` 去重后**每一条失败都入一条 `delivery_failure` 心跳事件**（不按时间节流）。失败唤醒只内部可见，不默认回渠道——模型的正常回复若再发主动消息可能再次被拒并形成自激循环；要触达群里只能走 `mention_member`（有被动窗口时）。**每一个消费正文的一方都要 ack**——进程内等待方（OpenAI 兼容端点的 `wait_for_external_reply`）取到回复时就地销账；跨进程的 SSE 消费方（MCP stdio 网关的 `negi_get_reply` 走这条路）由服务端在帧写出后自动销账，但**只对 `reply.final` 那一类**（`external_v1._ack_streamed_outbox_event`），第三方桥仍须自行 ack。服务端不自动销 `outbound.created`：同一条流既通向有消费者的渠道桥、也通向根本不接受这一类的拉取式客户端，服务端看不出客户端会不会把这一帧丢掉；按帧类型一律销账会让"问一下有没有回复"这一次连接把账本里唯一的存货标成已交付（正文仍在转录里，但"待投递"这个事实没了）。主动推送由真正取走它的一方 ack：桥发送成功后调同一颗端点，网关在没点名回合的续取读口返回它时同样调 `ack_reply`。ack 丢失的代价是下次重放时重复投递一次；从不 ack 的消费方会让记录永久驻留并按退避每小时重注入一份副本。
- 拉取式读口能取哪一类，判据只有一个单点：`g3ku/runtime/external_outbox.py::is_pull_consumable`（`reply.final` 与 `outbound.created`，且正文非空）。`GET /sessions/{id}/wake` 与 `/state` 的 `unconsumed_replies` 都走它。必要性在于心跳来源的回合**从不产 `reply.final`**：那条回合的正文只经主动推送车道进账，只认回合答案的读口会把"账本里有存货"报成"这轮没写回复"，节点→前门→用户这条链在没有渠道 pump 的会话（纯拉取式）上就断在转录里。
- 六种终态 status：`delivered`（渠道确认或 SSE 已写出）、`superseded`（同一会话登记了更新的 `reply.final`：拉取式客户端只会取到最新一条，旧回复的正文仍在转录里、按 `transcript_turn_id` 可取，因此只销投递记录）、`undeliverable`（桥按 `outbox_id` 耗尽投递预算后判毒，见「内置官方 QQ 适配器」——这是永久拒投目标的重试上界）、`unconfirmed`（请求已发给渠道 API 但回执没回来，桥因此拒绝重发这一条，见「内置官方 QQ 适配器」的出站幂等闸门）、`unreachable`（不可路由）、`discarded`（**只由操作员发起的一次性清理写入**，走 `external_outbox.ack_outbound_message`，桥侧 ack 端点的状态白名单不含它：账本里长期无人取走的存量按快照批量销账，对账循环只重注入未销账记录，这一批因此退出重注入）。年龄不参与判定：跨一天关机后请求方仍在等那条回答，晚到胜过不到——`discarded` 不是过期策略，运行时任何循环都不按年龄挑记录。
- 不可路由判定（`g3ku/shells/web.py`，每轮对账与启动重放各跑一次）三条：`ts` 畸形（周期重放按年龄过滤，这类记录结构上投不出去）、会话不在外部会话注册表、该会话所属 bridge 的 token 明确 `enabled=false`（整表替换后旧 `qq-official*` token 就是这个形状）。判定一律 **fail-open**：注册表或配置读不到、注册表为空（空表与"没读到"在磁盘上不可区分）、bridge 在 `tokens` 里没有条目，都判为可达并保留记录并留一行 WARNING。误判"可达"只多几份副本，误判"不可达"是删掉用户还在等的回答。`externalApi.enabled` 总开关不是终态。
- 启动重放：`ensure_web_runtime_services` 在 drain 拉起后把所有未 ack 的条目带原 `outbox_id` 重新注入总线（drain 复用该 id，不重复登记），随后压实账本。
- 周期对账（`_outbox_reconcile_loop`，每 60s）：启动重放是一次性的，覆盖不了「重启时账本为空、滞留消息在重启后才入账」的窗口（重启落在 cron 触发与 agent 产出之间即如此）。每轮先跑不可路由判定（不依赖重启），再把 pending 中「年龄超过 120s 且对应会话 hub 无订阅者」的条目带原 `outbox_id` 重新注入总线——有订阅者说明 pump 在线，SSE `Last-Event-ID` 重放已兜底，再注入只会制造重复副本。重注入按记录指数退避（60s 起步、1h 封顶）；到达桥侧的重复副本由 pump 的 `outbox_id` 去重吸收（见「内置官方 QQ 适配器」）。活动轮立即压实账本、稳态每小时压实一次，append-only 文件不随运行时间无界增长。
- `GET /outbox/pending` 返回本 bridge 名下会话的 pending 清单（只带路由身份 `outbox_id/session_id/external_key/ts`，不带正文——正文经 SSE 重放投递），供桥启动首跑与常驻对账循环重建 pump（见「内置官方 QQ 适配器」）。
- 账本覆盖 `outbound.created` 与 `reply.final` 两类，共用同一份 jsonl、同一个 ack 端点、同一个 `outbox_id` 去重维度。`reply.delta` 与 `progress` 仍是只进 hub 的瞬时事件（断线超过 `eventBufferSize` 即被逐出），其可达性由桥侧 pump 的重连契约兜底——它们对用户不是交付物，重复或丢失都不该产生账本写盘。

## 7. 内置官方 QQ 适配器（qq-official）

- `g3ku/qq_official/` 是 g3ku 唯一内置渠道桥，以 in-process 桥身份消费本契约；QQ 协议收敛在该模块内，核心其余部分不出现 QQ 代码。一个 QQ 号 = 一个 AppID = 一条 bridge_id `qq-official-<appId>`（`messages.py::bridge_id_for_app_id`），号与号之间不共享任何句柄。bridge 身份决定三件事：用哪条 `externalApi.tokens` 凭证、会话键的 bridge 段、以及 registry / outbox 的可见集作用域——因此一个号的 pump 与周期对账按构造看不见另一个号的滞留推送（多号共用一条 bridge_id 时才会出现的互抢形态：拿别人的 openid 去投、5 次重试后跳毒消息）。QQ 开放平台的 openid 按 AppID 隔离，同一自然人在两号下是两个 `external_key`、两个会话、两份记忆作用域；跨号身份打通平台不提供手段（官方口径是"后续提供跨 AppID 绑定"）。
- 配置段 `qqBot`：`enabled`（总开关）与 `accounts`（以 AppID 为键的字典，每项 `appSecret / sandbox / enabled / label`）。每号的 `appSecret` 与 `externalApi.tokens[].token` 同走 overlay 三件套（保存剥离、落盘占位、解锁回填），覆盖层键是 `config.qqBot.accounts.<appId>.appSecret`。旧的单账号形状（顶层 `appId/appSecret/sandbox`）由 `g3ku/config/loader.py::_migrate_legacy_qq_bot_account` 折叠成 `accounts[<appId>]` 并复存一次；**折叠必须发生在覆盖层回填之后**，早于回填时账号折出来了却拿不到密钥，而保存会清掉那条旧覆盖层键，密钥就此丢失。管理面：Web「外部接入」页的官方 QQ 机器人面板按账号列行，对应 `main/api/admin_rest.py` 的 `/api/qq-bot/settings`（GET 返回 `accounts[]`，每行带掩码、`has_secret` 与该号的服务态；PUT 是整表替换，某行 `appSecret` 传空串表示保留该 AppID 的原密钥）与 `/api/qq-bot/status`（同样按号返回）。操作员注册走 `/api/qq-bot/register-owner/preview` 与 `/api/qq-bot/register-owner`：按当前渠道会话的发送者编号解析 sender id，口令门控后只写同一条 `ownerOpenids`（详见 `web-and-admin.md`「External Access Page Contract」）。整表替换后不对应任何账号的 `qq-official*` token 被置为停用（不删除，重新加回同号可复用）。
- 生命周期：每个账号一个 `QqOfficialService` 实例，注册表在 `g3ku/shells/web.py`（`_global_qq_official_services`，以 bridge_id 为键）随 web 运行时 refresh 与配置做 diff：新增建实例、签名变更重启、从配置里消失则 `stop()` 并摘除。状态机 `enabled_off / account_disabled / not_configured / connecting / connected / error` 按号独立（"总开关关"与"这一号被停用"必须可区分，否则管理面上一个号停用会把整列报成未启用）；启动时若该号的 `externalApi.tokens.<bridge_id>` 缺失则自动签发并 `save_config`。重启签名包含密钥摘要，因此只改 AppSecret 也能让停在旧凭证重试循环里的号被重建。桥异常崩溃由 `_run` 自身按退避重连（见下条「崩溃自愈契约」），不依赖外部复活；`sync_from_config` 负责的是桥任务已终结后的复活（`_run` 干净返回即终止循环），其触发点为 runtime refresh、启动序列与 outbox 对账循环（每 5 轮 ≈5 分钟），环境修好后因此最迟分钟级重新建桥。**sync 幂等是硬约束**：`_prompt_locked` 在每一个回合开头都调 `refresh_web_agent_runtime`，而后者无条件调 `_sync_qq_official_service`，所以每条入站消息都会 sync 一次自家桥——一次"配置未变也重启"的 sync 等价于每条消息拆掉自己所在的桥。已采纳的签名只能被真正的配置变化推翻，`stop()` 不清它（`_restart` 先写签名再 `await stop()`，在 `stop()` 里清空会让幂等判据永远不命中）；重启由"签名不同"决定，复活由"`_task` 为空或已终结"决定，两条判据互不依赖。`_sync_qq_official_service` 对整次 diff 持**一把**模块级 asyncio 锁而不是每号一锁：diff 必须原子，且 `sync_from_config` 在 `_restart` 的 `await stop()` 窗口内 `_task=None`，无锁的并发调用会各自建桥、先建者沦为无人持有的孤儿任务（双 botpy 连接、每条消息双份投递）。单号 `sync_from_config` 抛异常只记日志，不阻断其余账号建桥。

- 崩溃自愈契约（`service.py::_run`）：桥以异常终结（如 botpy 的 http 层对登录超时/限流只记 WARNING 返回 `None`，`Robot(None)` 抛 `AttributeError`）时，服务层按 1s→60s 指数退避自动重连，`error` 状态 detail 保留异常摘要与「将在 Ns 后重试」；崩溃前健康运行超过 60s 则退避重置回起始值，长期健康后的单次崩溃不被放大。**日志折叠**：每次崩溃都留一行 `crashed; retrying in Ns`（退避节律必须仍可逐条数），完整 traceback 只在该签名首见、以及每 `_BRIDGE_RETRY_TRACEBACK_EVERY`（20）次重复时给一份；退避重置的同时折叠状态作废，所以恢复一段时间后再发的事故重新拿得到栈。折叠只砍栈体，不砍行数、不改级别、不改锚点文案。理由与实盘：一号一桥，两条桥各自停在 60s 封顶就是 2 条/分，09-30 一夜 445 次崩溃、每次一份带变量表的 loguru 全栈（约 40 行/条），把 `console.log` 顶到 187 MB（封顶与轮转归 `operations-and-maintenance.md`「关键状态文件与目录」）。桥**干净返回**是它自报的环境类终态（botpy 缺失/intents 不兼容），不重试；配置变更与停用由 `stop()` 取消任务终结循环，不走本重试路径。

- 到期重登不算崩溃（`bridge.py::QqGatewaySessionEndedError`）：QQ 网关按约 1 小时用 close 4009（"Session timed out"）判 wss 会话过期，botpy 手里那一份 `_session_list` 随之排空；桥只跑一份列表（见「运行入口是硬约束」），列表一空就以 `QqGatewaySessionEndedError` 上抛要求重登。这一条走**计划内重排**的记法：单行 WARNING `gateway session ended after Ns; re-login in Ns`，不带 traceback；状态停在 `connecting`，detail 写「QQ 网关会话到期，将在 Ns 后重新登录」；退避钉在起始值，不逐轮翻倍。界线是健康窗口，不是异常类型——同一条异常若没跑满 `_BRIDGE_RETRY_HEALTHY_RUN_SECONDS`（60s）就排空，说明登录或网关自己坏了，仍按上面「崩溃自愈契约」记 `error`、给栈、退避照常上涨。把到期重登按崩溃记会把每小时一次的正常节拍写成故障风暴（每轮一份约 40 行全栈，面板每小时闪一次 `error`），也让折叠规则永远不生效：折叠只在同签名**连续**重复时计数，而每轮之间都跑满了健康窗口。实盘节奏：两条桥各 36 次到期、间隔约 60 分钟并成对出现（同一进程启动 ⇒ 登录时刻对齐 ⇒ 到期时刻也对齐），代价是一轮起始退避的重新登录；判"重登后是否真的恢复"用下一次到期的间隔——又隔了约 60 分钟就证明其间连接一直可用。

### 运行入口是硬约束

- botpy 的阻塞入口 `Client.run()`（内部对构造时捕获的 loop 调 `run_until_complete`）在已运行的 web 事件循环上会抛 "This event loop is already running"；桥必须走异步入口 `async with client: await client.start(..., ret_coro=True)`，使 botpy 与 uvicorn 共享同一事件循环，事件回调（`on_*`）因此可直接驱动回环 `/api/v1` 客户端。**`ret_coro=True` 与"一份会话列表只跑一次"同为硬约束**：不带它时 botpy 用 `while not self._closed: await multi_run()` 自行驱动，而 `multi_run` 第一次就把它自己的 `_session_list` 原地 pop 空，此后每次返回的都是一个从不挂起的协程——那个 while 于是变成持有 GIL 的忙等，实测把整个 web 事件循环钉死 20 分钟（单核跑满、所有 HTTP 请求无人处理，`service.stop()` 的取消也永远落不到挂起点）。桥因此取回协程后只 `await` 一次，它一返回就代表这份网关会话全部结束，立即以 `QqGatewaySessionEndedError` 上抛，由「到期重登不算崩溃」的记法重新登录换一份新会话列表；绝不重复驱动同一个 `multi_run`。这也让优雅退出有上界：`service.stop()` 的取消只能在真正的挂起点（`multi_run` 的 `asyncio.wait`）生效，忙等状态下 `await task` 永不返回，`POST /api/bootstrap/exit` 因此不会被处理。
- 消息流：入站 `on_*` 事件按 external_key 映射建会话（`qq:group:<group_openid>` / `qq:c2c:<user_openid>` / `qq:guild:<guild>:<channel>` / `qq:guilddm:<guild>:<author>`），经 `Idempotency-Key: qq-<消息id>` 提交回合——缺消息 id 时不带幂等键提交，绝不回退 external_key：external_key 对同一用户恒定，回退会撞掉该用户首条消息的幂等位并永久丢弃消息。提交返回 `status:"queued"`（会话正忙、消息已排队）时，桥必须把回执投递给用户（响应 `receipt` 为空则用兜底文案），静默会让用户以为消息被吞而重复发送。消息附件（botpy `message.attachments` 中带绝对 http(s) URL 的条目，每条消息至多 4 个）由桥下载后作为 `data_base64` 附件经本契约转发：图片为 `kind:"image"`（≤5MiB），其余（文档、压缩包…）为 `kind:"file"`（≤20MiB），上限与 `/api/v1` 双上限一致；下载失败或超限降级为仅文本提交，纯附件消息照常提交。小表情/表情包在协议里是正文中的 `<faceType=…>` 占位符（表情包的真图同时在同一条消息的 `attachments` 里，占位符 `ext` 解出来的 `text` 为空）：桥在入站时整段剥掉——带图片附件时不留占位，没有图片时落一个 `[表情]`，协议标记因此不进模型上下文，也不出现在网页气泡里。**`content_type` 是类别词不是 MIME**——实盘一条语音收到的是 `'voice'`（18:05:42 的 INFO 日志），所以媒体分类走 `bridge.py::_content_kind`（类别词与 MIME 都认），并且下载后还要按字节兜底判语音（`_declared_mime` 保证不把 `'voice'` 当 MIME 声明给服务端，也不拿它猜扩展名——那会把语音条命名成 `.png`）。`audio/*` 是唯一不进**模型可见**附件车道的类型：本机语音识别就绪时桥在提交回合前就地转写（同一事件循环内的进程调用，不经 HTTP），文本以 `用户语音，机器识别结果：` 前缀并入本条正文，识别失败另起 `用户语音，机器识别失败：<原因>`——标记措辞、以及"为什么必须带来源标记、失败为什么要另起措辞"归 `speech-to-text.md`「提示词侧」。转写成功时桥附带一条 `kind:"audio"` 附件，装的是引擎解码后的 24k WAV（不是收到的 silk 原始字节，浏览器播不了 silk）；服务端落盘前压成 MP3（压不动退回 WAV），而 `_build_external_user_message` 在附件说明行与 `UserInputMessage.attachments` 两处都跳过 `kind:"audio"`、只在 `metadata.external_attachments` 里留下给人回放的这一份（存放与寿命见 `speech-to-text.md`「语音气泡与音频字段的存放」，渲染见 `web-and-admin.md`「Attachment Bubble Rendering Contract」）。未就绪时语音退回上面的 `kind:"file"` 形状，能力开关不允许造成回退。QQ 媒体 URL 在事件落地那一瞬间不一定可读（实测同一条语音链接先抛异常、几分钟后返回 200；其 `content_type` 写着 `audio/mp3` 而字节其实是腾讯 silk v3），因此附件下载带一次延时重试；重试仍失败且语音就绪时，正文写 `用户语音，机器识别失败：语音附件下载失败`——纯语音消息此时正文与附件皆空，`on_incoming` 会早退，用户端就是彻底的静默。每条带附件的入站消息都会 INFO 记录各附件的 `content_type` 列表，因为"事件没到"与"附件取不到"事后只能靠这行区分。转写引擎与容器格式约束见 `speech-to-text.md`。每会话一条 SSE pump 消费 `reply.final` 与 `outbound.created`（主动提醒消费分支，路由见「出站路由（主动推送）」），文本经 `post_message` / `post_group_message` / `post_c2c_message` / `post_dms` 投递；群聊那一发带被动回复参数，形状与权限见「回复形状与主动消息权限」。
- 出站附件投递：事件携带 `attachments`（见「事件流」出站附件契约）时，附件先于正文投递。群聊/单聊：桥先从本机签名媒体 URL 取字节（≤20MiB），再以 **`file_data`（base64）直传**平台媒体上传接口（`/v2/{groups,users}/…/files`）——不回源，服务端只监听回环地址也成立；botpy 的 `post_group_file` / `post_c2c_file` 包装只暴露 `url` 参数（那条路径由 QQ 服务器回源下载、要求公网可达），留作回退。拿到 `file_info` 后以 `msg_type=7` 富媒体消息发出；群聊那一发同样带被动回复参数，与同一轮的正文共用那个 `msg_id` 的 seq 计数、每发递增（见「回复形状与主动消息权限」）。mime→`file_type` 映射：图片→1、mp4→2、语音→3、其余（文档/压缩包等）→4；**图片档只保证 png/jpg/gif**，所以非这三种签名的图片字节（实测 `.webp` 表情包）在上传前转成 PNG（动图转 GIF），日志记 `qq-official converted image attachment <name> to image/png`。`kind`/`file_type` 的判据是描述符 mime，而 `.webp` 在部分 Windows 的 `mimetypes` 里没有映射——`ceo_media.guess_media_mime` 按栅格后缀兜住它，否则描述符落成 `file`、平台档落成 4（实盘 `delivered group attachment 005.webp (file_type=4)`，用户收到的是一份文件而不是表情）；`file_type=4` 在 SDK 的接口注释里写着「暂不开放」，所以文档类能否成文件气泡与图片/视频/语音不是同一档能力，复测要同尺寸各打一张图片和一个文档。语音这一档按 SDK 注释要求 **silk 容器**（腾讯语音条的真身，入站取证见 `speech-to-text.md`「已知边界」），而桥递上去的是描述符里的原始字节：出站语音由 skill `edge-tts` 产出，它只有 MP3（24 kHz / 48 kbps / 单声道，包内没有格式开关），改成 silk 需要 ffmpeg 解码 + `silk-python` 编码，本仓库在出站这一侧没有任何转码。`file_type=3` 的平台侧行为没有实盘读数——实盘成功过的只有 1 与 4（见「回复形状与主动消息权限」）——映射本身由 `tests/resources/test_qq_official_bridge.py::test_pump_delivers_audio_attachment_as_voice_media` 钉住，它钉的是"音频落 3 档并以 `msg_type=7` 发出"，不替平台保证客户端画成语音条。每发的档位印在日志上（`file_data uploaded … (file_type=<n>)` 与 `delivered <kind> attachment <name> (file_type=<n>)`），"这一发出去的是语音档还是文件档"以这两行为准，不从文件扩展名推。
  - 上传这一发走桥自己的媒体 client（`httpx`），**不走 botpy 的 `http.request`**，只沿用 SDK 的 `Route`（域名、路径参数、沙盒切换）与它的鉴权头续期 `check_session()`。理由是 SDK 那枚构造参数 `Client(timeout=…)` 是全桥共用的一把：它同时套在每条文本消息的 POST 上。这把已经被桥抬到 `_BRIDGE_HTTP_TIMEOUT_SECONDS`（15 秒，SDK 默认 5 秒对文本太紧，见同节「投递确认」），但上传不能借它——20MiB 原始文件的 base64 请求体约 27MiB，按最低吞吐折算需要 68 秒，把共用一把抬到那个量级等于让一个卡住的文本 POST 占住这条会话的 pump 一分多钟（pump 单会话串行，毒消息上限 5 次）——单条上传该有自己的预算，按字节数推导（`_media_upload_timeout`）。
  - 预算从请求体字节数推导（`bridge.py::_media_upload_timeout`）：固定开销 `_MEDIA_UPLOAD_FIXED_BUDGET_SECONDS`（15s，覆盖握手与网关收下整段 base64 后落媒体存储）加上按可接受的最低上行吞吐（`_MEDIA_UPLOAD_MIN_THROUGHPUT_BYTES_PER_SECOND`，512KiB/s）折算的传输时间，连接超时另按 5 秒判死。上限由下载封顶决定：20MiB 原始文件的 base64 请求体约 27MiB，预算 68s——这就是带附件的一发能占住 pump 的最长时间。固定开销那档目前只有握手的实测量（本机到 `api.sgroup.qq.com` 的 DNS+TLS 约 0.56s），网关落媒体要多久以逐发实耗为准：每次成功记 INFO `qq-official file_data uploaded <bytes> bytes (file_type=<n>) in <elapsed>s (budget <budget>s)`，调档靠这些读数，不靠拍数字。
  - 失败出口都有日志且都回退 `url` 路径：连回执都没有（连接/读写超时一类）记 `qq-official file_data media upload failed after ...`；平台回了非 2xx 或 2xx 但 body 里没有 `file_info` 记 `qq-official file_data media upload rejected status=... body=...`（body 截 200 字节）。`url` 回退再失败才降级为签名下载链接文本行并入正文，用户至少拿到可下载链接，附件不静默丢失。频道/频道私信无文件接口：图片下载后经 `file_image` 字节直发（这一发仍走 botpy 的 `http.request`，因此吃那枚 5 秒全局超时），其余降级签名链接文本。
- 每会话 SSE pump 的存活契约（`bridge.py::_pump`）：流异常**或干净结束**（服务端重启/空闲关闭）都按 1s→60s 指数退避自动重连。重连与入站幂等重建是硬契约：pump 一旦终结且无人重建，该会话出站事件滞留内存 hub 无人消费，形成「入站正常、出站黑洞」的僵尸态。这条流的读超时独立于客户端默认值（`client.py` 的 `SSE_STREAM_READ_TIMEOUT_SECONDS`，90s）：服务端只在 `SSE_HEARTBEAT_INTERVAL_SECONDS`(15s) 发一条 keep-alive 注释行，沿用 30s 默认读超时会让任何一次事件循环抖动（大会话转录重写即如此）掐断这条流，把真故障埋进重连噪音；因此读超时按「容得下 3 次以上心跳缺席」取值，且 `httpx.TimeoutException` 走单行 WARNING（`qq-official event stream idle timeout ...`）而非异常栈。投递成功才推进 `seqs`：失败靠服务端 `Last-Event-ID` 重放自动重试（节奏随重连退避），同一事件连续失败 5 次判为毒消息，记 error 后跳过、不阻塞后续事件；确定性失败（见「回复形状与主动消息权限」的失败分档）一次即判毒，不吃满这 5 次。带 `outbox_id` 的事件（`outbound.created` 与 `reply.final`）在同一处按 `undeliverable` 销账并把这个 id 记进投递历史：账本不按年龄回收，投递预算是永久拒投目标（超窗、被拉黑、msg_type 不被接受）唯一的重试上界，而这份计数随**进程**重启清零（实测每小时那次网关到期重登已不清它），不销账就是每次重启后又一轮 5 次。投递历史（acked 集、attempts 计数与 unconfirmed 集，各自 1024 个 id 的有界 LRU）按 bridge_id 存在进程级账本 `bridge.py::bridge_delivery_state`：已 ack 的 id 之重复副本（服务端周期对账/重启重放注入）直接跳过，用户不会收到重复内容；同一 id 跨 seq 累计投递失败达上限（5 次）后，其后续副本零尝试丢弃——重放副本各带新 seq，仅靠 per-seq 计数会让毒消息随每份副本重新获得完整重试预算。ack 失败不进去重集：副本可再投，维持 at-least-once。
- 出站幂等闸门（`bridge.py::DeliveryUnconfirmedError`）：渠道 API 无回执（`deliver` 拿到 `None`）意味着请求已经写进那条连接，只是回执没回来，服务端无法分辨「没送达」与「送达了但回执丢了」。带 `outbox_id` 的这类事件在首次失败时把 id 记进 `unconfirmed_outbox_ids`；其重放副本只推进 `seqs`、按 `unconfirmed` 终态销账，并记一条 WARNING `qq-official suppressed replayed send for outbox ...`，不产生第二次 POST。这道闸的判据是「每条无回执都可能出现两份副本」（实盘：01:14:22 `deliver failed ... seq 80 (attempt 1/5)` ⇒ 01:14:23 `pump connecting ... last_seq=79` ⇒ 01:14:24 `delivered`，同一条回答在 QQ 端出现两遍），代价是那条可能真空未达且没有第二次机会。两个边界：不带 `outbox_id` 的事件没有可幂等的身份，照旧靠重放重发；连接建立前的失败（平台 4xx、`ClientConnectorError`）不记这个标记，仍走 5 次投递预算。这份凭据只在进程内，进程重启后该 id 的重放副本会再获得一次 POST。
- pump 建立时机：首条入站消息、每次入站的幂等存活校验（`_spawn_pump` 按 session 记录任务，已死则重建）、桥启动时按 `GET /outbox/pending` 的对账首跑、以及常驻对账循环（每 30s 轮询同一清单，为「有 pending 记录且无存活 pump」的会话重建 pump）。常驻循环覆盖启动首跑扑空的窗口：服务端重启落在 cron 触发与产出之间时账本尚空，滞留消息稍后才入账，而入站消息可能迟迟不来——周期对账保证分钟级补投。list 失败只记 warning，对账循环绝不因单轮失败而死。
- 桥的两层状态必须分清：**pump 句柄**（`pumps` / `pump_tasks`）长在 `run_qq_official_bridge` 的闭包里，桥终结（重启/停用/崩溃收尾/到期重登）随 `finally` 全部取消，所以"某会话此刻没有 pump"是常态而非异常；**投递账本**（`sessions`、`seqs`、`outbox_id` 投递历史）由 `bridge.py::bridge_delivery_state(bridge_id)` 按号持有，活过整轮登录，只在进程重启时清空。游标跨重登存活是这条渠道不重复推送的前提：服务端那条会话的事件缓冲（`SessionEventHub`，512 环）长在 web 进程里，桥重登不动它，而账本的 ack 墓碑每小时随 `compact_outbox` 落盘——两边都留不住「这条已经送过了」。账本长在闭包里时每次重登同时抹掉游标与去重集，新 pump 于是只能以 `last_seq=0` 连上 SSE 并把整段历史重新投给用户（实盘：03:29:14 网关到期重登 ⇒ 03:59:50 一次 `pump connecting ... last_seq=0` 打出三条 `qq-official delivered`，其中两条是 02:33:43 与 02:40:12 已 ack 销账的回答；回归 `tests/resources/test_qq_official_bridge.py::test_bridge_relogin_resumes_from_last_delivered_seq`）。因此新建 pump 从该会话最后一次成功投递（或判定跳过）的 seq 续拉，本号没有这条记录时才从 0 起——那正是进程重启后的首连，此时缓冲里只有服务端启动重放注入的未 ack 记录，全量重放就是它该有的行为。网页在渠道会话里发起的回合因此**不能**指望入站重建：它没有入站。它的可达性来自回复本身进账本——常驻对账看到该会话有 pending 就建 pump，把回复投出去，代价是 ≤30s 延迟。缓冲被逐出或进程重启（hub 是内存态）时，服务端启动重放/周期对账带原 `outbox_id` 重新注入，桥侧按 id 去重吸收；已投递但未 ack 的事件在重建 pump 时可能重复送达，这是 at-least-once 的既定代价。身份注销会把该会话的 hub 退役（`drop_session_event_hub`），seq 因此从头计数，端点按「`Last-Event-ID` 越过本进程已发布 seq 即全量重放」兜住这个错位（见「事件流」）。
- 投递确认：`deliver` 校验 botpy 回执——botpy 的 http 层对请求超时只记 WARNING 就静默返回 `None`，无回执一律抛 `DeliveryUnconfirmedError` 而不是记一次假成功，这一条随后由出站幂等闸门决定不重发（见同节「出站幂等闸门」）；成功投递记 INFO 回执日志 `qq-official delivered ...`（含平台消息 id、`format=` 正文形状栏 `markdown`/`text`，以及 `passive=` 回复形状栏），排查「发没发出去」与「这一发是什么形状」都以该行为准。**SDK 的共用超时由桥显式抬高**：`run_qq_official_bridge` 构造 botpy client 时传 `_BRIDGE_HTTP_TIMEOUT_SECONDS`（15 秒），不能用 SDK 默认的 5 秒——实测一发群聊被动回复的 POST 跑过 5 秒，SDK 于是吞掉超时返回 `None`，桥只能记一次无回执；平台其实收了（用户在群里看得到），而出站幂等闸门为免第二份会把它按 `unconfirmed` 终态销账，于是"是否送达"变成无从判断。日志窗口内这类无回执 2/74 发。回归 `tests/resources/test_qq_official_bridge.py::test_bridge_raises_the_shared_http_timeout_above_the_sdk_default`。带 `outbox_id` 的事件（主动推送与回合回复）投递确认后经 `POST /sessions/{id}/outbox/{outbox_id}/ack` 销账；不带 body 即 `delivered`，判毒时带 `{"status":"undeliverable"}`，无回执时带 `{"status":"unconfirmed"}`（见「持久 outbox」）。
- `qq-botpy` 在核心依赖（pyproject `dependencies`）里，`pip install -e .` 即装；唯一 `import botpy` 的模块是 `bridge.py` 且为惰性导入，环境缺失时服务报 `error` 状态，不会拖垮 web 运行时。

### 回复形状与主动消息权限

一条出站消息有两种平台形状，选哪一种决定这一发要不要权限。

- **主动消息按目标节流**：额度只对**主动形状**计费，被动回复不占。桥按目标维护分钟档与日档（`_ACTIVE_SEND_PER_MINUTE`=15，低于平台单关系 20/qpm 的口径以留余量；`_ACTIVE_SEND_PER_DAY`=1000，与平台的每日 1000 条/目标对齐）。撞分钟档的那一发**不发出**、抛 `rate_limited` 交给 pump 重连退避重试（天然不齐发，也不会白挨一次 429）；撞日档的是 `quota_exhausted`，当天停发。
- **发送失败按种类决定还花不花预算**：`deliver` 把平台异常包成 `ChannelSendError(kind=...)`，pump 只对 `transient`（网络、无回执、429、5xx、认不出的文案）吃满 5 次预算；`passive_expired`（文案含 `msg_id` 与"过期"）、`active_denied`（文案含"无权限"）、`quota_exhausted` 一次判死并按 `undeliverable` 销账。判据只能是文案：botpy 的 http 层把 HTTP 400 也抛成不带数字码的 `ServerError`，所以认不出的文案一律当 `transient`——宁可多试，也不要把网络抖动判成永久失败。分类结果印在 `qq-official deliver failed ... kind=<kind>` 与 `qq-official send failed kind=... shape=...` 两行上。
- **富媒体同样走被动**：`msg_type=7` + `media` + `msg_id` 在群聊实测 `file_type=1`（图片）与 `file_type=4`（任意文件）都返回 200，所以群附件带被动参数是对的。看到别的框架对"文件/视频"摘掉 `msg_id`、把媒体一律按主动消息发，那是保守而不是平台限制，不要照抄；反过来把媒体摘成主动形状，在无群主动权限的号上等于附件一条都发不出去。
- **正文走 markdown 形状**：群与单聊的正文一律 `msg_type=2` + `markdown.content`，且**不带 `content` 字段**（平台合同：传了 markdown 后 `content` 必须为空）。频道与频道私信保持纯文本 `content`：自定义 markdown 官方只全量开给单聊与群聊，频道要内邀。渲染口径以真机读数为准，不按官方「支持格式」清单裁剪——清单只列标题/文字样式/链接/图片/列表/引用，实测代码块（带语言标签与复制按钮）、行内代码、表格、分割线全部渲染，单个 `\n` 就直接成行，零宽字符只是不可见。因此 `g3ku/qq_official/messages.py::render_qq_markdown` 只做一条归一：编号列表项紧跟在非空行之后时前面补一个空行（不补则 QQ 丢编号、把它画成上一项的嵌套子项，并把那行正文吸进列表层级），围栏内的行原样不动。`40034009「markdown参数有换行符」`属模板参数族，自定义 `content` 带上百个换行实测照收。群 @ 的 `<qqbot-at-user id="…" />` 与正文同一个 markdown 块内发出实测 200 并解析成真实 @。平台以 markdown 族文案拒绝时，`deliver` 拿同一份正文换纯文本再发一次（日志 `qq-official markdown rejected for ...; retrying as text`；回落那一发丢掉 @ 标签，文本形状不支持 @）——不回落就会被判 `transient`、吃满 5 次预算后按 `undeliverable` 销账，用户一条都收不到。
- **单条正文不分段是实测结论，不是遗漏**：往单聊实发 4000 / 8000 / 16000 字符都返回 200，客户端也完整显示；换成 markdown 形状后 8023 / 16024 字符同样全量渲染到最后一个字符。桥这一侧对正文没有任何长度上限（只有 20MiB 的**附件**字节封顶，见「事件流」出站附件契约）。所以 `deliver` 把整份回复原样发出去就是该有的行为，不需要像别家框架那样拆成多条链逐条发。真要容纳超长内容，正确方向是落成文件走附件车道，而不是分段刷屏。
- **被动窗口参数只认入站消息**。两档上限照平台口径钉成常量：窗口 `_PASSIVE_REPLY_WINDOW_SECONDS`（5 分钟）、同一 `msg_id` 最多回 `_PASSIVE_REPLY_MAX_PER_MESSAGE`（5）次；平台还会拒**相同 `msg_id`+`msg_seq` 的重复发送**，所以 pump 失败重放的那一发必然换新 seq，而不是重试同一发。正文与附件共用同一个 msg_id 的 seq 计数，每发递增。实盘对照（同一条入站、相隔数秒的两发）：入站 id 上 `seq=2` 仍返回 200，说明一条入站在窗内可换多发；把 id 换成**机器人自己刚发出的那条消息**（远未过 5 分钟）则返回 `400 / code 40034005「回复消息msg_id已过期」`，说明平台不把自家输出当可回复对象——**"用上一条回复续窗"这条路不成立**，看到别家框架缓存发出消息的 id 当票据也不要照抄。
- **主动消息**：不带 `msg_id`，平台按主动推送判定并要求该目标具备主动消息权限。

分工按实测结果定：**群聊只在被动窗口内可达**。群目标实测没有这项权限——每一次 POST 被判 `400 / code 40034105「主动消息失败, 无权限」`，5 次投递预算打穿后按 `undeliverable` 销账，实盘读数里 `qq-official delivered` 只有 `kind=c2c`、群 0 条。单聊与频道用同一主动形状实测发得出去，因此保持原形状：不给一条能用的车道换风险。

落回主动道的两类形状对群就是必然被拒的：**超窗**（长回合，或网页在渠道会话里发起的回合——那条回复要等账本对账在 ≤30s 内拉起 pump 才被消费，晚于入站 5 分钟即出窗）与**回满 5 次**。这两类的出路不在桥内，只有为该号申请群聊主动消息权限；桥的处置照旧是预算用尽后判毒销账，症状仍是"网页有完整回复、群里什么都没有"，用 `qq-official delivered` 那行的 `passive=` 栏认形状（`<msg_id>#<seq>` 是被动，`-` 是主动）。被动引用按**目标**持有，不按事件类型：任何一发群聊消息——回合回复、排队回执、主动推送都算——落在窗口内就用掉一格 seq。渠道会话的回合时长实测（同一 openid 的两个会话键，220 与 489 轮配对）是 p50 86/75 秒、p90 579/338 秒，超过 300 秒的那 10–25% 因此必然出窗。

主动推送（心跳、cron、任务终态）没有可回的入站，那一发落在窗口之外就是主动形状，群里同样受这项权限约束；推送目标还必须先注册过会话（该用户/群先与机器人产生过消息）。平台侧还有两条不由本桥决定的限制：接收端「允许主动发送」开关关掉时主动消息一律发不出去，而群聊没有单聊那种「互动召回」额度（单聊在用户发起对话后 30 天内可有 4 次周期性下发），群与单聊共享每日一千条的主动上限。

## 8. 常见排障入口

- 桥拿到 403 `external_api_disabled`：配置 `externalApi.enabled` 与 tokens；401：token 不匹配或条目被禁用。403 `cross_session_scope_required`：这个 token 的作用域是"仅本桥"，却在请求 `scope=all`。别名下的会话一律 404 `session_not_found`——先分清是"这个键真不存在"还是"作用域把它挡在外面"，判据在「启用与鉴权」的作用域一档：404 也出现在跨桥寻址被关掉的时候，而不是只在拼错键的时候。
- 消息提交成功但桥收不到回复：先确认 pump 是否真的在跑——锚点 `qq-official pump connecting session=<会话键> last_seq=N`，**每次连接尝试一条 INFO**。它在、而 `qq-official delivered` 不在 ⇒ 事件没到或投递被判失败（找桥侧 WARNING）；它一条都没有 ⇒ pump 从未被执行（任务没被调度/桥没建 pump），此时 18790 上会只剩浏览器 WS 那条回环长连接，`outbox.jsonl` 也是空的——这是"入站正常、出站黑洞"的最小心证；`connecting` 之后紧跟一条 WARNING `qq-official pump cancelled for session <会话键>` 则是第三种形态，指向桥自身在该时刻被重建（pump 随桥的 `finally` 一起取消，判据是同进程里 `[botpy] 登录机器人账号中...` 的条数在涨），先查 sync 是否丢了幂等而不是查 pump。再确认桥订阅的 SSE 会话与消息提交的会话一致（同一 `session_id`）；看事件缓冲是否被 `eventBufferSize` 淘汰（长断线超过缓冲窗口）。回复也登记进持久账本，所以分界在账本里读得到：`GET /outbox/pending`（或 `.g3ku/external-outbox/outbox.jsonl`）里有这条 `event=reply.final` 而未 ack ⇒ 泵/重注入路径的问题；连记录都没有 ⇒ 该会话拿不到 `external_key`（注册表里没有它的孤儿转录，只走内存投递），或登记本身失败（锚点 `external outbox append failed`）。
- 渠道端收到重复内容（旧回答跟着这一轮的新回答再投一遍）：分三种形态。一种是一次登录里 `qq-official pump connecting ... last_seq=0` 之后紧跟多条 `qq-official delivered`，而 `outbox.jsonl` 里那个会话只剩最新一条 `reply.final`（其余都已 ack 并随每小时压实落盘）——那是桥的投递游标与 `outbox_id` 去重集没了，按「内置官方 QQ 适配器」的桥两层状态查：账本要跨到期重登存活，只有进程重启才该清空（那时 hub 同样是空的，全量重放才是对的）。第二种是同一 `outbox_id` 的两份副本各投一次（服务端周期对账/启动重放注入的正常形状），锚点是 `qq-official outbox ack failed ...; may redeliver after restart`：ack 一直失败才会留下重复送达的窗口。第三种是同一个 `outbox_id` 只有一份事件却被 POST 两次：`qq-official deliver failed ... (attempt 1/5)` 带 `RuntimeError: qq-official delivery unconfirmed (empty API response)`，紧跟一次 `pump connecting ... last_seq=<本条 seq-1>` 与一条 `delivered`——渠道 API 收了请求却没给回执，重放按 at-least-once 又发一份。出站幂等闸门把这类副本拦在同一 id 上：只销账、不重发，落一条 WARNING `qq-official suppressed replayed send for outbox ...`，账本留下 `{"status":"unconfirmed"}` 的 tombstone（机制见「内置官方 QQ 适配器」出站幂等闸门）。分形态先用转录：`sessions/*.jsonl` 里只有一个助手行而渠道端收到两条，是第三种形态；两个助手行才是重复起轮。
- 出站消息不到达（主动推送与回合回复）：沿「出站路由（主动推送）」链路查——发布侧（`source=heartbeat` 日志）→ drain（`external outbound published to hub`，含 outbox_id；伴随 `no live subscriber` WARNING 说明发布时无人消费，属对账兜底路径）→ 桥侧回执（`qq-official delivered ...`）。有 published 无 delivered 说明事件没有消费者（先看 `qq-official deliver failed ... kind=` 那一栏：`transient`/`rate_limited` 是重连重试，`passive_expired`/`active_denied`/`quota_exhausted` 是一次判死的确定性失败，见「回复形状与主动消息权限」）：查 pump 重连日志（真故障：`qq-official event pump error ... reconnecting` 带异常栈；流安静过头：WARNING `qq-official event stream idle timeout ...`；服务端干净关闭：WARNING `event stream ended ... reconnecting`）与 `GET /outbox/pending` 滞留清单。滞留消息的补投不依赖重启：服务端 60s 周期对账（动作日志 `external outbox reconcile: republished ...`）与桥侧 30s 对账（动作日志 `qq-official spawned ... pump(s) from pending outbox entries`）自动收敛。账本没有年龄出口：记录 pending 到被某个消费方 ack、或被判 `unreachable`/`undeliverable`/`unconfirmed` 为止，所以"几天前的东西反复投"要先查有没有消费方在 ack，三条终态锚点是 `external outbox record retired as unreachable`、`qq-official dropping undeliverable event ...` 与 `qq-official suppressed replayed send for outbox ...`。会话转录/Web UI 里看得到回复而渠道端收不到时，优先怀疑本链路——转录落盘与渠道投递是两条独立链路。分形状读 `qq-official delivered ... (id=..., attachments=..., passive=...)` 的最后一栏：`<msg_id>#<seq>` 是被动回复，`-` 是主动消息形状。群目标只有被动形状能落地，所以"群里 @ 了没回复、单聊照常"先看这一栏是不是 `-`（超窗或回满 5 次），再看桥侧是否有 `botpy.errors.ServerError` 配 `code 40034105`（平台按主动消息判该目标无权限）与随后一条 `qq-official dropping undeliverable event ...`；两种形状都试过的会话会同时留下 delivered 与 dropping。判据与残留范围见「回复形状与主动消息权限」。回合由网页发起（`/ws/ceo` 的渠道输入车道）时，那发回复晚于入站 ≤30s 才由账本对账拉起 pump，对群目标即出窗形状，先按同一条契约确认。
- 渠道端收不到文件（只收到链接或什么都没有）：先确认事件是否携带 `attachments`——出站附件只由正文中**存在的本地文件**的 markdown 链接触发（见「事件流」出站附件契约），裸路径引用不提取；再看桥侧日志，出站上传车道每发都留实耗（合同见同节「出站附件投递」）：`qq-official file_data uploaded <bytes> bytes (file_type=<n>) in <elapsed>s (budget <budget>s)` 是直传成功；`(file_type=3)` 就是音频落进了平台语音档，这一栏也用来分"上传成功但渠道端不是语音条"——那种情况是容器不是平台要求的 silk，与投递车道无关（见「内置官方 QQ 适配器」）。`qq-official file_data media upload failed after <elapsed>s ...` 是这一发连回执都没有（连接、读写预算判死），正在回退回源上传；`qq-official file_data media upload rejected status=... body=...` 是平台回了非 2xx 或回了但没有 `file_info`；`qq-official attachment delivery failed ... degrading to text link` 表示两条上传路径都失败、或取字节失败/超 20MiB，用户会收到签名链接文本行。成功行里 `<elapsed>` 逼近 `budget` 就是该调预算档的信号，而一条 `uploaded` 都没有、只有 `degrading`，先按字节量核对是不是根本没发起上传。botpy 自己的 `请求超时，请求连接: https://api.sgroup.qq.com/v2/.../files` WARNING 属于 SDK 的 `http.request` 车道，媒体直传不走它——看到这行说明有上传调用被搬回了那条带全局 5 秒旋钮的道。OneBot 桥走 `upload_*_file` base64 直传，失败同样降级为链接行。入站侧：桥只转发带绝对 http(s) URL 的附件，文件类入站上限 20MiB。
- 终态缺失导致桥状态悬挂：属实现缺陷，对照「回合契约」终态不变量检查执行器改动。
- QQ 机器人面板报错/不连接：`/api/qq-bot/status` 与 settings 的 `accounts[]` 都**按号**给状态，先定位是哪一号再看它的 detail——AppID/AppSecret 错误表现为登录失败，intents 未开通表现为网关拒绝；出现 "This event loop is already running" 说明桥被改回了阻塞 `Client.run()` 入口。detail 带「将在 Ns 后重试」说明瞬时崩溃正按「崩溃自愈契约」退避重连，等待其自愈即可；detail 为「QQ 网关会话到期，将在 Ns 后重新登录」且 state 停在 `connecting` 是每小时一次的到期重排（网关 close 4009），按设计无需处理，判据是日志锚点：到期记 `gateway session ended after Ns`（WARNING、无栈），崩溃记 `crashed; retrying in Ns`（ERROR、带栈）。把两者混为一谈会把正常节拍当故障去找网关问题。detail 为 botpy 缺失/intents 不兼容属环境终态，需修环境后刷新配置触发重启。状态值区分 `enabled_off`（总开关）与 `account_disabled`（本号停用）：只看到前者就去找单个号的配置会走弯路。改过 AppSecret 的号若一直停在旧凭证的重试里，确认重启签名是否含密钥摘要。
- 整个服务停止响应但端口仍在 LISTENING（网页、`/api/*` 全部超时，进程单核跑满）：抓一根栈（`py-spy dump --pid <web 进程>`），MainThread 落在 `botpy/connection.py::multi_run` / `client._pool_init` 就是桥重入了 vendor 的会话循环，判据与修法归「运行入口是硬约束」。这种状态下「重启并更新」表现为点了没反应：执行体的 `POST /api/bootstrap/exit` 无人处理，60s 超时后按设计等端口释放、90s 后放弃且不动代码，日志锚点 `.g3ku/logs/update-apply.log` 的 `exit request: exit_unreachable` + `abort: port ... still busy`。它与"桥在退避重连"不同——后者只有渠道静默，web 照常响应。
- 加第二个号之后"原来那条 QQ 会话不再回话"：新格式下同一个 AppID 也会得到新的 bridge 段与新会话键，**存量会话不迁移**（旧键的转录/sidecar/记忆作用域原样留在会话列表里作为历史）。症状是旧会话在网页里仍可读写、QQ 端什么都没有——那条会话已经没有桥在消费它的事件了，发布侧会打 `no live subscriber`，滞留的记录按 1h 封顶的退避反复重注入，直到该 bridge 的 token 停用被判 `unreachable`。要保住的是指向旧会话键的 cron/心跳目标：把它们改指新会话键。
